- **事件 scene 实际取值**（前后端必须同步）：`image`、`video`、`model3d`、`llm`、`writing`、`character_portrait`、`world_extraction`、`world_generation`、`world_map`、`asset_provenance`、`pipeline`、`agent_canvas`、`system`、`download`、`stt`、`embedding`
  - 来源：`backend/app` 全量 `record_event(scene=...)` 扫描 + 前端 `EventLogTab` 场景下拉
- **任务持久化白名单**：`image_generation`、`creative_writing`、`world_domain_expansion`、`world_map_visual`；独立放行：`novel_download`、`live2d_processing`
- **事件/任务状态**：`pending` / `running` / `done|completed|succeeded` / `failed` / `cancelled`

## 六、工程约束与模式

1. **双层观测模式**：调用类事件自动收口（`ai_call_context` 注入身份与 `retry_payload`），业务语义事件手写并用 `suppress_auto_event` 抑制自动记账，避免同一操作落两条。
2. **任务不能自动收口**：高频 `chat` 若自动建任务会冲垮任务中心；任务需要业务粒度（一次"地图成图"一条）。
3. **重试必须复用业务端点函数**：重建参数后直接 `await generate_video(req)`，保证资产入库、项目关联、事件与新任务与手动生成一致；不要另写一份 provider 直连逻辑。
4. **前端任务类型选项必须与后端白名单同步**：`TASK_TYPE_OPTIONS` 缺项会导致用户在下拉里筛不到任务（本 change 曾出现 `novel_download`/`world_map_visual` 漏配）。
5. **不落库要说明原因**：`should_persist` 返回 False 时必须打日志（否则表现为"任务凭空消失"，无从排查）。
6. **降级可用的重要细节**：`generate_image/generate_video/chat` 直接函数调用时 `external_key` 要显式传 `None`，避免把 `Depends(...)` 默认对象传进业务逻辑。

## 七、设计决策

| 决策 | 理由 | 被否决的方案 |
|---|---|---|
| 事件日志与任务账本分两套 | 前者是只读审计流、后者要驱动恢复；混在一张表会让审计被恢复逻辑污染 | 单一"任务+事件"大表 |
| 任务不全量持久化 | 只登记白名单类型，避免高频/临时任务把表撑大 | 无条件持久化所有任务 |
| 不建 ELK/OTel | 先用轻量 in-app 方案覆盖主流程，避免过度基建 | 一期即引入系统级观测平台 |
| 取消只改状态 | 队列不持有 asyncio 句柄，真实中断需业务侧协作；先诚实反映用户意图 | 假装能强杀执行中的协程 |
| 重试 = 重新提交（产生新任务） | 保留原任务可追溯，行为与手动重新生成一致 | 原地重放 provider 请求（会丢资产/事件链路） |
