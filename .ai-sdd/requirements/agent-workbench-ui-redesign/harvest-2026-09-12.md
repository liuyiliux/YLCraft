## 二、术语与业务对象（6 项 ✅ 新增）

| 术语 | 定义 | 证据 |
|---|---|---|
| **三区布局** | `/agent` 页面的顶层结构：顶部控制栏（52px 单行）→ 左栏会话 → 中部消息列，底部为输入区与遥测条 | design.md §3、`index.tsx` 的 `pageShell` |
| **顶部控制栏（Top Control Rail）** | 单行控件条：智能体选择 + 模型 + 默认工作流 + 查看运行轨迹 + 工具与权限 + 智能体设置 + 刷新 | `index.tsx` `commandBarStyle` |
| **待确认横幅 vs 确认卡片** | **横幅**在顶部控制栏下方，只做提示（准确条数）+ 定位（滚动到卡片），不含操作；**确认卡片**在消息列顶部，才承载确认/拒绝按钮。两者职责不重叠、文案不重复 | `index.tsx` 顶栏 Alert 与消息列卡片 |
| **遥测条（Telemetry Strip）** | 输入区上方一行：Run 状态 / 步骤 / 工具 / 耗时 / Token / 成本，等宽字体，缺失显示 `--` | `index.tsx` 底部状态栏 |
| **`thread.status` 与 run 级状态** | `thread.status` 属于**线程**（`AgentThread`），run 级的 running/待确认/完成/失败属于 **`AgentRun`**。二者不是一回事，混用会导致"看似有状态字段、实则拿不到想要的值" | `db/models/agent.py` `AgentThreadBase` |
| **运行轨迹（trace）默认折叠** | 工具调用与每步 trace 以 `<details>` 渲染，仅在运行时 `open`，完成后自动折叠；失败/待确认仍在折叠态可见 | `index.tsx` `<details open={isRunning}>` |

## 三、业务规则与校验逻辑（7 项 ✅ 新增）

| 规则 | 内容 | 证据 |
|---|---|---|
| **顶栏模型/工作流写回配置** | 顶栏的「模型」与「默认工作流」下拉**直接写回当前智能体配置**（`updateAgentProfile`），**不是**本次请求的临时参数。原因：run 载荷不含 model/mode 字段，而这两项决定运行时实际行为。UI 必须给出「已保存到智能体配置」反馈 | `applyProfileSetting` |
| **拒绝工具确认 = 取消整个运行** | 后端无 step 级 reject 端点，故「拒绝」复用 `cancelAgentRun`。**必须**用二次确认写明后果（"后端暂不支持只跳过这一步，拒绝会取消当前整个运行"） | `handleRejectRunStep` + `Popconfirm` |
| **会话状态点「有数据才显示」** | 只在状态可知时渲染状态点；无数据时**不渲染**，不用默认值/推测值冒充 | 左栏会话列表 |
| **遥测缺失显示 `--`** | 字段缺失显示 ASCII 双连字符 `--`（不是中文破折号 `—`）；无 run 时「步骤」「工具」也显示 `--` 而非 0 | 底部遥测条 |
| **卡片收敛的四类例外** | 优先用 `borderTop` 分隔线 + 留白替代带边框卡片；**保留边框**的例外：① 页面外壳 ② Markdown 表格单元格 ③ 选中态（左栏 section / 工具授权 / 会话激活）④ 错误与待确认隔离（failed/pending 步骤卡）。另有虚线占位区保留 | design.md §4 + 本轮实现 |
| **窄屏折叠按类名不按序号** | 顶栏在 ≤820px 折叠次要控件，用 `.agent-rail-optional` 类名定位，**不要**用 `:nth-child(n)` | `index.css` @media 820px |
| **缓存区 opt-in** | cache 命中率 / 首 token 均值依赖 provider usage 数据，数据不可用时**整个区块不渲染**（代码中不存在即为正确状态），依赖已记于 design | design.md §3.4 / §5 |

## 四、API 知识（5 项 ✅ 新增）

| 接口 | 关键约定 |
|---|---|
| `POST /agent/runs/{run_id}/steps/{step_id}/confirm` | 确认并执行 pending 工具步骤；前端 `confirmAgentRunStep(runId, stepId)` |
| `POST /agent/runs/{run_id}/steps/{step_id}/memory-candidates/save` / `/discard` | 记忆候选的保存与丢弃（**这一对是完整的确认/拒绝**） |
| `POST /agent/runs/{run_id}/cancel` | 取消整个运行；当前被「拒绝工具确认」复用（见业务规则） |
| `GET /agent/threads` | 返回 `id / thread_id / session_id / title / status / active_profile_id / created_at / updated_at`。**`status` 与 `active_profile_id` 此前前端未声明而被丢弃** |
| `updateAgentProfile(profileId, patch)` | 前端可直接改 `model` / `default_workflow` 并持久化；顶栏依赖它 |

## 五、数据表/字段知识（4 项 ✅ 新增）

| 表/字段 | 结论 |
|---|---|
| **`AgentRun`** | **没有** `duration_ms`，也**没有** `token_estimate` / `total_tokens` / `cost`。proposal 与 design 均假设 `AgentRun.duration_ms` 存在，**与代码不符** |
| **`AgentRunStep`** | 有 `duration_ms` ✓（所以"每步耗时"可用，但"整个 run 耗时"只能由各步累加近似） |
| **`AIUsageLog`** | 有 `prompt_tokens` / `completion_tokens` / `total_tokens` / `cost` / `latency_ms`，但**未与 agent run 关联**（无 run_id 类外键），故无法按 run 聚合 |
| **`AgentThread`** | 有 `status` 字段并被 `/agent/threads` 返回；但写入处仅 `active` 与 `archived`（archived 被列表过滤）。`running` 出现在 `AgentRun` 上，不在线程上 |

## 六、枚举与字典（3 项 ✅ 新增）

- **`AgentThread.status` 实际取值域**：`active` / `archived`（**不要**假设还有 running/awaiting/done/failed）
- **`default_workflow`（智能体默认工作流）七档**：`general_assistant`（通用助手）、`creative_project_advance`（创作项目推进）、`novel_writer_room`（小说写作室）、`character_visual_card`（角色视觉卡）、`storyboard_reference_match`（分镜参考匹配）、`asset_curation`（素材整理）、`quality_review`（质量检查）
- **会话状态点四态**：运行中 / 待确认（`#faad14`）/ 完成（`#52c41a`）/ 失败（`#ff4d4f`）——**仅当前会话可得**

## 七、工程约束与踩坑（6 项 ✅ 新增）

1. **窄屏折叠禁用 `:nth-child`**：顶栏控件会随功能增长而插入，序号定位会在新增控件时**静默错位**（隐藏的变成新控件，原按钮仍占位导致横向溢出）。改用稳定类名（本项目为 `.agent-rail-optional`）。本轮就是插入两个下拉后触发该问题。
2. **`tabular-nums` ≠ 等宽字体**：前者只保证数字等宽对齐，后者才是 `font-mono`。若遥测条只写 `fontVariantNumeric` 而没设等宽字体族，与"等宽数字"的字面要求不符。做法：把等宽字体栈加在**容器**上（拉丁字符与数字走 mono，中文标签自动回退 CJK 字体，无需逐个 span 设置）。
3. **批量替换 `border` 时按缩进天然分层**：用相同缩进做 `replace_all`，可自动跳过页面外壳（缩进更少）等需要保留四周框的容器——本轮靠缩进差异正确跳过了 `pageShell`。但**必须事后枚举确认没有遗漏目标**。
4. **JSX 注释不能作为 `&&` 表达式的第二个兄弟节点**：`{cond && ( <A/> )}` 里若把 `{/* 注释 */}` 与 `<A/>` 并列，会报 `JSX expressions must have one parent element`；注释应放在子元素内部。
5. **内联 `style` 会被样式表的 `!important` 覆盖**：`.agent-workbench` 的媒体查询大量使用 `!important`，因此即便某元素有内联样式（如 `gridTemplateColumns`），媒体查询里的 `!important` 仍生效——判断响应式行为时不能只看内联样式。
6. **审计"已勾选"任务必须逐条比对字面描述**：本 change 有 3 项勾选与事实不符（见下节）。勾选项不等于已实现，反之亦然——本次 #12/#17 是实现了却没勾。

## 八、设计决策（4 项 ✅ 新增）

| 决策 | 理由 | 被否决的方案 |
|---|---|---|
| 模型/工作流写回 `AgentProfile`，不进 run 载荷 | change 限定 frontend-only，而 run 载荷本无这些参数；写回配置既真实生效又不碰后端 | 伪造一个"只影响本次"的下拉（无处生效） |
| 缺数据时不伪造 UI 状态 | 会话状态点只渲染可知状态、Token/成本显示 `--`——不可见的数据若用默认值冒充，用户会误判 | 用 `updated_at` 反推状态、用 0 代替缺失 |
| 拒绝复用 `cancelAgentRun` 并明确告知后果 | 后端无 step reject；与其不做（规格缺一块）或新增后端（超出范围），不如复用现有能力并把差异讲清楚 | 新增 step reject 端点（范围外）/ 留缺口不实现 |
| 卡片收敛保留四类边框例外 | design §4 明确"仅层级需要时才用卡片"；页面外壳、表格、选中态、错误隔离都属于需要边框表达层级或状态 | 一律去边框（表格与选中态会失去可读性） |

## 九、冲突项（4 项，均需人工确认）

### 冲突 1 — `AgentRun.duration_ms` 是否存在
- **现有描述**：proposal.md「Wire existing backend telemetry fields」与 design.md §3.4/§5 均称 `AgentRun.duration_ms` 可用。
- **新发现**：`db/models/agent.py` 的 `AgentRun`（继承 `AgentRunBase`）**没有**该字段；前端 `AgentRun` 类型也没有。只有 `AgentRunStep.duration_ms` 存在。
- **分析**：文档写作时基于假设；实现阶段未回填修正。
- **建议**：**更新现有描述**——改为"run 级耗时由各步 `duration_ms` 累加近似；真正的 run 级耗时需后端补字段"。

### 冲突 2 — token 与成本的可得性
- **现有描述**：proposal 称"YLCraft 已记录 `AIUsageLog`（tokens, cost）"，design §3.4 据此要求展示 `Token N` / `成本 $N`。
- **新发现**：`AIUsageLog` 确有这些字段，但**未与 run 关联**，无法按 run 聚合。
- **分析**：字段存在 ≠ 可关联；这是 schema 层面的缺口。
- **建议**：**两者共存并区分**——保留"要展示"的目标，同时标注"当前不可得，恒显示 `--`，需后端补关联"。

### 冲突 3 — 会话状态点的数据来源
- **现有描述**：design §3.2 要求"会话项带状态点（运行中/待确认/完成/失败）"。
- **新发现**：`/agent/threads` 只返回 `thread.status`，取值域仅 `active`/`archived`。
- **分析**：需求合理但数据契约未跟上。
- **建议**：**保留需求、标注缺口**——实现按"有数据才显示"，并在文档中写明需后端补「最近一次 run 状态」。

### 冲突 4 — 「拒绝」的语义
- **现有描述**：spec R1 与任务 #5 要求确认卡提供 `确认执行` 与 `拒绝`。
- **新发现**：后端无 step 级 reject；当前「拒绝」= 取消整个运行。
- **分析**：语义比字面更重，但已在 UI 二次确认中写明。
- **建议**：**共存并区分**——UI 如实告知，文档记录"真正的跳过单步需后端端点"。
