# agent-team-composition 知识回流（2026-09-13）

来源：`openspec/changes/agent-team-composition`（归档当日收口：17/23 → 21/23，余 2 项前置不存在）。
配套：`openspec/changes/archive/2026-09-13-agent-team-composition/`。

## 一、术语（→ domain-glossary）

1. **主机平面（host plane）**：进程级单例——工具/技能/子代理注册表、会话存储、模型路由、成本计量、沙箱与审批栈。跨会话共享是**设计意图**，不是缺陷。
2. **代理平面（agent plane）**：per-session / per-role 状态——persona、计划模式、压缩器、循环检测器、工具执行器、技能路由器、上下文装配器。**必须隔离**。
3. **声明式团队模板（TeamTemplate）**：团队 = 角色清单 + 依赖 + join + 预算，由 YAML 描述；运行时只做实例化、调度、连接，不含角色专属执行逻辑。
4. **能力授权（authority grant）**：角色挂载的 `profile` + `tools` + `skills` + `spawn` 不是普通配置，而是**权限授予**。挂载即授权变更。
5. **前缀缓存稳定（prefix-cache stability）**：工具 schema 按名称字典序、字节级确定，使同一工具集的请求前缀可被 provider KV 缓存复用。
6. **压缩溯源引用（`system_prompt_ref` / `tool_schema_ref`）**：压缩产物除"折了哪些消息"外，还指名它是在哪一版系统提示与工具 schema 下产生的。

## 二、规则（→ business-rules）

1. **模板校验失败绝不 fallback**：依赖环、缺 join、未知 profile ⇒ 结构化错误，在任何子代理启动前拒绝，**绝不回退到已删除的硬编码执行路径**（避免静默回归）。
2. **失败不得降级为普通文本**：校验失败、运行时缺失、预算超限都以结构化失败呈现。
3. **模式切换不增删工具**：变更类工具保留在目录里，用追加的指令文本覆盖行为；隐藏工具会破坏从首个变动 schema token 起的缓存复用。
4. **压缩是有损状态迁移，不是效率优化**：压缩产物必须携带源 span 引用 + 摘要版本 + 确定性展开路径（+ 本次新增的 prompt/schema 引用），否则等于制造"无版本的记忆替身"。
5. **归档前必须核对 delta spec 是否描述了未实现的行为**（本次新增的程序性规则）：本次归档前发现该 change 的 delta spec 有 3 处描述尚未实现（plan/batch 模式下的目录稳定性、能力变更的审批路由、persona/plan-mode 实例化），已按事实收窄后再归档。**若原样归档，主 spec 就会长期宣称不存在的能力。**

## 三、数据（→ data-model / enum-dictionary）

1. **委派任务上下文即不可变授权溯源**：`TeamComposer.build_tasks` 为每个任务写入 `context["team_role_authority"]`（= `role_capabilities(role)`，工具与技能**排序**以获得稳定表示），该 context 随子 Run 的 `context_json` **一次性落库**（`runtime/delegation.py`）。事后可核对"本次委派授予了哪个角色哪些权限"，不必依赖可能已被修改的模板文件。
2. **`spawn_mode` 取值**：`spawn`（全新子会话 + 冻结有界快照）/ `fork`（继承父上下文只读引用）；`shadow` 类无值。

## 四、工程约束（→ design-conventions）

1. **`AgentScope` 需要一个"安装既有作用域"的入口**：`enter(host, agent)` 只能装新建的；调用方常需要先 `child()` 派生（继承 host 与团队上下文、隔离 agent 平面）**再安装**，故补 `enter_scope(scope)`，退出与异常路径都恢复上一层。
2. **隔离要靠结构保证，而不是靠"恰好各自 new 了实例"的约定**：接线 1.2 前复核发现，`AgentService` 的状态**本就是实例级**、`services/agent/` 下**无模块级可变态**——即"角色共享可变实例"的风险当时并不存在。价值在于把隔离从约定升级为结构保证。
3. **同一形状的定义只能有一份**：`capability_diff` 与运行溯源原本会各写一份角色授权形状，提取公共 `role_capabilities(role)` 后共用，避免漂移。顺带让此前**在生产代码里零调用**的 `capability_diff` 真正被用到。
4. **统计测试函数时正则必须覆盖 `async def`**（本条已第二次踩）：`^def test_` 会漏掉项目里大量 `async def test_`，据此得出"某项无测试覆盖"的结论是**错的**。正确写法 `^(?:async\s+)?def\s+test_`。
5. **平台级 API Key 的开关语义**：`REQUIRE_KEY` 关闭 = 不强制携带，但**携带即必须有效**（无效 Key 仍 401）。

## 五、设计决策

1. **不引入 Cordis / LangGraph / CrewAI / AutoGen**：只借鉴"声明式组合 + 平面边界"的思想，在 Python/FastAPI/SQLModel 语境下原生复刻。
2. **用显式作用域容器复刻 DSH 的 `isolate` 域**，而不是依赖模块级全局。
3. **`MultiAgentCoordinator` 保留为 HTTP 兼容门面**（响应形状不变），内部改为 `TeamComposer.run("scene-sim")`；确认 legacy 执行代码已整体删除（`AgentSlot` / `_store_candidate` / `use_team_template` / `_run_hardcoded` 全库 0 处）。
4. **归档时收窄 spec 而非保留过度声明**：`Capability Provenance And Approval` → `Capability Provenance`（去掉审批路由的 SHALL，改为说明性注记），并移除 `Mode switch preserves catalog` 场景（模式不存在）。理由：主 spec 是后续 change 的"当前真相"，宣称不存在的能力会直接误导。

## 六、未完成与阻塞（不得掩盖）

1. **2.4 后半（能力变更走草稿审批）无实现对象**：团队模板是仓库内 YAML，变更走 git 评审；`api/v1/agent.py` 中**不存在模板创建/更新端点**，没有可挂审批的写入路径。`AgentSkillDraftService` 面向的是**技能**草稿，与模板角色授权是两套对象。
2. **4.2（plan/batch 模式保持工具目录不变）无实现对象**：`plan_mode` / `batch_mode` 全库 0 命中；约束当前空洞成立，前缀稳定性由 4.1 的字典序断言保证。待引入该模式时方可执行。

## 七、对照外部研究（复用既有 §9.20）

本 change 与 `docs/papers/2608.25512-spatiotemporal-composability.pdf`（DeepSeek × 北大）的对照结论：
- **空间可组合性**：本项目的 `TeamTemplate.depends_on` + 校验器环检测已对应；但**无"变更即通知"的响应式机制**。
- **时间可组合性**：`AgentScope` 是**作用域回收**，不是论文要求的**可逆效应**（每次上下文变换携带运行时持有的显式逆操作）——若将来做"Agent 自己改自己的工具"，这正是会撞上的缺口。
