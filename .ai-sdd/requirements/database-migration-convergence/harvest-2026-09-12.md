## 二、术语与业务对象（4 项 ✅ 新增）

| 术语 | 定义 | 证据 |
|---|---|---|
| **Alembic head / revision** | 迁移链顶端 revision；本仓库当前唯一 head 为 `008_add_project_publish_records`，链为 `2d4ffb118355 → 002 → … → 008` | design.md |
| **运行时 DDL（Runtime DDL）** | 应用代码里执行的 `create_all` / `table.create` / `ALTER TABLE`，与 Alembic revision 相对立 | design.md「Runtime DDL Inventory」 |
| **元数据漂移（metadata drift）** | 线上库的实际 schema 与当前 SQLModel metadata 之间的差异（本项目审计出 177 处，含已废弃的 legacy 表与历史 default/nullable/index 差异） | design.md |
| **一次性演练库（disposable rehearsal DB）** | 由 `template0` 建出的临时 PostgreSQL，用于验证迁移链后**在 `finally` 中销毁**，绝不触碰生产库 | 任务 #5 / #10 |

## 三、运维安全规则（5 项 ✅ 新增）

| 规则 | 内容 |
|---|---|
| **升级是运维动作，不是请求路径动作** | `alembic upgrade head` 只能由运维/部署显式执行；应用**永不**自动升级远程库 |
| **每条运行时 DDL 必须有归宿** | 三选一：被某个 revision 表示 / 作为记录在案的临时兼容例外保留 / 其迁移验证通过后移除。不允许"谁也说不清"的 DDL 留在代码里 |
| **升级前必须备份并记录 `alembic current`** | 升级远程库前先备份并留存当前 revision |
| **迁移测试只用一次性数据库** | 迁移测试**不得**连接或改动配置中的远程库 |
| **部署完成的判据是三合一的** | `alembic current` 到位 + 针对性 API 检查 + 应用启动日志确认 head 且未触发兼容 DDL |

## 四、工程约束与踩坑（5 项 ✅ 新增）

1. **⚠ `alembic_version.version_num` 默认只有 `VARCHAR(32)`，存不下长 revision id**。本仓库的 `003_add_image_prompt_reference_library` 就超长，导致首次演练在 revision `003` 完成前就失败。修法：在 revision `003` 的**第一个操作**里先把该字段扩到 `VARCHAR(128)`——**必须早于** Alembic 写入自己的 revision id，否则来不及。
2. **⚠ 只由运行时 `create_all()` 建出的表，全新库会缺**。`project_publish_records` 曾在 SQLModel 里存在，但 revision `001`–`007` 都没有它，只有运行时 `create_all()` 提供；`--autogenerate` 因为历史原因也没补上。最终由 revision `008_add_project_publish_records` 补齐建表、两个外键与七个索引。**判断"迁移链是否完整"不能只看代码能跑通，要看全新库能否从 `001` 升到 head。**
3. **Alembic `env.py` 必须导入完整模型包**：改为 `import app.db.models` 后再赋 `SQLModel.metadata`，这样 `--autogenerate` 才能看到 Agent、创作项目、画布、Prompt 库、任务等全部表，而不是手工挑选的子集。已有回归测试守护这一点。
4. **只读诊断工具的价值**：`tools/check_migration_state.py` 只读 `alembic_version`、报本地 head、并对连接串密码脱敏；**不**调用 upgrade/stamp/create_all/DDL。结果非 current 时应视为"备份与演练的依据"，而不是"可以改远程库的许可"。
5. **元数据漂移数字要谨慎解读**：全量比较报出 177 处差异，但同时 revision `003`–`007` 引入的十张表其实都已存在且列/索引与代码一致。也就是说，`--autogenerate` 的大差异**不等于**远程 schema 未收敛——其中大量是已废弃 legacy 表与历史 default/nullable 漂移。

## 五、设计决策（3 项 ✅ 新增）

| 决策 | 理由 | 被否决的方案 |
|---|---|---|
| 启动时只做只读迁移状态诊断，不做任何 DDL | 请求路径改 schema 风险极高且难以回滚 | 启动时 `create_all` 兜底 / 自动 upgrade |
| `ensure_agent_tables()` 降级为 no-op 兼容钩子 | 逐步摘除调用方，避免一次性大改 | 直接删除（会同时破坏仍在调用的路径） |
| 远程库显式 `alembic upgrade head`，**不用 `stamp`、不删表、不重置、不重写数据** | `stamp` 会掩盖真实缺表，是"假收敛" | `stamp head` 快速对齐版本号 |
