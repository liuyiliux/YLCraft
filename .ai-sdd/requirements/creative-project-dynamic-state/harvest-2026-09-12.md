## 二、术语与业务对象（5 项 ✅ 新增）

| 术语 | 定义 | 证据 |
|---|---|---|
| **动态状态（dynamic state）** | 随剧情推进而变化的设定值（角色等级、技能、关系、世界倒计时等），与"静态设定"相对 | design.md §5 |

## 三、业务规则与校验逻辑（6 项 ✅ 新增）

| 规则 | 内容 |
|---|---|
| **内容不设 schema，信封必设 schema** | `value_json` 是自由 JSON（标量/列表/对象），但 `project_id`/`scope`/`key`/`op`/`chapter_number`/溯源字段都有约束 |
| **append-only + fingerprint 去重** | `fingerprint = sha256(project:scope:key:op:value:chapter:source)`；已存在则跳过，重批也不会产生重复条目 |
| **折叠语义 `_apply`** | `set` → 覆盖；`add` → 数值 `current + value`、列表 `union`（去重）、否则覆盖；`remove` → 数值 `current - value`、列表 `差集`、标量删除键 |
| **折叠顺序确定** | 按 `(chapter_number, created_at)` 顺序折叠，保证同章多次重批结果稳定 |
| **章节重批用 supersede** | `replace_chapter_entries` 先删该章旧条目再落新条目，复用既有 `_supersede` 语义 |
| **隔离原则** | 静态设定（`Character` 性别/外貌/性格/能力、`CharacterStoryLink` 项目覆盖）**不碰**；锁定事实（`project_bible`/`world_asset` 且 `is_locked`）**不碰**，继续只读注入；动态状态**只**进 `ProjectStateEntry` |

## 六、工程约束与踩坑（4 项 ✅ 新增）

1. **状态更新走"LLM 输出字段"而非工具调用**：`prose_review` 的 JSON 输出新增 `state_changes`（与 `continuity_candidates` 并列），由 `ChapterAftermathPipeline` 的 `state` 阶段确定性读取并落账。**正文 prompt 零改动、新增零工具**——避免在创作主链路里塞工具调用导致延迟与不确定性。
2. **纯服务优先**：`StateLedger` 不依赖 HTTP 与请求上下文，用 fake session 即可单测折叠/去重/回滚。新增任何"计算型"能力时先问能否做成纯服务。
3. **注入必须分层且预算有界**：`dynamic_state` 只全量注入 `world` 与**当前章出场的角色**；未出场角色的长尾交给既有 T5 语义召回，不做全量塞入。
4. **无新 HTTP 路由时不要改 API surface**：本 change 明确"无新路由 → `API_SURFACE.md` 不变"。判断是否需要更新 API surface 的依据是**路由是否变化**，不是功能是否变化。

## 七、设计决策（3 项 ✅ 新增）

| 决策 | 理由 | 被否决的方案 |
|---|---|---|
| 内容自由 + 信封有 schema（借鉴 SillyTavern World Info / AetherState / sneq canonical fact） | 创作状态千变万化，给 value 定 schema 会不断加字段 | 为每类状态建独立表/字段 |
| 用 LLM 输出的 `state_changes` 字段驱动，不新增工具 | 创作主链路零改动、零额外延迟 | 新增"更新状态"工具让模型调用 |
| 动态状态与静态设定、锁定事实严格分层 | 避免模型误改人设定的正典（静态/锁定事实碰不得） | 统一存进角色表 |
