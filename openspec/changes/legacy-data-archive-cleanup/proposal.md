# Proposal: 老数据归档与兼容层清理

## Why

项目已经开始从旧 `assets` 表和零散素材写入，迁移到新的 Asset Hub/素材中枢模型。此前已经把旧 `assets` 数据迁入 Asset Hub，并让素材库优先展示新中枢节点，但代码里仍然存在大量旧 `AssetService` 写入、旧 API 兼容、旧页面入口和临时迁移脚本。

这些老数据和老代码不能一次性删除：当前下载、小说、AI 生图、角色立绘、种子、本地播放、任务记录等功能仍有一部分依赖旧 `/api/v1/assets` 或旧资产模型。需要建立一个明确的归档任务，把“已经可以归档的先归档”，同时保留兼容层直到所有新写入都切到 Asset Hub。

## What Changes

- 建立老数据归档清单，区分 `已迁移可隐藏`、`保留兼容`、`待切换写入`、`最终可删除` 四类。
- 将旧 `assets` 数据视为历史兼容源，默认素材库展示以 Asset Hub 节点为准。
- 继续保留 `/api/v1/assets` 作为兼容门面，但内部逐步切到 Asset Hub 读写。
- 将图片生成、角色立绘、项目分镜/漫画生图、下载导入、种子文件入库等新写入路径统一沉淀到 Asset Hub。
- 对临时迁移脚本、调试日志、重复旧入口进行安全清理。
- 在最终删除旧表/旧模型前，提供可回滚迁移、数据校验和用户确认流程。

## Goals

- 避免素材库出现旧资产和新中枢节点重复卡片。
- 让新生成、新导入、新下载的素材都能进入 Asset Hub，并保留来源、任务、项目、提示词、模型等谱系信息。
- 把旧 `AssetService` 收敛为兼容层或门面，减少后续功能继续写老表。
- 清理已确认不再需要的临时代码、调试日志和旧入口。
- 为远程数据库保留安全边界：先归档、再冻结写入、最后才考虑删除。

## Non-goals

- 不在本任务中直接删除远程数据库的旧 `assets` 表。
- 不一次性重写所有前端素材调用路径。
- 不删除仍被下载、小说、播放器、任务系统依赖的兼容 API。
- 不迁移或删除用户文件本体，只处理数据库记录、索引关系和展示入口。

## Already Done

- 旧 `assets` 表中的 31 条记录已迁移到 Asset Hub。
- 迁移脚本具备 dry-run 和幂等能力。
- `/api/v1/assets` 列表已合并 Asset Hub 节点，并对已迁移旧资产去重。
- `/api/v1/assets/{id}` 和缩略图读取已支持 Asset Hub fallback。
- 大文件旧资产的 `file_size` 已做 int32 兼容保护，真实大小保存在扩展字段。

## Impact

- **后端**：`AssetService`、`AssetHubService`、`/api/v1/assets`、图片生成、下载、种子、小说、创作项目资产链接会逐步改造。
- **前端**：`/assets` 保持主入口，但展示语义逐渐从旧 Asset 变成 Asset Hub-backed asset。
- **数据库**：短期不删旧表；新增归档标记、迁移元数据或兼容映射时必须向后兼容。
- **运维**：所有 destructive cleanup 必须先 dry-run，并在远程库备份后执行。

## Success Criteria

- 素材库不再显示同一文件的旧资产卡片和 Asset Hub 卡片重复项。
- 新生成的图片、角色立绘、项目漫画图、下载文件都能在 Asset Hub 中找到，并带有来源信息。
- `/api/v1/assets` 对旧调用方保持可用，但默认从 Asset Hub 读取。
- 老数据归档脚本可重复运行，输出清晰的 scanned/migrated/skipped/failed 统计。
- 旧表删除被明确推迟到最后阶段，并需要单独确认。
