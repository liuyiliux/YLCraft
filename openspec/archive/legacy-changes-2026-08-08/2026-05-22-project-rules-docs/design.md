## Context

YLCraft 是一个 AI 创作平台，使用 FastAPI (Python) + React (TypeScript) 技术栈。项目已实现模型配置、AI图片生成、B站视频搜索/下载、B站账号登录等核心功能，但缺乏系统化的开发规范文档。

当前项目状态：
- 后端：30+ API 模块、16+ 数据模型、多服务层架构
- 前端：27 个页面组件、Ant Design 5 UI 库
- 数据库：SQLite + SQLModel ORM
- 外部依赖：FFmpeg、yt-dlp、faster-whisper、ComfyUI

## Goals / Non-Goals

**Goals:**
- 创建 6 个结构化的 AI 规则文档，覆盖项目全栈开发规范
- 文档可直接被 AI 助手引用作为上下文约束
- 提供快速参考路径，降低新开发者上手成本
- 建立统一的代码风格和数据模型约定

**Non-Goals:**
- 不修改现有代码或架构
- 不引入新的工具链或构建流程
- 不是 API 参考手册（已有 OpenAPI 文档）
- 不涵盖未实现功能的规划（如 Story Maker、Live2D 等规划中模块仅简要提及）

## Decisions

### 决策 1：采用分层文档结构
**选择**：6 个独立文档按依赖关系组织（概述 → 端点规范 → 代码风格 → 快速参考）
**理由**：概述提供全局上下文，端点规范分别约束前后端，代码风格统一语言级约定，快速参考提供索引，数据库设计规则约束数据层
**替代方案**：单一 monolithic 文档 → 否决：难以维护和定位

### 决策 2：文档存放于 `docs/rules/` 目录
**选择**：`docs/rules/` 与现有 `docs/` 目录保持一致
**理由**：与项目现有文档结构一致，便于版本管理
**替代方案**：`.codebuddy/rules/` 或根目录 `rules/` → 否决：前者过于隐蔽，后者污染根目录

### 决策 3：以「规则」而非「教程」形式编写
**选择**：使用 SHALL/MUST 等规范性语言，面向 AI 约束而非人类学习
**理由**：主要消费者是 AI 助手，需要明确的可执行规则

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|---------|
| 文档与代码不同步 | 在 proposal 中标注「纯文档添加」，后续迭代时同步更新 |
| 规则过于严格限制灵活性 | 使用 SHALL 而非 MUST，允许合理例外 |
| 项目快速演进导致文档过时 | 设计为轻量级文档，更新成本低 |
