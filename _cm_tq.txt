feat(torrent): 种子断点续传（启动恢复 + resume data）—— 回答"种子也支持吗"

## 问题：断点续传只做了解析下载，种子没有

用户问"这个断点续传是只做了解析下载的 还是种子链接下载的也支持"。
实测确认：**两套完全独立的系统**，种子那边**没做**。

| | 解析/视频下载 | 种子下载 |
|---|---|---|
| 文件 | `api/v1/download.py` | `api/v1/torrents.py` |
| 引擎 | httpx / yt-dlp | libtorrent / qBittorrent |
| 断点续传 | ✅ 上一轮做了 | ❌ **这轮补** |

## ⚠️ 一个重要的技术差异（先澄清）

**种子下载的"续传"和 HTTP 不是一回事**：

  · HTTP 断了真的丢，要靠 `Range` 请求续
  · **BT 协议本身就有分片校验** —— 重新 add 同一种子，
    libtorrent 会扫描已有文件、校验分片、**只下缺的部分**

所以种子这边**不缺"续传能力"，缺的是"记住有哪些种子"** ——
进程重启后不知道该重新添加哪些。

## 实测发现的缺口

    ✅ 任务信息**本来就存在数据库**（TorrentDownload 有
       source_uri / save_path / torrent_hash）
    ❌ **没有任何代码在启动时读回来重新添加**
    ❌ libtorrent 的 `save_resume_data` / resume data **完全没配**
    ❌ `close()` 直接 `return None`（退出时进度全丢）

**后果**：重启程序后，之前正在下的种子**全部消失** ——
引擎里没了、数据库记录状态永远停在那一刻，用户只能删了重加。

（实测数据库里有 19 条历史种子的 `source_uri` 都完整，但状态全是 `deleted`。）

## 做了两件事

### 1. 启动恢复（`restore_active_downloads`）

读未完成的记录 → 用 `source_uri` 重新 add →
libtorrent **自动续传**（扫描+校验+只下缺的）。

  · 终态（completed/finished/seeding/deleted）**跳过**
  · **best-effort**：单个失败不影响其它，也不拖垮启动
  · 失败记账（`failed` 列表）让用户知道哪个要手动处理

`main.py` 启动时调用。

### 2. resume data 落盘

存 `<下载目录>/_resume_data/<hash>.resume`，让重启后**跳过重新校验**
（几十 GB 的种子校验要很久）。

  · `pause` / `close` 时**请求**保存
  · `_drain_alerts()` 处理 libtorrent 的**异步** alert 完成写盘
    （`save_resume_data()` 是异步的 —— 不处理 alert 就**永远写不出去**）
  · `list_torrents` 也 drain（前端轮询正好当心跳）
  · ⚠️ `close()` **不销毁 session**（它是类变量单例，
    销毁会让下个请求拿不到 handle）

## ⚠️ 实现的三个坑（都是实测踩到的）

1. **`getattr(rd, key, None) or rd.get(key)` 是错的**
   —— `read_resume_data()` 返回的是 `add_torrent_params` **对象**
   （不是 dict），**没有 `.get`**。`getattr` 返回 None 时会抛
   AttributeError 被 except 吞掉 → **加载永远 False**。
   症状：resume 文件明明写出来了（982 字节），加载却永远失败。

2. **不能 `setattr(params, "resume_data", bytes)`** —— 实测报
   **C++ 签名不匹配**（libtorrent 2.0 的该字段不是裸 bytes）。
   正确做法：`read_resume_data()` 返回的**就是** `add_torrent_params`，
   逐字段搬过去即可。

3. **模块原来没有 `logger`** —— 我写了 `logger.debug(...)` 是
   NameError，且**只在异常路径触发**（平时测不出来）。

## 实测

    [1] 加载已有 resume data → **True**，字段全部搬运到位
        （info_hash / trackers / save_path / flags / storage_mode）
    [2] 不存在的 hash → False（不崩）
    [3] 损坏文件 → False（不崩）
    [4] 完整流程：add → save → **1342 字节** → 再加载 → **True**
    [5] 模拟重启恢复：total=1 restored=1 failed=0，状态正确更新
