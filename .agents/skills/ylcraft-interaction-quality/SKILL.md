# YLCraft 交互质量门禁

## 这个 skill 解决什么问题

**登记齐全 ≠ 功能接通**（`ylcraft-add-platform` 的教训），
在交互层同样成立，而且更隐蔽：

> 后端工具有了、确认卡片也画了，用户就是**用不了** —— 而且**不报错**。

2026-10-14 实测确认的实例：`generate_image_asset` 工具存在、
确认卡片能显示 prompt、文案也说人话，但
**①生图预览只显示字段名 ②点「确认执行」不生效 ③失败时把 SQL 甩给用户**。
用户视角 = "这功能没有"。

本 skill 把「好交互」从形容词变成**可检查的条文**，并附上**有来源的行业依据**。

## 🚨 两条最根本的（比条文更底层）

### 1. 界面不许泄漏内部术语 —— 「引擎术语 / 用户术语」分开维护

OhMyGame 的做法（`docs/playable-nodes`，一手）：

> 「**编辑器给作者看更朴素的词。**代码、schema、工具和其他文档**保留引擎术语**。」

| 引擎术语（内部） | 编辑器术语（给用户） |
| --- | --- |
| Scene | **Node** |
| Exit | **Signal** |
| Template | **Preset** |
| History | 返回栈 |

> **不是翻译一下，是两套术语分别维护，各服务各的人。**

**我们的现状（有实例）**：
- `返回字段：success、normalized_request、visual_plan、`（`summarizeToolResult`）
- `relation: sequence`、`source_node_id`、`canvas_source_node_id`

**这些是"系统在怎么实现"，不是"我要做什么"。**
**暴露出去 = 用户看到的是内部结构 → 这正是"丑 + 不在点"的一个隐藏成因。**

### 2. 风格/场景定义里要写死「负向约束」和「一句文案」

handraw-style 的四字段（编号 / 名 / 文案 / 提示词）：

```
C-01 · 克莱因蓝
      「纯粹之蓝 通向无限」                        ← 文案（帮用户选）
      `主题色：克莱因蓝（Klein Blue）。`           ← 中英双名喂模型
      风格特征末尾：「…**避免统一的可爱微笑**。」   ← 负向约束
```

**「负向约束」是关键**：光说"要什么"会漂移，**必须同时说"不要什么"**。

> 我们的场景色只有 4 个内部 key（`THEME.drama` 等），
> **没有编号、没有文案、没有中英双名、也没有负向约束**。

## 铁律（违反必踩坑）

1. **生成/产出类工具的结果必须渲染成产物**，禁止只给文字摘要或
   `JSON.stringify`。用户看不到图 = 功能不存在。
2. **错误信息必须说人话**，禁止把 SQL / 堆栈 / 内部异常类名甩到界面。
   （`docs/rules/03-前端开发规范.md` 第 202 行早已规定，但**没有检查点就会违反**。）
3. **同一个动作全页面只允许一个按钮**。实测出现过两个「确认执行」
   （顶部横幅一个、执行轨迹里一个），用户不知道点哪个。
4. **待确认/待处理项必须绑定它所属的对话**，不得串台。
5. **一致性由系统注入，不靠用户重复描述**。角色、风格、参考图应从
   角色库/资产中枢**自动带入**每次生成请求。
6. **局部重生成优先**。改一个镜头、一句台词，不该重跑整段。
7. **参数要么真生效，要么别显示**。写了不生效的参数 = 失控感。
8. **内部路由要可见**。用了哪个供应商/模型，界面要说出来。
9. **等待期间必须能并行或批量**。不能让用户被一次生成锁死。
10. **真实素材优先**，禁止用 AI 生成的假界面/假结果充当成品。
    宣传展示类内容里，主角必须是**真实产出**。
11. **诚实说明 AI 的能力边界**，把该由人判断的事交回给人
    （例：AI 听不到声音，选曲必须人试听）。
12. **资产必须获得「稳定角色」**：图片 / 视频 / 主体 / 音频各有明确身份，
    不许混成一团。
13. **`UNKNOWN`、确认不存在、不适用，三者必须区分**，
    不许一律显示成"无"或"--"。
14. **对话负责沟通，界面负责事实** ——
    「Chat tells you what the agent **said**；看板 shows what the production is
    actually **doing**」（OpenMontage 原话）。
    **只显示"agent 说了什么"而不显示"实际做出了什么"，就是"不在点"。**
15. **门禁必须"强制"，不能只是"建议"** ——
    OpenMontage 的 checkpoint writer **会拒绝**没有批准记录的完成态。
    我们的确认按钮"点了不生效"，**连建议都没做到**。
16. **产出后自审，自审失败就不展示** ——
    例：ffprobe 校验 + 抽帧查黑帧 + 音频电平查静音削波；
    **若自审失败，视频不予呈现**。
17. **重大选择要留决策理由**，不只是结果 ——
    记「为什么选它、还考虑过谁、置信度多少」。
18. **源素材先探查再规划**，禁止凭文件名臆测内容。
19. 🔴 **Agent 汇报必须包含四项**：做了什么（可核对的 id/路径）、
    **没做什么**（边界声明）、**自检结果**、**变更规模**。
    只回「已完成」或回一串字段名 = 不合格。
20. 🔴 **随机只用于探索，不用于执行** ——
    形象（脸 / 模特）**只能随机一次，定了就锁**；姿势、服装可以随机；
    **光线和场景从来不随机**（跟项目和地点走）。
    任何「换一个 / 重新抽」按钮都要先问一句：**这个维度随机了会不会毁掉一致性**。
    反例：参考组合页第一版三格都能换，等于每按一次就换个人拍。

## 核心判据：什么该升级成「产物」

Claude Artifacts 的判断标准（一手来源见文末），**直接可用**：

一段内容满足以下任一条，就**不该**被压成一行文字摘要：

- 显著且自包含（**通常超过 15 行 / 是一个独立对象**）
- 用户会想**编辑、迭代或复用**它
- 它**脱离对话上下文仍能独立成立**
- 用户会**回头再看**或用它

> **对照我们的现状**：`frontend/src/pages/agent/index.tsx` 的
> `summarizeToolResult` 把所有对象压成「返回字段：url、local_path…」，
> 恰好**违反了全部四条**。生图结果的 `url` 是典型"用户会回头再看"的产物。

## 已验证的行业做法（带来源）

> 标 `一手` 的是我实际打开页面读到的；标 `二手` 的是他人报告/评测转述。

### A. 产物呈现

| 做法 | 出处 | 对我们的启示 |
| --- | --- | --- |
| 产物**开在对话旁边**的独立窗口，不在对话流里 | Claude Artifacts `一手` | 我们的图/视频不该塞在气泡里 |
| 所有产物**集中在一个 Tab**，任何对话都能找回来 | Claude Artifacts `一手` | 素材库已是这个角色，要打通 |
| **指哪改哪**：选中文字点"Edit with Claude"，不用描述位置 | Claude Artifacts `一手` | 局部重生成的交互范式 |
| 错误旁边直接给 **「Try fixing with Claude」按钮** | Claude Artifacts `一手` | 比"是不是要重试"的文案强 |
| **Node Execution History**：下载/全屏/换回当前输出/收藏/转节点 | Runway `一手` | 结果历史是一等公民，不是日志 |
| 生成即**自动存入 Project**，无需手动管理文件 | LTX Studio `一手` | 我们生成后要自动进素材库 |

### B. 一致性（跨平台最强共识）

| 做法 | 出处 | 原话 |
| --- | --- | --- |
| **Elements**：锁定角色/环境/物件，跨全部生成复用 | LTX Studio `一手` | 「**Instead of describing the same character in every prompt**」 |
| 角色库映射：输入故事→AI 识别角色→映射到角色库 | Dashtoon `一手` | 「our AI identifies the characters… maps each one to a character from our library of consistent characters」 |
| 角色资产：上传照片+声音样本+背景故事 | Showrunner `二手`（品玩实测） | 用户建的角色成为社区公共资产 |
| ❌ 没有一致性机制会怎样 | ComfyUI / V2EX `一手` | 「解决不了，你不能保证模型不出错」 |

### C. 局部重生成

| 做法 | 出处 |
| --- | --- |
| **Retake**：改光线/构图/表情，**不重生成整个镜头** | LTX Studio `一手` |
| 删一行台词→补新台词→重新生成→**自然融入原片** | Showrunner `二手` |
| **Inpainting**，可保留原构图 | Dashtoon `一手` |
| 历史输出**换回为当前输出**继续做，「without starting over」 | Runway `一手` |

### D. 过程可见与可控

| 做法 | 出处 |
| --- | --- |
| **双面板**：左侧对话、右侧"AI 的电脑"实时操作窗口 | Manus `二手`（他人调研报告） |

### E. 等待与并行

| 事实 | 出处 |
| --- | --- |
| 「你没法总去做副任务，因为**那些工作依赖 Gen-AI 的确切结果**」 | Reddit r/VEO3 `一手` |

### J. 创作框的行业基线（一手截图 · **交互设计的最佳教材**）

> 2026-10-15 实测即梦 / 可灵 / 海螺 / Midjourney / RunningHub，截图逐屏看过。

#### 🔴 最强的一条：`@` 引用素材已是行业基线

| 平台 | 交互 | 原文 |
| --- | --- | --- |
| **即梦** | `@` 添加主体 | 「支持 **/** 使用技能，**@** 添加主体，和 Agent 一起创作」 |
| **可灵** | `@` 调用参考素材 | 「描述画面，也可上传图片、视频、**主体或音色**…**支持使用 @ 快速调用参考素材**」 |
| **海螺** | 上传位带计数 | **`参考 (0/12)`** |
| **RunningHub** | 显式上传 | 「当前模型最多支持上传 **10 张参考图**」 |

**「在创作输入框里直接引用素材」是基线，不是加分项。**
（对照：我们 `ChatRequest` **连字段都没有**。）

#### 即梦的创作框（左侧仅 6 项导航，主区就一个框）

**它的输入框 placeholder 原文**：
> 「输入想法、剧本或上传参考，支持 **/** 使用技能，**@** 添加主体，和 Agent 一起创作」

**一句话教会全部用法，不需要教程。** 直接可抄的四点：

| 做法 | 细节 |
| --- | --- |
| **`/` 技能 + `@` 资产 双符号** | 符号**同时以可点按钮**摆在输入框上（`技能`、`@`）——**符号 + 按钮双通道**，不会打字的也能点 |
| **技能原地弹出** | 点「技能」在**输入框下方**弹出列表（2026-11-01 实测更正：原文写"上方"是错的，见 `docs/research/jimeng/02_skills.png`），**不跳页不弹模态**；每个技能带**一句话说明**（如「拆解参考视频的镜头语言、光影色调与声音节奏」）+ **`官方` 标记** + 顶部搜索框 |
| **技能名是任务名** | 「视频反解」「创作分镜」「剧情短片」「电商套图」「海报设计」——**不是功能名** |
| **chip 带 `New`/`Hot`** | 用徽标引导发现新能力，不靠用户自己翻 |

**「主体」是一级菜单**（与 创作/探索/资产 并列），独立管理页；
`@ 添加主体` 就是在对话里**引用这些主体**。
→ **这正是"对话里引用素材/资产"的行业做法。**

**「Agent 模式」是输入框里的一个可切换档位，不是一个独立页面。**

**作品展示带「查看创作过程」按钮** —— 点开能看到作品是怎么做出来的
（同 OpenMontage 的 `▶ REPLAY RUN`）。

#### 可灵（「计费写在花钱的地方」）

- 输入框说清**能传什么**：图片、视频、**主体、音色**
- **「计费规则」就在输入框里**
- 参数收成一行 chip：`视频生成▾ Kling4.0▾ 全能参考▾` + `720p·10s·16:9·1▾`
- **MCP / API 在正门导航**（开发者是一等用户）

#### 海螺（计数与成本透明）

- 🔴 **placeholder 给完整例句（含运镜）**：「例如，"一个孩子在公园里放风筝，金色阳光，**镜头上移**。"」
- 🔴 **参考图计数**：**`参考 (0/12)`**
- 🔴 **消耗写在按钮旁**：创作按钮右侧显示 **`60`**（积分）

#### Midjourney（导航全是动词）

- 导航：**Explore / Create / Edit / Organize** + **AESTHETICS: Personalize / Moodboards**
- **审美被单列成一级分组** —— `Moodboards` = 把审美偏好做成可复用资产
  （同我们的**写作风格档案**思路）
- **顶部只有一个输入框**，无参数面板；**默认页是作品流**

#### Google Flow TV（作品可见提示词 + 一键复用）

- **`Hide Prompt` 开关** —— 打开就显示这条视频的**原始提示词全文**
- 🔴 **`Reuse Prompt`** —— **直接拿这条提示词去创作**
- 标注生成方式：`Text to Video` + `Veo 3`
- 形态是**有频道的作品台**（CHANNEL），不是普通画廊
- **闭环：看到好作品 → 看提示词 → 一键复用**
  （对照：我们有提示词参考库，**但没这个闭环**）

#### ⚠️ 两个已查明的事实

- **Sora 网页版已下线**（「Sora is no longer available」），不要再把它当活跃对标。
- **Google Flow 主体按"账号地区"拒绝服务**，不是 IP 问题
  （实测 IP 已是美国仍被拒）。

#### 通用规律：参数收成一行 chip

`可灵 720p·10s·16:9·1` / `海螺 2K 5s 21:9` / `RunningHub 1:1 / 2k / JPEG`
—— **参数永远是一行，永远不是面板。**

### G. 资产固化与自动引用（剪映 Hub，2026-10-15 实测文，**商单但流程描述可用**）

剪映 Hub 的工作流是**我们建议方向的已上线验证**：

| 剪映 Hub 的做法 | 用户实际动作 |
| --- | --- |
| **保存到资产主体** | 批量生成人物/道具/场景后，一键存入，「这样整体的**人物、道具就固定好了**」 |
| **Agent 引用资产** | 点「生成分镜提示词」，Agent「**按照分镜，引用我们准备好的资产**，整理出所有提示词」 |
| **批量生成** | 人物/道具/场景**一键批量生成**；「批量生成视频」 |
| **画布按分镜衔接** | 「成片预览」时「按分镜做好视频之间的基础衔接」 |
| **免导入导出的精剪** | 「更多剪辑」直接进多轨道时间线，**完全不用导入导出** |
| **时间线内局部重生成** | 镜头时长不够，「**让 AI 把镜头延长**一点」 |

> 🔴 **这意味着"资产自动注入 + 批量生成"不是未来方向，是已上线的竞品功能。**
> 我们的差异化只在它没有的地方：**世界地图 / 剧情时间线 / 小说→世界提取**。

### I. 生产治理（OpenMontage，一手 README · **最完整的参考**）

`github.com/calesthio/OpenMontage` —— 开源 agentic 视频生产系统，
**AGPL-3.0，可学思路不可抄代码**。它的治理机制最值得抄：

| 机制 | 原文要点 | 对我们的启示 |
| --- | --- | --- |
| **对话 vs 实况分离** | 「Chat tells you what the agent **said**. Backlot shows you what the production is actually **doing**」 | 我们只有前者 |
| **批准是强制的** | 「Human approval gates are **enforced, not suggested**」；checkpoint writer **拒绝**无批准记录的完成态 | 我们的门禁是软的 |
| **渲染前校验** | 违背 delivery promise（如宣称 motion-led 却 80% 静图）→ **阻止渲染**，「catches broken plans before wasting GPU time」 | 可在提交生成前校验 |
| **产出后自审** | ffprobe + **抽 4 帧查黑帧/坏叠加** + 音频静音削波分析；**自审失败则不予展示** | 值得引进 |
| **Slideshow 风险评分** | 6 维（重复度/装饰性视觉/弱运动/镜头意图/排版依赖/无依据的电影感宣称） | 防"动画版 PPT" |
| **决策审计链** | 每个选择记录「**alternatives considered, confidence scores, and reasoning**」 | 我们有日志无理由 |
| **预算治理** | Estimate → Reserve → Reconcile；模式 observe/warn/cap | 我们只有 CostMeter |
| **供应商 7 维打分** | task fit 30% / quality 20% / control 15% / reliability 15% / cost 10% / latency 5% / continuity 5% | 选路更可解释 |
| **源素材先探查** | 「**No hallucinating content from filenames**」 | |
| **"不许自己发挥流程"** | 「**Do not improvise the production workflow**」；工作流写在 pipeline manifest 里 | 与我们 skill 思路一致 |

**它的三层知识架构（可直接抄结构）**：
- Layer 1 `tools/` + `pipeline_defs/` = **"What exists"**（能力清单）
- Layer 2 `skills/` = **"How to use it"**（本项目约定与质量标准）
- Layer 3 `.agents/skills/` = **"How it works"**（外部技术知识包）
- 每个工具**声明自己依赖哪些 Layer 3 技能**

> **注意它用的就是 `.agents/skills/` 目录约定 —— 和我们仓库一致。**

**看板的实现原则**：「the board **derives everything from the project files the
pipeline already writes**」—— **不要求流水线额外上报**，从既有产物推导。
（我们用「从后端 assets/logs 独立验证」是同一思路。）

### H. 提示词工作流分类（video-research-lab，一手）

**按"用户想完成的任务"分类，不按模型/供应商分类** —— 10 个工作流：
视频反推 / 首帧生成视频 / 替换主体 / 首尾帧生成视频 / 视频续写 /
替换场景 / 风格转换 / 动作复刻 / 运镜复刻 / **视频提示词检查**。

值得直接抄的两条原则：
- **Reference clarity** —— 「图片、视频、主体、音频资产获得**稳定的角色**，

- **Honest verification** —— 「`UNKNOWN`、确认不存在、不适用，**三者保持区分**」

该仓库的诚实值得学：明写「目前 **0 个已发布案例**」「不要把仓库里存在某个模板

## 本 skill 自己该怎么长（元规则）

来自 `liyupi/ai-promo-video-maker` 的一手经验（2026-10-15 实抓）：

> 「这个项目里**没有什么复杂的代码，核心是一份写给 AI 看的「工作规范」**……
> **AI 读完规范，就知道该从哪一步开始、每一步要做到什么标准。**」

三条可直接照搬的做法：

1. **每条规则都要来自一次真实翻车。**
   那个项目「规范里已经攒了 **80 多条踩坑记录**，像截图被横向压扁、开场铺垫太慢、
   配乐和画面不搭、旁白把品牌名念错，**每一条都来自我真实收到过的修改意见**」。
   → **本文件每加一条铁律，都必须能指向一个具体案例。**
2. **写清"每一步的验收标准"**，而不只是"要注意什么"。
3. **诚实标注能力边界** —— 那个项目明写「**AI 压根儿听不到声音**，
   曲子搭不搭还得你的耳朵来感受」，所以把选曲交给用户。

### 🚨 第 6 条：把「验证状态」分级（来自 handraw，这是第 4/5 条的完整版）

他们的原文（一手）：

> 「**软件或网页未能实际审看时标记未验证，不能只凭结构断言画面正确。**」
> 「**草稿结构通过不能称为剪映实际导出通过。**」
> 「写入结构通过**不等于**软件最终渲染通过。」
> 「应用打开、实际导出、音频与字体检查、用户审美接受**分别登记**。」

**→ 他们已经细到 4-5 层，我们目前只有 2 层，粒度不够。**

**我们应采用的五级标注（写文档/汇报时必须用其中之一）：**

| 级别 | 含义 | 判定 |
| --- | --- | --- |
| **L0 计划中** | 还没写 | 只有方案 |
| **L1 代码就位** | 代码写完了，**没跑过** | 🚨 **必须明说"未验证"** |
| **L2 结构通过** | 数据/结构对，但没实跑 | 🚨 不能说"能用" |
| **L3 实际跑通** | **真实执行过一次并看到结果** | 只有到这级才能说"能用" |
| **L4 用户验收** | 用户看过并接受 | 汇报时要单独说 |

> **汇报纪律**：
> - L1/L2 一律写「**未验证**」，不许说"已完成"
> - **L3 和 L4 要分开报** —— 「跑通了」≠「用户认可」
> - 改完代码只到 L1 时，**必须在 final 里写清"未验证"**

### 🚨 第 7 条：门禁要写「不能做什么」

handraw 的写法（原文）：

> 「"帮我做视频"**仅授权方案阶段**。确认前可盘点已有素材；
> **不得生成画面、配音、动画代码或预演**。」
>
> 「真实录屏、事实数据、用户原件缺失时……**不能用生成内容冒充**。」
> 「**不循环、冻结或变速凑时长**。」
> 「指定服务**不可静默替换**。」
> 「**新增名称不等于新增能力**。」

**→ 正面表述（"应该注意 X"）远不如禁止式（"不得 X"）有约束力。**
本 skill 的条文若改写，一律用**禁止式**。

### 🚨 第 8 条：降级方案必须用户同意，且方案改版旧授权失效

> 「取得**用户真实同意**；`render_backend=web` 或 `auto` **都不等于用户授权**；
> **方案改版旧授权失效**。」
> 「未经同意时，调整为可原生效果或提交浏览器路线方案，**不静默改变视觉**。」

**→ 我们的"自动兜底/自动降级"必须停下来问，且改方案后要重新问。**

### 🚨 第 4 条（来自 BeefTV 作者，最该学）

> 「**README 里写的让 Agent 主导创作流程，那是以后的目标，现在还做不到。**」
> 「核心维护的就两个人……**接口和数据结构说不定哪天就变了**。」

**→ 文档承诺 ≠ 现在能做，必须明说。**

> **这条对我们直接有用**：我们也有"文档写了、实际没实现"的情况
> （如 ComfyUI 工作流至今只是占位）。
> **凡没真跑通的，一律标注状态**，别让下一个人以为能用。

### 🚨 第 5 条：同一纪律的另一个说法（Infinite Canvas 的安装提示词）

> 「**不要把「安装成功」当成「生图和视频生成测试通过」。
> 没有配置模型 API 时，明确说明尚未验证生成能力。**」

**→ 交付汇报要区分"装上了"和"能用了"。**

**两个必须分开报的状态**：
1. **装上了**（安装/部署完成）
2. **验证过了**（真实跑通一次）

> **我们也要守这条** —— 改动写完，若只做到"代码就位"，
> **必须明说"未验证"**，不能让人以为功能已通。

## 🔴 实测标杆：Agent 应该怎么汇报（OhMyGame，2026-10-16 亲自跑通）

> 我给 OhMyGame 装了模型、让它真的在画布上建节点，**亲眼看到它的报告**。

### 它做完之后说了什么（原文要点）

> **工作了 23 秒**
>
> 已在画布上新建文本节点「一致性提示词说明」
> （`canvas/boards/9457bb79-….json`，节点 id `b1f7c2a4-…`），
> **原有 image 节点保留未动**。
>
> **已运行 `canvas_check`，校验通过。未做任何图片生成。**
>

### 五个必须抄的习惯

| # | 习惯 | 为什么 |
| --- | --- | --- |
| 1 | **带文件路径 + 节点 id** | 用户能自己去核对，不必只信 Agent |
| 2 | **主动交代"原有的 X 保留未动"** | 消除"它是不是乱删东西"的疑虑 |
| 3 | 🔴 **主动声明"未做任何图片生成"** | **明确说自己没做什么** |
| 4 | 🔴 **跑校验工具并报"通过"** | 自检有工具、有据可查 |
| 5 | **`更改了 N 个文件 +X -Y`** | 像 diff，可展开 |

### 🚨 对照我们 —— 方向完全相反

| | OhMyGame | 我们的 Agent（实测 2026-10-14） |
| --- | --- | --- |
| 结果呈现 | 图/文本节点直接落在画布上 | `返回字段：success、normalized_request、visual_plan、` |
| 边界声明 | 「**未做任何图片生成**」 | 无 |
| 自检 | 跑 `canvas_check` 并报结果 | 无 |
| 变更说明 | 文件路径 + 节点 id + diff | 无 |
| 耗时 | 「工作了 23 秒」 | 无 |

> **→ 铁律（新增）**：
> **Agent 完成操作后，汇报必须包含四项**：
> ① **做了什么**（可核对的文件/节点 id）② **没做什么**（明确的边界声明）
> ③ **自检结果**（跑了什么检查、是否通过）④ **变更规模**（改了几个文件/节点）
>
> **只回一句「已完成」或回一串字段名 = 不合格。**

## 🚨 调研方法论：三条踩过的坑（2026-10-16 补充）

### 1. 只拿到文章链接时，必须去核实真实来源

我曾基于一篇公众号文章写下「BeefTV 是桌面软件、需下载 200MB 安装包、Wails 打包」——
**核实后全是错的**：真实仓库 `glanderness/BeefTV`（★1444，MIT）
是 **Docker 部署的 Go Web 服务**（有 `Dockerfile` / `nginx.conf` / `render.yaml`）。

> **→ 规则**：只给文章/二手来源时，**必须用 GitHub API 核实仓库存在、许可、真实形态**，
> 再写进任何文档。

### 2. 🔴 许可永远要单独核实（最关键）

**`tigerowo/infinite-canvas` 是 AGPL-3.0，那篇文章一个字都没提。**

| 项目 | 许可 | 能否并入闭源 YLCraft |
| --- | --- | --- |
| OhMyGame | Apache 2.0 | ✅ 可以 |
| BeefTV | MIT | ✅ 可以 |
| **Infinite Canvas** | 🔴 **AGPL-3.0** | ❌ **可能要求整体开源，需法务判断** |

> **→ 规则**：任何打算「参考/集成/抄」的开源项目，
> **第一件事是查 LICENSE**。AGPL / SSPL / Commons Clause 一律先过法务。

### 3. 「看过文档」≠「看过界面」，必须分级标注

我一度把「读了 OhMyGame 的 `authoring.md`」写成「一手」，但那只是**一手文档**。

> **→ 规则**：文档里描述交互设计时，必须标注证据等级：
> - **直接证据** = 我截图看到了界面
> - **转述证据** = 只有官方文档/文章描述
>
> **文档会美化自己的设计**（就像 ComfyUI 的官方 README 不会写"用户嫌我难用"）。
> 最低成本的一步：**选中节点时高亮上下游。**

### 附 1：把依赖关系画出来（BeefTV 的连线）

> 「先生成一张人物设定图，后面三个分镜都拿它当参考，就连三根线过去。
> **以后想改人物形象，源头那张图换掉，顺着线就知道哪些东西受影响**。」

**→ 我们已有依赖数据（`world_entity_relations` 等），但没有画给用户看。**
「资产注入」不只要注入，还要**让用户看见影响面**。

### 附 2：「修复质量」要独立成类（FreeLipSync 教程分类）

它的教程里有一条叫「**修复口型同步质量**」——
「重新生成前先排查时间和源图片问题」。

**→ 承认会失败，并给出排查顺序。**
我们实测的「点确认不生效 / 错误甩 SQL」正是缺这一层。

## 使用方式

- **改前端/Agent 前**：读「铁律」+「交付前检查清单」
- **不确定某个结果该不该渲染**：读「核心判据」
- **要论证某个改动方向**：查「已验证的行业做法」，**引用时带上来源与一手/二手标注**
- **发现新的反模式**：补进本文件 + `docs/research/`，别只写在聊天里
