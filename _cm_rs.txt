## 一、单文件跨进程续传

### ⚠️ 先修一个**真 bug**（实测确认）

`outtmpl` 原来用 `hash(effective_url)` 做文件标识，而 Python 对 str 的
`hash()` **带随机盐**（`PYTHONHASHSEED`）——**每个进程都不同**：

    $ python -c "print(hash(url))"   → 1561049425
    $ python -c "print(hash(url))"   → 900355450   # 同一个 URL！

后果：**中断后重启 → 文件名变了 → yt-dlp 找不到 `.part` → 从头下**
（这正是断点续传要解决的问题本身），且同一 URL 会留下
一堆不同 hash 的半截文件。

改用 **md5**（确定性），并加测试**真的开两个子进程**对比。

### 实现

  · `<下载目录>/.partial/` 存半成品（不混进成品区）
  · `resume_state.json` 任务落盘（跨进程可读）
  · 下载成功 → 移出 `.partial/` + 注销记录；失败 → **保留**（才能续传）
  · `GET  /download/resumable`     列出可续传任务
  · `POST /download/resume/{id}`   续传（没有数据时**如实报错**）

### 平台下载器（B站/抖音/X 走这条路，才是主力）

原来 `_download_file_simple` 和 `BilibiliDownloader._download_file`
是**两份几乎一样的循环**，都 `open(path, "wb")` —— 无续传、重试从头来。
抽出 `_stream_to_file` 共用，加：

  · `.part` 临时文件（"存在" ≠ "完整"）
  · `Range: bytes=<已下载>-`
  · **206 才追加**（`"ab"`）；返回 **200** 说明 CDN 忽略 Range → 从头写
    （否则得到"半截旧数据 + 完整新数据"的坏文件）
  · `os.replace` 原子改名
  · ⚠️ **`follow_redirects=True`** —— 实测漏开时会把 302 重定向页面
    （90 字节 HTML）当文件下下来

### 实测（真中断）

    下载 28MB 文件，3 秒后取消
      → .part 保留 24.00 MB
    重新下载 → 耗时 **0.93 秒**，最终 28.33 MB ✅

（28MB 从头下要好几秒；0.93 秒只补了剩下 4MB —— 真的从断点续传。）

## 二、批量任务队列（落盘）

新增 `download_batch.py`（状态存储）+ `download_batch_routes.py`（接口）：

    POST   /download/batches                  提交一批（立刻开始跑）
    GET    /download/batches                  列进度（含 resumable 标记）
    GET    /download/batches/{id}             单批次详情
    POST   /download/batches/{id}/resume      **只续跑没成功的**
    DELETE /download/batches/{id}             删记录（默认**保留文件**）

状态写 `batches.json`，重启不丢。

### ⚠️ 三个实测踩到的坑（都修了）

1. **`list_batches` 无条件重置 running** —— 本意修"重启残留"，
   但**无法区分**"上次进程崩了"和"当前正在跑"。而前端要**轮询**
   这个接口 → 真实的 running 被每次轮询打回 pending →
   **进度永远 0%**。修法：记 `_PROCESS_START`，只重置
   `running_since < 进程启动时间` 的。
2. **`BackgroundTasks` 不调度** —— 它的生命周期绑在**那一个请求**上，
   对跑几小时的批次不合适（任务没被调度）。改用 `asyncio.create_task`
   + **模块级 set 保留强引用**（否则 task 被 GC，任务莫名消失）。
3. **不能直接调 `create_download_task`** —— 它是 FastAPI 路由函数，
   参数含 `principal` 依赖注入，直接 await 签名不匹配、异常被吞，
   表现为"批次一直 0%"。改为直接构造 `DownloadTask` + 调
   `_run_download_task`。

### 实测（真中断 + 续跑）

    提交 5 个 → 强杀（此时 1 done / 1 running / 3 pending）
    重启后： progress=20% done=1/5 **resumable=True**   ← 进度保留
    续跑：   "已续跑 4 个未完成条目（已完成的会跳过）"
    t=6s  →  done=2/5    ← 第 2 个完成（**不是从第 1 个重来**）
    t=15s →  done=3/5

## 测试（只跑相关文件）
