## 1. 为什么要重做

看完用户截的三张图，问题很清楚：

### 现状三个问题

| 问题 | 证据 |
|---|---|
| **确认不生效** | 用户要手动打一句「确认执行上一条待确认工具：generate_image_asset」才能过 |
| **结果给人看的是 JSON** | 回复里是 `{"success": true, "url": "/api/v1/assets/download?path=backend%2Fapp%2Fstorage%2Fimages%2F20261015_012333_%E4%B8%80...}` |
| **Skill 乱匹配** | 用户只要生成图，命中 8 个 Skill，包括「章节钩子节奏」「BGM 工作流」 |

### 判断：**不是审美问题，是信息没分层**

现在的 Agent 页等同于**把 console.log 当界面用**：
- 所有内容同一个字号
- 步骤、结果、错误混在一段流里
- 原始数据直接抛给用户

## 2. 原型做对了什么

### ① 三栏结构

```
┌──────┬────────────────────────────┬──────────┐
│ 会话  │  主对话（抄 Codex/DSH Web）   │ 智能体    │
│ 列表  │                            │ 面板      │
│      │                            │（抄画布）  │
└──────┴────────────────────────────┴──────────┘
```

**用户明确指定**：
- **主对话**抄 Codex / DSH Web
- **右栏**抄画布原型里的智能体面板

### ② 主对话的核心改动

| 要素 | 之前 | 现在 |
|---|---|---|
| 结构 | 一整段流 | **用户气泡右 / AI 左**，分段清晰 |
| 过程 | 全摊开 | **折叠成一行**：「执行过程 · 9 步 · completed」，点开看细节 |
| 结果 | JSON 字符串 | **直接给图** + 底部操作条（下载/存素材/拿去编辑） |
| 元信息 | 混在正文 | 顶栏右侧：`9 步 · 2 工具 · 107,082 tok` |

### ③ ⭐ 确认卡重做（最关键）

**现在的样子**：

```
┌─────────────────────────────────────────┐
│ ⚡ 这一步要花钱，先确认                     │
│ 要调用 generate_image_asset 重新生成一张横图。│
│ 这是一次真实的生成，会消耗额度。              │
│                                          │
│ ┌───────────┬───────────┬───────────┐   │
│ │ 消耗额度   │ 预计耗时   │ 生成数量   │   │
│ │  ⚡ 14     │  ~18 秒   │   1 张    │   │
│ └───────────┴───────────┴───────────┘   │
│                                          │
│ 这次会这么生成                            │
│ [构图 横3:2] [模型 GPT Image 2]           │
│ [风格 延续上一张] [尺寸 3072×2048]         │
│                                          │
│ [确认生成 ⚡14] [取消]        Enter确认 Esc取消│
└─────────────────────────────────────────┘
```

**四个改进**：
1. **钱写在按钮上**（「确认生成 ⚡14」）—— 点之前就知道花多少
2. **三个关键数字并排**（额度/耗时/数量）—— 不用读文字
3. **参数预览**—— 知道这次会生成成什么样
4. **快捷键提示**—— Enter 确认、Esc 取消

### ④ 确认过的痕迹

```
✓ 你已在 17:23 确认过这次生成 —— 不再重复询问
```

**不能第二次问同一个问题。** 这是「确认总不生效」的直接对治。

### ⑤ 右栏做「动作管家」，不做第二个聊天

右栏的定位不是「再聊一遍」，而是：

| 在主对话 | 在右栏 |
|---|---|
| 说要做什么 | 问「这一步花了多少」 |
| 看结果 | 看用量明细 |
| 长内容 | 紧凑卡片 |

右栏还主动提醒：「上一张图你还没存素材库，要我现在存吗？」

## 3. 和原版对比

| 维度 | 原版 | 原型 |
|---|---|---|
| 字号层级 | 1 层 | **4 层**（标题 17/正文 13.5/说明 12/元信息 10.5）|
| 过程展示 | 全摊开 | **折叠，一行摘要** |
| 结果展示 | 原始 JSON | **图 + 操作条** |
| 确认 | 需手动打字 | **卡片 + 按钮 + 快捷键** |
| 花费 | 底部小字 | **写在按钮上** |
| Skill 揭示 | 8 个混在一起 | 只在过程里提「命中 2 个」 |

## 4. ⚠️ 原型没解决的问题（诚实列出）

| # | 问题 | 为什么没做 |
|---|---|---|
| 1 | **Skill 误匹配** | 这是后端 `runtime/skills.py` 的逻辑问题，原型改不了 |
| 2 | **确认不生效的真 bug** | 需要在真前端定位，原型只能展示「应该是什么样」 |
| 3 | 图是占位 | 原型没有真图 |
| 4 | 多轮长对话的滚动性能 | 真实现才需要 |

**原型的作用是「把应该长什么样定下来」，不是修 bug。**

## 6. 一个观察：这也回答了「要不要换 DSH」

用户觉得**丑**。但 DSH 的 Web GUI 也是通用聊天界面，
**换成 DSH 内核，界面一点都不会变好看**。

**丑是前端问题，换内核解决不了。**

是资产，不该因为前端丑就丢掉。**
