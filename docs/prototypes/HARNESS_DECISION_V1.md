人会对着文字同意一个看起来合理的方案，然后做下去才发现不对。

## 1. 四个方案的骨架对比

| | A 只当工具 | B 换持久化后端 | C Fork 改内核 | D 双轨并行 |
|---|---|---|---|---|
| **DSH 角色** | 开发辅助 | **业务内核** | **深度定制内核** | 部分内核 |
| **改 DSH 吗** | 不改 | 写插件，不改 lib | **改 lib** | 部分改 |
| **我们自己 harness** | 保留 | **替换** | 替换 | 双份维护 |
| **多租户** | 无关 | 建在 session 层 | 建在内核 | 建在 session 层 |
| **上游升级** | 无影响 | 可跟随 | **分叉，自己合** | 难跟随 |
| **工作量** | 小 | **中** | 大 | **最大** |

## 2. ⭐ 关键发现：B 方案的真实依据

我之前说「强多租户和 DSH 矛盾」，**这个判断在查到源码后需要修正**。

### 证据一：持久化是设计上的接缝

`dsh-session/lib/index.js` 原文注释：

> **「Persistence is a plugin concern (subscribe to `session/event`, drain on `session/flush`).」**

`dsh-session-persistence/README.md` 原文：

> 「The seam ships the JSONL backend... **A third-party backend may implement the service directly**」

**翻译**：持久化本来就是一个插件接缝，官方明说第三方可以实现自己的后端。

### 证据二：五个方法，接口很小

```
ctx.sessionPersistence.create(header)     → 建会话，拿写权
ctx.sessionPersistence.open(id, 'write')  → 打开已有会话
（还有 read / append / close，共 5 个）
```

**只要这五个方法能用 Postgres 实现，B 就成立。**

### 证据三：单写者锁这个约束，Postgres 天然支持

原文要求的保证：

> 「only one writer per session is allowed within a backend instance」
> 「readers never receive torn tails」

**这正是 Postgres 擅长的**（行锁 / advisory lock / 事务）。
**比文件系统更容易做对。**

## 3. ⚠️ 但 B 有三个未验证的前提

原型阶段必须标出来，不能假装它们成立：

| # | 前提 | 怎么验证 | 现在状态 |
|---|---|---|---|
| **1** | 五个方法的语义能用 Postgres 完整实现 | 逐条对照 README 的 backend contract | **未验证** |
| **2** | 换后端之后，agent loop 不需改 | 读 `dsh-agent-loop` 是否只依赖 `ctx.sessionPersistence` | **未验证** |
| **3** | 多租户可以只加在 persistence 层 | 读 `dsh-api-remote-access` 的 principal 模型能否扩展 | **未验证** |

**这三条只要有一条不成立，B 就要退回 A 或升到 C。**

## 4. C 方案（Fork）的真实成本

MIT 允许改，但改动之后的关系变了：

```
原 DSH ──→ 持续更新（rc → 正式版）
   │
   └─ fork ──→ 你改的内核 ──→ 你的产品
                   ↑
              上游每次更新都要手动合
```

**成本不在「能不能改」，在「改完之后怎么办」：**

| 改动位置 | 升级成本 |
|---|---|
| 只加插件 | 几乎为零（跟着 npm 升）|
| 换 persistence 后端 | 低（接口稳定）|
| 改 agent-loop | **高**（核心逻辑，上游常改）|
| 改身份/权限模型 | **高**（和上游冲突概率大）|

**结论：C 只有在 B 验证失败、且非改不可时才走。**

---

## 5. D 方案（双轨）的问题

看起来最稳，实际上最贵：

- 两套 harness 同时存在
- 两套都要跟业务变更
- 员工 / AI 要知道「这个功能该放哪边」
- **决策成本每天产生一次**

**只在「老系统不能停、新系统要试」时用。我们没这个约束。**

---

## 6. 我的推荐路径（可被反驳）

```
① 先验证 B 的三个前提（读文档 + 写最小 Postgres 后端，不接业务）
        │
        ├─ 三条全过 → 走 B
        │
        └─ 有任一条不过 →
               ├─ 是 persistence 层的问题 → 退回 A（不换内核）
               └─ 是 loop/身份层的问题 → 考虑 C（fork 改）
```

**为什么不是直接选 B**：因为 B 依赖三个未验证的前提，直接做等于赌。

**为什么不是选 C**：因为 C 的成本在「以后」，而 B 可能一开始就够。
