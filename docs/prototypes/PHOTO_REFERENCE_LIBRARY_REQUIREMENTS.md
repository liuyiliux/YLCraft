# 摄影参考库 · 需求规格（草案 v1，待确认）

> 2026-10-21
> 用户三条原始需求：
> 1. 拍照姿势需要保存，支持批量上传，上传时可打标签和修改标签
> 2. 这属于工具类还是什么类
> 3. 素材库播放器 / 小红书等详情播放器需要能点截图当前帧，保存到审美学习或姿势学习参考里
>
> 用户补充：「我是想的，提供入口，然后你或者其他 agent 帮我上传」

# 一、分类定位（回答需求 2）

**它不是「工具类」。**

| 分类 | 是什么 | 典型产品 | 我们的 |
|---|---|---|---|
| 工具类 | 有输入→输出的一次性运算 | 修图、生成、转码 | 已有（本地调整、超分…） |
| **资产类（DAM）** | **存 → 找 → 用**，长期积累 | Eagle、Lightroom Catalog | **本次要做的** |
| 流程类 | 推进一个有时限的任务 | 项目管理、CRM | 摄影策划台（规划用） |

**结论：属于「资产类（DAM）」，要配一个 L1 通用采集能力。**

```
L1 基础能力   ── 截帧 capture（任何播放器可挂）
L2 页面组合   ── 参考库 reference（资产页的一种）+ 摄影策划台 photo-plan
L3 画布       ── 不参与
```

# 三、需求清单（A→D）

## A. Agent 入库工具 `import_assets`（用户最想要）

**为什么这是第一优先**：用户一次要传 100–500 张，
UI 上传的工作量是「一张张确认标签」，而 agent 上传是「说一句话，批量做完」。

### 工具签名（草案）

```python
@register_tool(
    name="import_assets",
    description="把一批本地文件/图片导入素材库，可批量打标签。返回入库报告。",
    parameters={
        "paths": ["D:/ref/coser/*.jpg", ...],   # 支持 glob 或目录
        "tags": {                                 # 按维度分组
            "题材": ["coser"],
            "人数": ["单人"],
            "感觉": ["清纯"],
            "角色作品": ["原神-雷电将军"],
        },
        "collection": "姿势库",                   # 可选：归入某个收藏集
        "source_url": "https://...",             # 可选：来源
        "dry_run": True,                          # 默认 True！先出报告不写库
    },
)
```

### 两阶段：先报告，再入库（用户明确要求）

```
阶段 1  dry_run=True（默认）
        → 读文件 → 读图内容 → 推测标签
        → 返回报告：
          「共 512 张；识别出 12 个角色、4 种风格；
            其中 8 组（24 张）高度相似，疑似重复；
            37 张无法判断题材（需人工）；
            预计入库 512 张，占用 xx MB」

阶段 2  用户确认 → dry_run=False
        → 真正入库 → 返回明细
```

**这个「先报告」是用户明确选的**，不是我自己定的。

### 需要配套的

- 工具实现要复用现有 `POST /upload` 的入库逻辑（不重写）
- 标签写入走现有 `AssetTagLink`，`source="ai"`、`confidence=<模型给的值>`
- 用户手动改过的标签，`source` 改为 `manual`，**以后 AI 不再覆盖**

## B. 批量上传（UI）

- 一次 100–500 张（用户选的档位）
- **队列 + 并发 3-4 + 进度 + 失败重试**
- **先勾一批标签再整批套用**，再单独调个别错的
- 去重：dHash 指纹，相似的在入库前标出来

## C. L1 通用截帧能力

用户选的是「**以后所有播放器都要有**」→ 必须做成通用能力，不是每个播放器各写一遍。

```ts
// 新建 hooks/useFrameCapture.ts
const { capture } = useFrameCapture(videoRef)
capture({ target: 'pose' })   // 返回 Blob + 元数据
```

### ⚠️ 必须提前解决的技术坑

平台详情视频走 `/api/v1/proxy/video` 代理。
**如果直连 CDN，canvas 会被污染，`toBlob` 抛 `SecurityError`。**
→ 截帧必须只从代理源取帧，且 `<video crossOrigin="anonymous">`。
**这一点要在实现前先验证，否则做完发现全失败。**

用户选的采集方式：**截时弹小窗选用途**（姿势 / 审美 / 光影 / 调色）。

截帧入库时自动带：来源平台、博主、笔记、**第几秒**。

## D. 标签体系（5 个维度）

⚠️ **这一节等另两份调研回来后可能微调**（Shotdeck 的维度设计、审美学习的维度）。

基于现有树形 `Tag` 表，不用改结构：

| 维度 | 值 | 依据 |
|---|---|---|
| **题材** | coser / 老年人 / 领证跟拍 / 情侣写真 | 用户给的 |
| **人数** | 单人 / 双人 / 多人 | 行业第一权重（决定姿势能否复用） |
| **姿势族** | 站/坐/靠/走/拥抱/回头/蹲/躺/跳/互动 | 检索入口 |
| **感觉** | 松弛/优雅/可爱/帅气/电影感/仪式感/搞怪 | **只做标签不做目录** |
| **场景** | 室内/户外/民政局/影棚/街边 | 决定「什么时候用」 |
| **用途** | 姿势/审美/光影/调色 | 一个库多视图 |
| **角色作品** | coser 专用（作品名 + 角色名） | coser 圈的组织单位 |
| ~~身体部位~~ | 手/下巴/腿/重心/肩线 | **只做筛选 chip，不做一级** |

**为什么身体部位不做一级**：调研发现没有一家主流产品这么做
（Posing App 放「技巧」、ModelPoser 放子分类）。
部位是「调整手段」，不是「检索入口」，做一级会把库切碎。

**标签输入方式**（用户选的）：**受控词表 + 自由备注**。
- 受控词表用于统计和筛选
- 免费备注放「这张好在哪」这种没法结构化的东西

# 四、⭐ 一个必须正视的产品判断

调研发现现有姿势库产品都在解决「看」，但摄影师的真实痛点是「**说**」。

> SLR Lounge：「你可以学了几年摆姿，存了几百张参考图，
> 但当两个真人站在你面前时，脑子还是一片空白。
> **这不是知识问题，是检索问题。**」
>
> 「图库给你的是一张成品照片。它不告诉你**怎么把两个紧张的人**从现在的位置带到那个结果，
> 更不告诉你**过程中该说什么**。」

## 对需求的含义

**如果只做「存图 + 打标签」，做不到差异，因为 Eagle 已经够了。**

建议每个姿势条目至少带两块：

| 字段 | 内容 | 必要性 |
|---|---|---|
| 图 | 参考照片 | 必须 |
| **怎么摆** | 一句话物理指令 | **必须**（否则只是个图片库） |
| **怎么说** | 现场原话（cue） | 强烈建议 |
| 常见崩点 | 这个姿势最容易失败在哪 | 可选 |

参考结构（抄 Cue & Capture，不抄内容）：
`setup`（身体怎么放）→ `cue`（现场原话）→ `capture`（机位/张数）→ `failure`（崩点）

## 而且这正好能接上 AI

**明确的产品空位**：没有产品做「**上传姿势图 → 自动生成中文口令**」。

→ 这就是 `import_assets` 之后最值得做的 AI 能力：
**入库时顺手生成「怎么摆 + 怎么说」**。

# 四·补 ⭐⭐ 另一个更重要的判断（审美学习调研后新增）

## 4.1 「审美学习」不是一个真实的产品品类

外部调研的结论：英文里也没有完全对应的词。
真实产品把它拆成了**四种独立功能**，而且最常见、最成熟的是「收藏」：

| 对应 | 代表 | 停在哪 |
|---|---|---|
| 收藏 / 灵感库 | Eagle、PureRef、Pinterest | **存完没有下一步** |
| 分析 / 点评 | Adobe Project Indigo、PickEpic、YAN | 评的是「你拍的这张」，**不是「你存的这张」** |
| 对比 / 选择 | WhichOne、GuruShots | 帮你决定，**不教你怎么看** |
| 复盘 / 回顾 | Daily Pieces、Eagle 随机模式 | 自我认识，**不是审美判断** |

> **用户说「我要开始审美学习」，产品给他的往往只是一个更漂亮的收藏夹。**

## 4.2 「收藏夹变成技能」没有可验证的成功案例

反例倒是很硬：

> 一位 Eagle 重度用户存了 **5 万多份素材**：「随手保存只要一秒，整理一份却要十几秒」，
> 最后「几万份灵感就在硬盘里长眠。**真急着用，还不如打开 Pinterest 重新搜**。」

> 「**收藏一万张图，不如解构一百张图**。」

> Eagle 官方博客自己承认：**收集和整理本身，并不保证你变快或设计变好。**

## 4.3 ⭐ 因此核心字段要改：不是标签，是「一句话偷师点」

**原方案的核心是「标签体系」。调研后建议改成：**

> **标签解决检索，句子解决学习。**

保存一张图时，写一句「**我要从它身上拿走的那一项**」，
**不超过 40 字**，配 6 个快捷 chip：**光 / 构图 / 色彩 / 情绪 / 元素 / 标准**。

| 好例子 | 坏例子 |
|---|---|
| 「逆光把发丝和背景分开，脸留暗部」 | 「好看」 |
| 「阴影加青、高光加蓝、整体降饱和」 | 「高级」 |
| 「眼睛不要太大，下巴不要过尖，肤色不要偏绿」 | 「氛围感」 |
| 「前景用纱/玻璃做一层雾，人物只占三分之一」 | 「日系」 |

> 坏例子的共同点：**没有信息量，等于没写。**

**为什么这是唯一该做核心的功能**：

1. **唯一一个在「保存那一刻」改变用户行为的功能**——其他功能都依赖它
2. **把「好看」翻译成「可操作特征」**——正对着「只知道好看、不知道该学哪一项」这个普遍困境
3. **直接对抗「被牵着走」**——写的是自己的判断，写完图可归档、判断留下来
4. **轻**：不需要 AI、不需要每天打卡，一张图 5 秒
5. **会沉淀成「标准」**：30–50 条之后聚成「我的标准」（眼睛多大算自然、肤色多白算假）

## 4.4 三个「不要做」

| 方案 | 为什么不做核心 |
|---|---|
| **AI 评分** | 给的是通用反馈，不知道你的意图/客户/场景；**而且它鼓励你继续消费，不鼓励你判断** |
| **间隔重复（Anki 式）** | 审美判断没有唯一正确答案；**没有 note 的复习只是重新刷图** |
| **自动标签 / 以图搜图** | 解决「找得到」，不解决「学得会」 |

> AI 要做的是**追问**，不是**评分**。写完 note 后问：
> 「还有哪个维度你没注意到？」「换成你的场景这一条怎么用？」
> 输出应该是「可操作特征」（阴影加青/高光加蓝），不是 0–100。

**补充数据**：AADB 数据集里 5 个标注者的平均一致性 Kendall's W 只有 **0.5322**
——**连人类对「构图好不好」都没有高度共识，AI 的分数更不该当真理。**

## 4.5 「看多了被牵着走」要变成产品机制

这是摄影教学中反复提到的一条：过度分析他人作品，会干扰自己的判断。

但「少看」不是解——真正的结论是：
**被动地看会被带偏，主动地拆不会。问题不在输入量，在「看完之后有没有变成自己的判断」。**

| # | 机制 | 具体做法 |
|---|---|---|
| 1 | **分流** | 入库时强制选「**找感觉 / 对脚本**」；找感觉的看完归档，不长期挂在眼前 |
| 2 | **写原则不写形容词** | 不存「高级感」，存「阴影加青、高光加蓝、降饱和」 |
| 3 | **反参考** | 除了「我要什么」，再记一条「**我不要什么**」 |
| 4 | **关掉参考再创作** | 拍之前先收起来按原则拍，拍完再并排对比（不是边看边拍） |

## 4.6 ⚠️ 「审核截图」和「审美参考」不能混

| 如果是 | 那就是 | Schema |
|---|---|---|
| 别人给你的**审片意见截图** | **错误库** | 截图 + 哪里错 + 正确做法 + 标签「踩过的坑」 |
| 自己的**成片** | **作品库** | 成片 + 参数/地点/脚本 + 当时的判断 |

> **两者 schema 不同，混在一个收藏夹里会互相污染。**

## 4.7 定位警告：不要做成「另一个 Eagle」

> Eagle 已经赢了「存」，PureRef 赢了「摆」。
> 我们的差异应该是：**每次存图的一次判断 + 写方案时能翻到的弹药库**。
> 如果只做「更大更全的库」，就会重复「5 万份素材长眠在硬盘里」的命运。

# 九、v3 修订：ShotDeck 调研后的具体化

> 四份调研全部回来了。这一版把「标签体系」和「批量入库」写成**可实现的规格**。

## 9.1 标签体系定稿（5 个必做维度，照 ShotDeck 的取舍）

| # | 维度 | 取值 | 谁来填 |
|---|---|---|---|
| **①** | **人物与关系** | `单人 / 双人 / 三人以上` × `coser / 老年 / 情侣 / 亲友` | **人数和人脸年龄让 AI 数** |
| **②** | **光** | 光质（硬/柔/混合）× 方向（顺/侧/逆/顶）× 时段（清晨/白天/黄金时刻/蓝调/夜） | EXIF + 图像统计**半自动**，人工确认 |
| **③** | **色调** | 1 条主色板 + 冷暖/饱和/对比三个值；支持按色值搜 | **全自动** |
| **④** | **景别/构图** | 景别（大特写/特写/半身/全身/环境人像）+ 构图（居中/三分/留白/前景遮挡） | 半自动 |
| **⑤** | **情绪/氛围** | **不做下拉框**：用「色调 + 光 + 表情」合成 + **一个自由词** | 合成 + 用户自由词 |

**外加两个必填/可选**：
- **系列（批次）**：**唯一强制的标签**——一次上传默认落进一个「系列」
- **偷师点**：一句话，≤40 字（v2 定的核心字段）

### 明确不做的维度（省打标预算和界面面积）

| 不做 | 理由 |
|---|---|
| 相机 / 镜头型号 | 人像找参考不看机身；EXIF 自动读当「可搜不必填」 |
| 人种 | 敏感、填不准 |
| 地区层级树 | 维护成本极高；换「地点自由词 + 场景类型枚举」 |
| 故事年代 / 画幅比 / 格式 | 影视拉片或自动提取才需要 |
| 镜头运动 / 技法 | 那是 Eyecandy 的活，我们是静帧库 |

## 9.2 ⭐ 批量入库的核心机制：把打标做成「改」，不是「填」

**这是从 500 次录入降到 50 次的关键。**

```
① 上传即分组：一次上传 → 一个「系列」（唯一强制标签）
② 自动算：主色板、明暗、画幅、人脸数、人脸年龄、清晰度、重复图
③ 最近邻继承：新图找库内最近邻 → 把邻居的场景/关系/光/情绪抄过来
              → 标成「待确认」→ 人只连点「对/不对」
④ 批量套用：框选一批 → 一次设「时段=黄昏、光质=逆光、场景=民政局门口」
⑤ 「待确认 N 张」队列：让她知道还剩多少，而不是感觉永远打不完
```

**第 ③ 步是核心**：行业里 Cosmos/Savee 都验证过「找相似」这条路
（Cosmos 原话「Start with an image you love and find more like it」）。

## 9.3 截帧入库（已确认是空白，要做）

- 快捷键 → **自动取前后各 1–2 秒的 3–5 张候选帧**让她挑（避免抓到糊帧）
- **必须自动带时间码 + 来源**（ShotDeck 的 `SHOT TIME: 0:12:29` 就是干这个的）
- 入库后**立刻跑 9.2 的自动流程**，不要让她截完还要再进另一个页面打标

## 9.4 ⭐ 建议把「参考图 vs 成片对照」放进第一版

| 谁做了 | 在哪 |
|---|---|
| Lightroom Reference View | **在修图软件里，不在参考库产品里** |
| StillsLab | 参考库产品里唯一做了双图对比的 |
| ShotDeck / FilmGrab / ScreenMusings / Savee / Cosmos | **都没有** |

**这是空白位，也是最容易做出差异化的一个点。**
她拍完能立刻知道「差在哪：是光位、是色温、还是构图留白」。

**交互照 Lightroom**：
- `Shift+R` 或点 `R|A` 图标 → 2-up
- **参考图静态不可编辑，当前图可编辑**
- 切模块会清空参考图 → 要能**锁定**

→ **需要你决定：进不进第一版？** 我建议进。

## 9.5 检索入口的摆法（照行业已验证的形状）

- **首屏只放一个搜索框**（自由词）+ 5 个 facet 的第一层，其余折叠
- 已选条件做成 **chip，可单个 ×**，显示「**命中 N 张 / 共 M 张**」
- **每张图悬停就出「找相似」**，不要藏在详情页
- 首屏第一动作永远是「打几个字」，不是「展开筛选器」

## 9.6 v3 实施顺序（更新）

| 阶段 | 做什么 |
|---|---|

| **P0** | 自动算维度（主色板/明暗/人脸数/重复图）+ **最近邻继承** |

# 十一、v4 修订（用户反馈 + 摄影方法论补强）

## 11.1 ⭐ 三个库，不是两个（用户指出我漏了最重要的那个）

| 库 | 放什么 | 用途 | 我之前的问题 |
|---|---|---|---|
| **好库** | **别人的好片子**：电影截帧、大师作品、别人拍得好的 | **学 / 找参考** | **❌ 我漏了** |
| **不好库**（错误库） | 别人给你的审核意见截图、自己拍坏的 | 别再犯 | ✅ 提了 |
| **我的库**（作品库） | 自己的成片 | 复盘看进步 | ✅ 提了 |

**「审美学习」本来指的就是第一类「好库」**，我上一版把它和「审核截图」混在一起谈了，是我的错。

### 好库对应哪类产品

调研里 **ShotDeck** 就是这类：电影截图 + 按光/构图/色调/情绪检索。
我们的好库要能：
- 存别人的好图（电影/大师/网上）
- 按「光 / 构图 / 色调 / 情绪 / 场景」检索
- 每张写一句「偷师点」

### 三个库的关系

```
好库（学） ──→ 写进脚本/分镜 ──→ 拍
                                  ↓
不好库（别再犯） ←── 复盘比对 ←── 我的库（自己的成片）
```

## 11.2 不自动抽帧，改成「按人的反馈定位」

**用户明确否掉**：「视频导入自动抽帧不要了吧，AI 审美还是不太行」。

**有硬证据支持他**：AADB 数据集 5 个标注者一致性 Kendall's W 只有 **0.5322**
——连人类对「构图好不好」都没共识，AI 更不该当裁判。

**用户提的替代方案（更好）**：
> 「有别人评论过那里好看这种的可以有，比如视频是大家看过的有评论的网上」

| 信号 | 怎么用 |
|---|---|
| **B 站弹幕密度** | 弹幕突然暴涨的时间点 = 大家都觉得「这一下好看」 |
| **评论区「第几分几秒绝了」** | 直接定位 |
| **高赞评论里的时间戳** | 定位 + **理由**（他们说了好在哪） |

**为什么这比 AI 好**：
1. 不用猜，是真实的人类集体判断
2. **评论里带理由**（「这个逆光绝了」）→ 这正好就是「偷师点」

→ 所以：不自动抽帧，改成「**按弹幕/评论热度提示这段值得看**」，用户手动截。

## 11.3 摄影方法论补强带来的字段修正

读了第 09 / 22 / 25 课后，三个字段要改：

### ① 「光」维度有现成词表了（摄影通行分类）

| 光位 | 判定特征（看照片能判） |
|---|---|
| 顺光 | 脸的光线很均匀，缺少立体感（人像里最容易「平」的一种） |
| 侧顺光 | 45° |
| 侧光 | 90°，一半亮一半暗（俗称阴阳脸） |
| 侧逆光 | 身后45°；轮廓光+鼻头光 |
| 逆光 | 「拥有最强层次感」 |
| 顶光 | 鼻下阴影 |
| 底光 | 下巴向上光 |

**光质另算**：「影子深、有边缘 = 硬光；无边缘、过渡均匀 = 柔光」

### ② 「情绪」不是单张标签，是「整组主题 + 曲线」

> 「从平静慢慢有些爆发，然后再到完全安静下来」
> 「几乎每一张图看着都有一点点病态」「最后放了一个窗户，好像看到希望」

→ 情绪字段应该挂在**系列/整组**上，不是一个主题词 + 一条情绪曲线；
单张图可以有「表情」标签，但不是「情绪」。

### ③ 加「可实现性」判断

**摄影常识**：把别人片子的色调搬到自己照片上，只有在**题材、风格、配色都相近**时才成立；
条件差太远时，同一套调色会「反噬」画面。

→ 参考库每条要有：**可实现 / 不可实现**（这也是之前调研里已经提过的标签）

# 十二、v5 修订：补完摄影方法论后新增的字段

> 这一版来自对摄影方法论的系统补强（构图/光线/灯光/磨皮/情绪/调色六个模块）。
> 只写通用摄影知识，不引用任何具体课程内容。

## 12.1 新增候选字段（8 个）

| 字段 | 取值 | 必要性 | 为什么 |
|---|---|---|---|
| **光影结构是否完整** | 完整 / 被磨平 | **高** | 人像修图最常见的失败是「把脸磨平了」，光在脸上的结构没了。这是「不好库」最有价值的判据之一 |
| **背景虚化** | 浅 / 中 / 深 | 中 | **比记录光圈值 f/1.4 更有意义**——用户关心的是视觉结果，不是参数 |
| **焦段感** | 广角（脸会变形）/ 标准 / 长焦（脸被压缩） | 中 | 焦段改变人脸透视，这是「风格」维度，不是「参数」维度 |
| **灯数** | 1 / 2 / 3+ | 中 | 只对「灯光人像」题材显示 |
| **主灯作用** | 控环境 / 做造型 | 中 | 同上 |
| **色片** | 有（什么颜色）/ 无 | 中 | 同上 |
| **色彩搭配** | 互补（橙蓝 / 红青）/ 类似（蓝白）/ 单色 | 中 | 灯光人像的核心检索词，而且是成套的名字 |
| **胶片** | 底片型号 + 冲扫方式 | 可选 | 「胶片感」是可追溯的具体配方，不是玄学 |

## 12.2 色温要记两项，不是一项

**摄影常识里的一个坑**：光源的色温值，和相机白平衡设置里的色温数值，**变化方向是相反的**
（数值变小反而画面变冷）。

→ 参考库如果记色温，必须同时记：
- **光源色温**（这个灯/这个时段的光是多少 K）
- **相机白平衡设置**（当时设了多少 K）

只记一个，以后无法复现。

## 12.3 「磨皮不能破坏光」应该做成一条审美检查项

人像修图里最难的一步不是调色，是**磨皮**——因为它要在「让皮肤变好」和「保持光在脸上的结构」之间平衡。

**失败的样子**：脸变得平整光滑，但光没了——鼻子没立体感、颧骨没阴影、轮廓糊了。

→ 做成一条可勾的检查项：**「光影结构还在吗？」**
→ 这条同时属于「不好库」（记录踩过的坑）和「参考 vs 实拍对比」（诊断差异）

## 12.4 对「参考 vs 实拍对比」的诊断项补充

之前的六项（光位/色温/构图/景别/情绪/背景）要补两项：

| 诊断项 | 怎么比 |
|---|---|
| **光影结构** | 参考有立体感 / 实拍被磨平或补光过度 |
| **色彩搭配** | 参考是橙蓝互补 / 实拍是单色 |

## 12.5 v5 状态

需求到这里，**字段设计已经完整**（v1 四件事 + v2 偷师点 + v3 标签体系 + v4 三类库 + v5 摄影字段）。

**原型已占位**：`docs/prototypes/photo-ref/index.html`
（三个库 + 偷师点 + 参考 vs 实拍对比 + 筛选 + 批量/截帧入口）

**下一步**：等用户验收原型，再决定先实现哪一块。

# 十三、v6 修订：「场景」维度定稿（外部调研后）

## 13.1 核心结论：场景必须拆成两个正交维度

> **场景类型**（受控词表，15 个叶子）+ **地点**（自由文本）
>
> **不要把场景做成一个不断加长的标签列表。**

### 为什么必须分开

**地点是容器，场景是容器里的环境类型。**

| 地点（容器） | 里面有哪些场景类型 |
|---|---|
| 亚龙湾 | 沙滩 / 雨林 / 草坪 / 礁石 / 花园 |
| 民政局 | 大厅 / 颁证台 / 门口 / 车内 / 附近咖啡店 |

合并的话会产生「地点 × 场景」的组合爆炸——这正是标签膨胀的来源。

而且**同一场景类型会跨地点复用**：「海边」可以在三亚、厦门、青岛；「咖啡店」在任何城市。

**产品佐证**：
- Google Photos 侧栏把 **Places** 单独分开
- Lightroom 把 **Where** 做成地点层级，另用 Who/What/When 描述其他维度
- 旅拍业务自己就把「心仪的城市」和「心仪的风格」分开问

**没有找到任何公开产品把「地点 + 场景类型」做成同一棵树。**

## 13.2 场景类型 v1：5 组、15 个叶子

| 大类 | 叶子 | 打标时看什么 |
|---|---|---|
| **室内棚拍** | 影棚 / 纯色背景 | 背景纸、柔光箱、影棚灯、无明显环境 |
| | 实景基地 / 主题棚 | 欧式柱、韩式布景、中式木构、仿真街景 |
| **室内生活** | 居家 / 室内 | 沙发、床、厨房、阳台、窗帘 |
| | 店铺 / 民宿 / 咖啡店 | 吧台、货架、菜单、民宿床品、书店 |
| **城市人文** | 城市街拍 / 建筑 | 街道、巷弄、斑马线、招牌、天桥、地标 |
| | 交通 / 车内 | 车内座椅、方向盘、车窗、车站、公路 |
| | 展馆 / 活动现场 | 展台、漫展场馆、舞台、灯光架 |
| **自然户外** | 公园 / 校园 / 绿地 | 树、草坪、长椅、跑道、教学楼 |
| | 海边 / 水边 | 沙滩、礁石、海浪、栈桥、湖边、泳池 |
| | 山林 / 草地 / 花海 | 树林、山路、草地、花田、芦苇、茶园 |
| | 古镇 / 园林 / 古建 | 白墙黛瓦、木构、亭台、石板路、城墙 |
| | 废墟 / 工业 / 天台 | 断墙、水泥、厂房、铁架、天台、车库 |
| **仪式政务** | 民政局 / 政务大厅 | 红底、登记窗口、颁证台、宣誓厅、喜字 |
| | 教堂 / 礼堂 / 宴会厅 | 彩窗、长椅、拱顶、酒店宴会厅 |
| **其他** | 无法判断 | 环境信息不足 |

**先不单列的**：「雪山 / 沙漠 / 盐湖」暂放「山林 / 草地 / 花海」；
「漫展」放「展馆 / 活动现场」。量大了再加二级。

**教堂和民政局不能合并**：领证和婚礼是两种业务，检索语义不同。

## 13.3 地点：独立维度，不做长受控列表

| 项 | 做法 |
|---|---|
| **城市** | 20–30 个常用做下拉 + 自由输入 |
| **具体地点** | 自由文本（「西湖区民政局」「亚龙湾公共沙滩」） |
| **未知** | 允许留空，**不强迫填** |
| **层级** | 最多 3 层（国家 → 省 → 城市）；具体地点不做层级 |

## 13.4 标签膨胀的控制数字（有出处）

| 原则 | 出处 |
|---|---|
| **2–3 层**，用 facet 组合替代深树 | Trimming an Untamed Taxonomy |
| **少于 4 层**，每子类至少 2 个条目，**3 次点击可达** | FotoWare |
| **3–4 层**；**400 个叶子是灾难**，用户用不到第 3 层 | Aetopia |
| 「把不同性质的词放同一层」是最大毛病；应建**平行维度**而非一棵树 | 中文 taxonomy 资料 |

### 我们的执行数字

| 项 | 目标 |
|---|---|
| 场景大类 | 4–6 个 |
| **场景叶子** | **12–16 个**（现在是 15） |
| 场景层级 | **2 层** |
| 每维度取值 | 5–12 个 |
| 每张图标签数 | **3–6 个** |
| **总受控值** | **60–80 个**（超 100 要警惕） |

## 13.5 维护规则（防膨胀）

1. **一个概念一个规范词**，同义词走「入口词」表（棚拍=影棚；海边=海景；民政局=婚姻登记处）
2. **新值只在「其他」超过 10% 且连续 2 个月时增加**；不要在一次批量上传中临时加
3. **3 个月使用率 < 5% 的叶子合并或停用**；停用不删除，保留历史映射
4. **一个叶子超过 20% 的图就考虑拆分**；拆前先看是不是「其他」在混淆
5. **每季度审查**：看「其他」占比、搜了但库中没有的词
6. **变更留记录**：旧值→新值映射 + 生效日期

## 13.7 批量打标签流程（100–500 张）

1. **先建词表，再上传**：批量过程中**不加新值**
2. **按拍摄批次打默认值**：一次拍摄通常同一题材、同一地点、1–2 个场景
3. **用「最近使用标签」**：适合大批量重复标注
4. **只强制 3 个字段**：题材、场景类型、人数；其他允许空
5. **「其他」集中放**：每周统一看一次，再决定加值还是归并
6. **保存常用筛选**：领证 / 情侣 / 老年 / coser 各存一个智能集合

## 13.8 六条「不要做」

- ❌ 不要把地点塞进场景词表（「民政局门口」是地点不是场景）
- ❌ 不要照搬影楼销售目录（影楼按套系卖，按视觉找是两回事；它能组合上千种场景）
- ❌ 不要一开始做 50+ 场景
- ❌ 不要让「其他」成为垃圾桶（>10% 说明词表缺类）
- ❌ 不要把风格/服装/色调塞进场景
- ❌ 不要给情绪做下拉（已定用合成）

## 13.9 一句话

> 场景维度的目标不是「穷尽所有拍摄地」，而是
> **让摄影师在 3 次点击内找到「我想要的那种环境」**。
> 15 个场景叶子 + 一个独立的地点字段，比 100 个场景标签更接近这个目标。

# 十四、v7 修订：对比不是唯一形态，参考图也可以临时给

> 用户指出：「作品可能有的是直接拍的，然后分析，没有对比，这种考虑过吗？
> 并且对比的应该是可以自己传的。」

**这暴露了我之前一个隐藏假设：默认「每张作品都有参考图」。** 不成立。

## 14.1 两种模式，不是一种

| 模式 | 前提 | 干什么 | 依据 |
|---|---|---|---|
| **参考对照** | 有参考图 | 比「像不像」 | Lightroom Reference View 的心智 |
| **分析作品** | **没有参考图** | 看「好在哪、差在哪」 | Adobe Project Indigo / PickEpic 的心智 |

**实际拍摄里很多是直接拍的**：客户没给参考、临时想到的画面、抓拍。
这些没有「参考」可比，但仍然需要复盘。

### 分析模式的关键设计

**不打分。** 分成三类输出：

| 类别 | 内容 | 标记 |
|---|---|---|
| **成立的地方** | 可观察的事实 | 绿标「可观察事实」 |
| **可疑的地方** | 需要创作者判断的点 | 黄标「要你判断」 |
| **看不到的地方** | EXIF 里没有的信息 | 灰标「参数里没有」 |

> 比如：「f/4 让背景还看得见轮廓，虚化比常见的弱。
> **是故意保留环境，还是当时光线不够？**」
> —— 这是提问，不是结论。

**「看不到的地方」这一类尤其重要**：你当时想表达什么、这张在整组里是开头还是结尾，
这些 EXIF 永远读不出来，只能由人说。

## 14.2 参考图必须支持「临时给」

**不能假设参考图一定在库里。**

真实场景：
- 客户刚在微信发来一张「我想要这种感觉」
- 刚在小红书刷到一张，还没入库
- 电脑里存着一张，从来没用过

### 三种来源

| 来源 | 交互 |
|---|---|
| **从审美库选** | 走库内检索 |
| **临时上传 / 拖入** | 直接把文件拖进面板 |
| **粘贴图片** | Ctrl+V |

**关键**：临时参考图**不用先入库**。对比完再决定要不要存进审美库。

> 这符合「采集摩擦要低」的原则——如果对比前必须先入库，
> 用户会放弃对比，直接凭感觉看。

## 14.3 两个模式共享同一个助手

对比助手和分析助手是同一个，只是切换上下文：

| 模式 | 助手第一句话 |
|---|---|
| 参考对照 | 「我看完两张图的参数了，硬数据上差在这几处…」 |
| 分析作品 | 「这张我只看得到参数和画面，**看不到你的意图**…我不打分。」 |

**都要做的事**：先报确定的（EXIF），再指出不确定的，最后提问。

# 十五、v8 修订：分析模式去掉三类卡片（用户明确要求）

> 用户原话：「不需要这三卡片，我自己分析。显示下拍摄参数和当时的脚本啥的，
> 可以折叠编辑。最多和智能体聊聊，让它总结，然后可以添加到反思。」

## 15.1 我上一版做错了什么

我做的是「**工具替你分析**」——输出三类卡片（成立/可疑/看不到）。
用户要的是「**工具替你摆材料，分析自己来**」。

> **这是个方向性错误：把「辅助」做成了「代替」。**

## 15.2 改成：三块折叠记录 + 一个能聊的助手

### 三块折叠区（默认收起，点开可编辑）

| 折叠区 | 内容 | 来源 |
|---|---|---|
| **拍摄参数** | 相机 / 镜头 / 焦距 / 光圈 / 快门 / ISO / 白平衡 / 时间 / 地点 | **EXIF 自动读** |
| | **补录**：当时的光、现场状况 | **人填**（EXIF 看不出） |
| **当时的脚本** | 项目 / 场景 / 分镜 / 要的画面 / 必带道具 | 关联摄影策划台 |
| | **偏离了** + **为什么** | **人填** |
| **客户/自己的评价** | 客户原话（别转述）+ 自己的判断 | **人填** |

**关键**：每一块都是「**自动的自动填，人工的人工补**」，来源标清楚（绿标 EXIF / 黄标人填）。

### 智能体的角色变了

| 之前（错） | 现在（对） |
|---|---|
| 替你分析、输出结论卡片 | **陪你聊，帮你把话理清楚** |
| 「成立/可疑/看不到」 | 「要不要我整理成一句可以存的反思？」 |
| 单方面给判断 | **等你先说自己感觉到什么** |

**交互示例**（原型里的）：
```
你：这张我感觉光对了，但脸有点太暖，说不上来哪不对
AI：看参数对上了：白平衡设的是 6100K，而当时的光是下午 5 点侧后方的太阳，
    这个时段的自然光本身偏暖，相机再往暖设就叠加了。
    再加上你补录的「风大、抓十几张」，说明是按快门优先在抢瞬间，
    颜色判断被牺牲了。
    下次可以试：白平衡往 5200K 压，或者拍之前先对白纸定一次。
    → 生成总结，存进反思
```

**AI 的作用**：**用你补录的信息 + EXIF，把你「说不上来」的感觉翻译成具体原因**。
它不做审美裁判，它做翻译。

### 存进反思是一步动作

AI 生成的总结 → 你确认 → **存进「反思」库**，带自动标签（白平衡/傍晚/逆光）。

这条链路把三个库串起来了：
```
作品（这张图） → 和 AI 聊 → 总结 → 存进 反思（下次别再犯）
```

# 十六、v9 修订：补两个维度（个性来源 / 表演方式）+ 一个漏掉的对象

## 16.1 新增两个维度：这张片子是「谁」的个性

人像作品里的「个性/性格」来自两处，需要分开记：

| 维度 | 取值 | 用途 |
|---|---|---|
| **个性来源** | 模特的 / 摄影师的 | 这组片子是记录她，还是表达我 |
| **表演方式** | **本色出演** / **角色扮演** | 让模特做自己 vs 让她演一个角色 |

**为什么重要**：
- 「角色扮演」是绝大多数商业/写真拍摄的实际形态（摆姿势、演情绪）
- 「本色出演」很难，前提是**你足够了解这个模特**
- 两者对脚本、对引导口令的要求完全不同

## 16.2 ⭐ 漏掉的一个对象：模特 / 客户

之前所有调研和需求里都没有这个对象。但真实工作流里它是核心：

**你要「本色出演」，就得了解这个人。**

建议加一个轻量对象：

| 字段 | 内容 |
|---|---|
| 称呼 | |
| 性格特点 | 她自己说的 + 你观察到的 |
| 拍过的片子 | 关联作品库 |
| 适合的方向 | 什么风格她最好看 |
| 她自己的偏好 | 她喜欢/不喜欢什么 |
| 注意事项 | 镜头恐惧、体态问题、沟通方式 |

**为什么值得单独建档**：
- 老客户/老模特复拍是常态
- 「了解」是慢慢积累的，散在作品里会丢
- 这也是「作品库」和「反思库」之外，第三个需要长期沉淀的东西

## 16.3 反思库可以有一条固定检查清单

人像后期有固定的处理顺序（修瑕疵和磨皮可以互换，其余不宜乱序）。
反思时按顺序过一遍，比自由写更容易发现遗漏：

```
曝光 / 白平衡 → 瑕疵 → 液化（形体）→ 磨皮（高光阴影结构）
→ 调色 → 肤色 → 锐化/输出
```

**注意**：这只是「检查顺序」，不是「我们替他做」——判断仍然是人做。

本版无原型改动（维度与对象是需求层的）。
原型最新是 v8：三块折叠记录 + 能聊的助手 + 存进反思。

# 十八、v11：「反思」库页面（唯一会随时间增值的库）

## 18.1 为什么反思库长得和另外两个不一样

「审美」和「作品」是**图片网格**——因为它们的单位是「一张图」。
「反思」是**文字条目列表**——因为它的单位是「一条经验」。

> **一条经验可能挂着几张图，但它是独立存在的。**
> 所以不能做成网格，否则就成了「作品的附属品」。

## 18.2 每条反思的结构

| 字段 | 内容 | 例 |
|---|---|---|
| **状态** | 还会犯 / 已改掉 / 未标 | `还会犯` |
| **一句话** | 那条经验，≤60 字 | 「傍晚侧逆光拍摄时，白平衡不要跟着光走……下次压到 5200K 或先对白纸定白。」 |
| **来源** | 分析作品 / 参考对照 / 审核截图 | |
| **时间** | 3 天前 | |
| **标签** | 自动继承 | `白平衡` `傍晚` `逆光` |
| **原图** | 缩略图 + 「↗ 看原图」 | 点得回去 |

## 18.3 ⭐ 唯一需要人维护的状态：「还会犯 / 已改掉」

**这是整个功能的骨架。**

不是所有经验都值得一直挂着。积累到 200 条的时候，
如果全都是「重要提醒」，等于全都不重要。

| 状态 | 含义 | 视觉 |
|---|---|---|
| **还会犯** | 还没改过来，要提醒 | 红色左边条 |
| **已改掉** | 这条已经收进肌肉记忆了 | 绿色左边条 + 整条变淡 |
| **未标** | 刚存进来的 | 灰色 |

**点一下就切换**，不写进度、不打卡。
「已改掉」的条目变淡但不删——因为**它证明你进步了**。

## 18.4 四种视图（按状态切）

| tab | 内容 | 为什么需要 |
|---|---|---|
| **全部** | 37 条 | |
| **还会犯** | 5 条 | **拍之前该看的是这个** |
| **已改掉** | 32 条 | **低谷期该看的是这个**——你改掉了 32 个毛病 |
| **很久没看** | 8 条 | 防止经验腐烂 |

> 「已改掉」这一栏有个心理作用：**它把「我好像没什么进步」变成可查证的数字。**

## 18.5 按维度筛选

白平衡 / 站位·光位 / 构图 / 引导 / 磨皮 / 交付

# 十九、v12：图片切换与键盘（按行业事实标准，不凭感觉）

> 用户原话：「分析这种的应该可以上下图片切换，类似 Lightroom 编辑那种？看看主流怎么做的」

## 19.1 ⚠️ 三处纠正（调研结论与直觉相反）

| 直觉 | 事实 | 出处 |
|---|---|---|
| 「上下切换」 | **左右（← / →）才是事实标准** | Lightroom 官方：「Go to next/previous photo in the Filmstrip — Right Arrow / Left Arrow」；Photo Mechanic、Figma、Google Photos 一致 |
| 「J/K 是翻页」 | **不是**。Lightroom 里 J = 显示剪切预警（Develop）/ 循环网格（Library），K = 调整画笔 | Lightroom 官方快捷键文档 |
| 「上下键没用」 | 有明确分工：**↑/↓ 在 Photo Mechanic 预览窗 = 按页滚动缩略图条**，在 Lightroom Compare = 交换对比对象 | 两家官方文档 |

> **「切换内容」用左右，「滚动浏览」用上下。**
> 这是桌面修图软件和网页图库的压倒性惯例。

## 19.2 采纳的键位（对齐事实标准，不发明新键）

| 动作 | 键 | 依据 |
|---|---|---|
| 上一张 / 下一张 | **← / →** | 四家一致 |
| 放大 / 还原 | **空格** | Lightroom Loupe↔1:1 |
| 显隐胶片条 | **F6** | Lightroom |
| 显隐右侧参数面板 | **F8** | Lightroom |
| 打星 | **1–5** | 三家一致 |
| 清除星 | **0** | 三家一致 |
| 收藏 / 淘汰 | **P / X** | Lightroom |
| 颜色标签 | **6–9** | Lightroom |
| 关闭 | **Esc** | |

### ⭐ 最容易被低估的一组：标记并自动跳下一张

| 组合 | 作用 |
|---|---|
| **Shift+P** | 收藏并下一张 |
| **Shift+X** | 淘汰并下一张 |
| **Shift+1–5** | 打星并下一张 |

> **把「标记」和「翻页」合成一个动作，一晚上少按几千次方向键。**

调研说这是摄影师觉得 Lightroom「快」的第一原因，排在「胶片条只加载附近图」和「全键盘单键」之前。

### 明确不这样用

| 键 | 为什么不用 |
|---|---|
| **↑ / ↓** | 留给滚动胶片条和换对比对象（Photo Mechanic / Lightroom 的分工） |
| **J / K** | 与 Lightroom 语义冲突，强行用会和肌肉记忆打架 |

## 19.3 布局：中图 + 右参数 + 底胶片条

三家（Lightroom / Capture One / Photo Mechanic）布局一致：

```
┌─────────────────────────────┬──────────────┐
│                             │              │
│         大图（居中）         │  参数面板     │
│                             │  （可折叠）   │
│                             │  偷师点       │
│  [← ] ←/→ 切图 [ →]         │  标签/场景    │
│   快捷键提示条                │  拍摄参数     │
├─────────────────────────────┴──────────────┤
│  胶片条（F6 显隐）                          │
│  [▣][▣][▣][▣] 后 2 张 →                    │
└────────────────────────────────────────────┘
```

**两条要点**：
1. **参数面板在右侧，不覆盖在图上**——选片时人在判断画面，遮挡等于减分
2. **胶片条只渲染当前前后几张**（Photo Mechanic 的做法），不要一次加载整个图库

## 19.4 「上下滚动浏览」要不要做

**可以做，但不做主模式。**

| 模式 | 适合 |
|---|---|
| 左右翻页 | **批量选片 / 精确回看 / 需要标记** |
| 上下滚动 | 轻浏览、发现、「下一个更好看」 |

Instagram 式竖流在「停下、标记、回看某张」这三件事上都更差。
建议作为**次要模式**（一个开关切换），默认关闭。

# 二十、v13：⚠️ 反思模型重做（用户纠正）+ 作品分组 + 修图打通

## 20.1 ⚠️ 我错了：反思不是「学会了就不会再犯」

> 用户：「提示不对，应该是提示**可能遇到的问题**，
> 反思这种东西**不是说学习了下次就不会犯了**。」

### 我原来的错误设计

| 我的设计 | 错在哪 |
|---|---|
| 状态：**还会犯 / 已改掉** | 把反思当成**待办任务**，暗示「改掉 = 完成」 |
| 「已改掉」变淡、收起来 | **收起来就不再提醒了**——恰好在最该提醒的时候消失 |
| 拍完才知道犯了 | 反思没用在前 |
| 提示方式：「你还有 2 条傍晚的毛病没改」 | **这句话的潜台词是「改了就没事了」，是错的** |

### 正确的模型：反思 = 条件触发的提醒

**一条反思不是「一个待办」，是「一对（条件 → 容易犯的错）」。**

| 字段 | 说明 | 例 |
|---|---|---|
| **一句话** | 那条经验 | 「傍晚侧逆光时，白平衡不要跟着光走」 |
| **⭐ 触发条件** | **什么情况下会重现** | `傍晚` `逆光` `白平衡手动` |
| **热度** | 最近犯了几次 | 最近又犯了 / 有触发条件 / 很久没犯 |
| **原图** | 可选，可完全不挂 | |

### 状态从「完成度」改成「热度」

| 旧 | 新 | 含义 |
|---|---|---|
| 还会犯 | **最近又犯了** | 最近踩过，现在最该看 |
| 还会犯 | **有触发条件** | 有明确的重现条件，平时安静 |
| 已改掉 | **很久没犯** | 冷静下去了，**但不删** |

> **你犯一次它就热一次，很久不犯它就冷静下去，但永远不会被删掉。**

### 提示方式也要改

| 旧（错） | 新（对） |
|---|---|
| 「你还有 2 条傍晚的毛病没改」 | 「**傍晚逆光的时候，你以前在这上面栽过 —— 白平衡容易跟着光走，压到 5200K 更稳**」 |

**关键区别**：
- 旧：「你有毛病没改」→ 暗示改了就完事
- 新：「**这种条件下你容易怎样，先留意**」→ 提醒，不是任务

### 这个模型下「触发条件」是最重要的字段

因为它决定「什么时候冒出来」。没有触发条件的反思 = 永远不响 = 白存。

→ **写反思的时候，触发条件应该比那句话更被强调。**

## 20.2 ⭐ 反思可以不挂图：写完拍的总结

> 用户：「要，可以不带图，可能就是**我拍照完了的反思或总结**」

新增一种反思类型：

| 类型 | 有没有图 | 例 |
|---|---|---|
| **从图上来的** | 挂图 | 「参考是侧逆光我是顺光，差在站位」（来自分析/对比） |
| **⭐ 写完拍的总结** | **不挂图** | 「今天这组整体比上次松……但中途客户来了朋友围观，节奏乱了」 |

**为什么这类很重要**：
- 拍完的感受是**整组的**，不属于任何单张图
- 「这个月十八组里有九组是逆光，发现自己总在安全区」——这种观察**没有对应的图**
- 强迫挂图 = 逼人把组级经验硬塞给某一张，反而失真

→ 原型里用了紫色「写完拍的总结」徽章 + 「不带图」占位，视觉上就不一样。

## 20.3 作品要能按拍摄批次分组

> 用户：「作品要可以分组文件夹，类似那种，我今天拍的人像或者风景。
> 也可能一天拍了好几组。」

### 分组用「拍摄批次」不用「文件夹」

**为什么**：「文件夹」是死目录，一次拍摄可能跨两个地点；「拍摄批次」是一个**事件**，天然带时间、客户、场景。

| 分组维度 | 内容 |
|---|---|
| **批次名** | 自动建议「今天 · 小清新人像 · 客户A」 |
| 时间 | 拍摄日期（可从 EXIF 批量推） |
| 张数 | 18 张 |
| 场景 | 民宿 / 城市街拍 / 民政局 |
| **修图进度** | **未修 / 已修 12 / 已交付** ← 关键 |

### 修图进度是分组的核心价值

一次拍摄几十张，修到哪了是真实痛点。
→ 批次卡片上直接显示「已修 12 / 18」，不用点进去数。

**一天可以有多组**：原型里就是「今天 · 小清新人像 · 客户A」和「今天 · 街拍 · 客户B」并列。

# 二十一、v14：「出门前检查」页（两个使用场景对齐后的产物）

## 21.2 三个关键判断

### ① 这是「动手前的检查」，不是「事后复盘」

我之前的反思库是**事后**用的（拍完存反思）。用户说的两个场景都是**动手之前**。

→ 所以反思库之外，需要一个**前向的检查页**。两者共用同一批数据。

### ② 人群类型要按调研证据强度分三档，不是只做四类

> 用户：「不只是这四类，我只是举例，你可以按你调研数据来。」

| 档 | 类型 | 依据 |

| **有分组方法**（按关系/流程组织） | 婚纱/婚礼（关系分组）、家庭/亲子（关系分组）、旅拍（城市→景点） | 调研有明确组织方式，但没到口令级 |
| **暂无专门结论** | 个人写真 / 小红书博主 / 商业人像 | **如实标「还没有这个类型的结论，拍完可以自己补一条」** |

> **不硬编数据。** 没有结论的类型就明说没有，而不是编一段像模像样的文字。

### ③ 客户偏好「按类型」不「按个人」

| 细节 | 为什么 |

## 26.1 实现了什么

在原型里内置 **NOAA 太阳位置算法**（`SunCalcLite`，约 90 行纯 JS，无任何外部依赖）：

```
输入：纬度、经度、日期、时区、当地时刻
输出：太阳方位角（0-360°）、高度角（-90~90°）

支持：
  · 任意时刻的太阳位置
  · 日出/日落时刻（二分搜索高度角穿过 -0.833°）

```

## 26.2 ⚠️ 过程中踩了两个真 bug（都验证出来了）

### Bug 1：时角公式用错了时间基准

**第一版**用 UTC 小时算真太阳时：
```js
const utcHours = hour + minute/60 - tz;
const tst = (hour*60 + minute + eqtime + 4*lon) % 1440;  // ← 混用了当地时间和 UTC 时刻
```

**症状**：正午 12:00 算出太阳高度角 **-33.7°**（太阳在地平线下）。

**修正**：标准公式是「当地钟表时间 + 时差 + 4×(经度 − 时区中心经度)」
```js
const tzCenterLon = tzOffsetHours * 15.0;   // UTC+8 → 120°E
const tst = (hour*60 + minute + eqtime + 4*(lon - tzCenterLon)) % 1440;
```

**验证**：修后 12:00 太阳在正南 180.4°、高度 33.4° — 完全合理。

### Bug 2：二分查找里用了未定义变量

原代码 `var prev_h = h;` 在循环末尾声明，但循环开头就用了 `prev_h`——
第一次迭代时它是 `undefined`，导致整个查找失效。

**修正**：重写为闭包 `altAt(h)` + 提前保存 `prevH/prevAlt`。

# 三十二、v25：模特 / 客户档案（所有竞品都没有的对象）

> 用户选择「1」——做模特/客户档案
>
> 依据：从课程里挖出来的判断——「想要拍好**本色出演**其实是比较难的，
> **你得对这个模特非常的了解**」

## 32.1 为什么这个对象重要

**拍「本色出演」的前提是你真的了解她。**

但这些信息散在聊天记录和记忆里，**每次复拍都要重新想一遍**。

> 建一次，以后都在。

**而且这是唯一一个「越用越值钱」的对象**：
- 作品会过时
- 反思会冷静
- **但「了解一个人」只会越来越深**

## 32.2 六个核心模块

### ① 头部：这个人是谁

- 合作次数、最近合作时间、关系类型
- **个性标签**（从观察里提炼）：说话直来直去 / 不怕丑 / 偏爱胶片感 / 不喜欢大笑

### ② ⭐ 这个人该怎么拍（核心判断）

**按课程框架分成两种**：

| 方式 | 对她的判断 |
|---|---|
| **🎭 本色出演**（推荐） | 「她不需要演。**给她空间和环境，让她自己做事情**就行——她发呆、走路、整理头发的时候最好看。」 |
| **🎬 角色扮演** | 「她**演不了**「甜」和「活泼」，会明显僵。**别让她对着镜头笑**，一要求笑就出戏。」 |

> ⚠️ 这是**每次拍完更新**的判断，不是一开始就有的。
> **第 1 次是猜，第 8 次是准的。**

### ③ 拍之前要知道的（观察到的）

| 项 | 内容 |
|---|---|
| 性格 | 说话直来直去，不绕弯。不喜欢被夸，夸多了会不自在 |
| 镜头前 | 不怕丑，但**在意「假」**——一张图她觉得摆拍就会直接说 |
| 节奏 | 能接受慢，不催。可以一个镜头拍半小时 |
| 偏好 | 喜欢胶片感、低饱和、真实皮肤。不喜欢过度磨皮 |
| **禁忌** | 别让她「笑一个」；别用太甜的引导词（「小可爱」这种她会翻白眼） |

### ④ ⭐ 对她管用的口令（实测有效 / 实测无效）

**这是别的产品不会有的——口令是按人积累的。**

| 口令 | 状态 | 说明 |
|---|---|---|
| 「你就当我不在，做你自己的事」 | ✅ **有效 5/6 次** | 她讨厌被注视，这句把「拍摄」变成「记录」 |
| 「往前走，我数到五你再回头」 | ✅ 有效 | 计数给了她明确任务，不用想「我该摆什么」 |
| ❌「笑一个」「放松一点」 | ❌ **失败 4 次** | 一听到「笑」就进入执行态，嘴角僵眼睛没笑。**这条已经失败 4 次了，别再用了** |

**「失败次数」和「成功次数」都记**——这比只记有效的话更有用。

### ⑤ 容易出问题的地方

| 级别 | 内容 |
|---|---|
| 🔴 | **不要一次给多个指令**。她说过「一下说太多我脑子是空的」 |
| 🟡 | **拍到第 40 分钟左右会累**。她不会主动说，但表情会开始僵 |
| 🟡 | **风大的天她会睁不开眼**。2025-10 那次拍废了半小时 |

### ⑥ 了解的过程（时间线）

```
2026-09 第8次   确认「你就当我不在」最有效。她开始主动提想法了
2026-06 第6次   发现她不喜欢大笑，但喜欢闭眼的片子。调整了引导方向
2026-03 第4次   开始能预测她在哪个环节会僵。第40分钟定律第一次被记下来
2025-10 第1次   第一次合作。当时全是猜的——以为她喜欢甜一点，拍出来一张没选
```

**时间线让人看见「了解」是怎么长出来的。**

## 32.3 底部的「下次拍她之前，这三点最该记住」

> 1. **别让她笑。**给她事情做，让她自己进入状态。
> 2. **一次一个指令。**她明确说过指令多了脑子是空的。
> 3. **第 40 分钟安排坐下。**她自己不会说累，但脸会出卖她。

**这是整个档案的浓缩版**——真到现场只会看这三行。

## 32.4 和别的模块的关系

```
模特档案 ←→ 脚本策划（选人时带出「该怎么拍」）
    ↓
拍摄 → 拍完更新档案（第 N 次 → 第 N+1 次）
    ↓
作品库（她的 8 次合作）
    ↓
反思库（对她的专属反思）
```

- ✅ 头部档案（个性标签）

## 37.1 五道检查全部实现

| # | 检查 | 动作 | 实现方式 |
|---|---|---|---|
| **1** | 含**形容词**（自然/放松/自信/高级/好看…） | **拦** | 关键词匹配 13 个 |

| **5** | 没有**来源** | **拦** | 字段必填 |

```
③ 不是纯禁止式                  ✓  ← 绿
④ 有重试说法                    !  ← 黄（未填）
⑤ 有来源                        !  ← 黄（未填）
```

# 三十八、v31：⚠️ 两个纠正（用户指出）+ 新建拍摄双模式

## 38.1 ⚠️ 纠正一：我一直在超纲做「实现」，不是「原型」

> 用户：「为什么原型你总想接真的」

**他说得对。** 我做的这些严格说超纲了：

| 我做的 | 该不该在原型阶段做 |
|---|---|
| 接入真实 API（Open-Elevation / Nominatim） | ❌ 超纲 |
| 「实测验证通过」太阳算法 | ❌ 超纲 |
| 让录的口令真的存下来、能引用 | ❌ 超纲 |
| 现场页接真实数据传递 | ❌ 超纲 |

**约定的边界是**：
> **原型先把位置占上，具体实现之后再说。**

**原型该做的是**：界面长什么样、信息放哪、交互怎么走。
**不该做的是**：数据从哪来、真不真、能不能跑通。

> 我之前把「算得准」当成优点，其实是在**提前做实现**，
> 会拖慢原型迭代，也可能在需求没定死时白做。

**后续原则**：原型里数据一律是**写死的示例值**，需要说明的地方标「示例」。

## 41.4 没有 ffmpeg 的解决办法：PyAV

项目里**没有装 ffmpeg**（`where ffmpeg` 找不到，也没有 imageio-ffmpeg）。

**但 faster-whisper 依赖的 PyAV 自带 ffmpeg 库，含 libmp3lame 编码器。**

所以可以纯 Python 抽音频：

```python
import av
inp = av.open(video)
a = inp.streams.audio[0]
out = av.open('out.mp3', 'w', format='mp3')
ost = out.add_stream('libmp3lame', rate=16000, layout='mono')
ost.bit_rate = 32000
inp.seek(int(start / a.time_base), stream=a)
for frame in inp.decode(a):
    ft = float(frame.pts * a.time_base)
    if ft < start: continue
    if ft > end: break
    for pkt in ost.encode(frame): out.mux(pkt)
for pkt in ost.encode(None): out.mux(pkt)
```

**不需要装 ffmpeg。**

### ① ⭐ 拍摄参数 Tab（焦段 / 光圈 / 快门 / 白平衡 / 光质 / 布光）

**最大的错误是：之前现场页只有「快门/光圈/ISO」，没有焦段。**
但知识里明确：**影响风格的三个参数是焦段、光圈、快门**，ISO 恰恰不影响。

新 Tab 内容：

| 模块 | 内容 |
|---|---|
| **焦段** | 85 / 50 / 35 / 24 / 135，每个带**透视说明** |
| **光圈** | f/1.8 → f/8，说明「越小越写实」 |
| **快门** | 1/2000 → 1/30，说明「慢快门能拍出旋转的过程」 |
| **⭐ 白平衡** | **光源色温 + 相机设定 两个下拉 + 相反警告** |
| **⭐ 光质** | 硬光 / 柔光 / **不确定**，配「看影子边缘」的判据 |
| **布光** | 双灯示意（主光 + 造型光 + 光比），可折叠 |

**白平衡那块的警告原话**：
> ⚠️ **这两个数字是相反的** —— 光源越暖 K 越小；相机里的 K 越小，画面反而越冷。
> 只记一个，回来复现不了。

**光质的判据**：
> **判据**：看鼻子在脸上的影子 —— **边缘像刀一样**是硬光；**没有边缘**或过渡均匀是柔光。
> 拿不准就先选「不确定」，到现场看一眼再改。

### ② ⭐ 后期交接 Tab

**这是课程里反复出现的现象 —— 拍的时候的想法，到修图时就忘了。**

| **已经知道要修的** | 「脸部逆光偏暗，要提亮但别丢轮廓」 |
| **客户/模特提过的要求** | 「不要太磨皮」（小林第 3 次说了） |

### 平方根归一化

```js
const mx = Math.sqrt(Math.max(...hist));

```

## 43.5 新增四个参数（影调分离）

课程里讲「看直方图判断高光溢出」，但**曝光是拉整张**，压不住单独的高光。
所以补上：

| 参数 | 范围 | 作用 |
|---|---|---|
| **高光** | -1 ~ +1 | 只动亮部（权重 = 亮度²） |
| **阴影** | -1 ~ +1 | 只动暗部（权重 = 暗度²） |
| **清晰度** | -1 ~ +1 | 中间调加 S 形，不碰两端 |
| **色调** | -1 ~ +1 | 负=偏绿，正=偏品红 |

**实现**（`leToneMap`）：
```js
// 高光：权重随亮度平方增长
v += highlights * 0.28 * (v*v)
// 阴影：权重随暗度平方增长
v += shadows * 0.28 * ((1-v)*(1-v))
// 清晰度：中间调权重 × S 形
v += clarity * 0.16 * sin((v-0.5)*π) * (1 - |v*2-1|)
```

**顺序**：影调 → 色阶 → 曲线。
因为影调解决「哪一段亮」，曲线解决「怎么改」。

| 参数 | 谁用 |
|---|---|

# 四十八、v41：修两个真问题（裁剪没反应 / 采纳后参数不变）

> 用户：「两个问题。点裁剪没反应 应该预览吧。

## 48.1 ⚠️ 问题一：点裁剪没反应

### 根因：我自己的全屏 CSS 用 `!important` 压掉了 JS

`leApplyCrop()` 里是这么写的：

```js
img.style.aspectRatio = String(r);
```

但我在改全屏时加过这条：

```css
.le-body3 .le-img{ aspect-ratio:auto !important; }
```

**`!important` 的 CSS 规则 > inline style** —— 所以 JS 设了也被压掉。

### 修法：改成走 `data-crop` 属性

```js
img.dataset.crop = LOCAL_ADJ.crop;   // 只设属性，不设 inline
```

```css
.le-body3 .le-img[data-crop="1:1"]{ aspect-ratio:1/1 !important }
.le-body3 .le-img[data-crop="4:3"]{ aspect-ratio:4/3 !important }
.le-body3 .le-img[data-crop="3:4"]{ aspect-ratio:3/4 !important }
.le-body3 .le-img[data-crop="16:9"]{ aspect-ratio:16/9 !important }
.le-body3 .le-img[data-crop="9:16"]{ aspect-ratio:9/16 !important }
/* 裁切时用 cover，才像真的裁过 */
.le-body3 .le-img:not([data-crop="原图"]){ background-size:cover !important }
```

### 实测

| 比例 | 图片实际尺寸 |
|---|---|
| 1:1 | **640 × 640** |
| 16:9 | **640 × 360** |

**之前点哪个都没反应，因为 CSS 一直压着。**

## 48.2 ⚠️ 问题二：采纳后右边参数没变

### 根因：图层参数和滑块是两套东西

- 采纳建议 → 参数进了 `LE_LAYERS[i].p`
- 右边滑块显示的是 `LOCAL_ADJ`（基础参数）

**两者从来没打通。** 所以图片变了，滑块还停在 0。

### 修法：选中图层，滑块就调它

**这是 Photoshop / PhotoMaster 的做法** —— 选中哪一层，面板就显示哪一层的参数。

```
右栏顶部：正在改：整体提亮，背景压暗，拉开层次   ← 青色高亮
         [← 回到基础参数]

曝光  ▬▬▬●▬▬▬  +0.20EV      ← 这就是那个图层的参数
对比  ▬▬▬●▬▬▬  1.06
高光  ▬▬●▬▬▬▬  -0.12
阴影  ▬▬▬▬●▬▬  +0.18
```

**关键实现**：

```js
function leSetTarget(){
  if (LE_SEL_LAYER >= 0 && LE_LAYERS[LE_SEL_LAYER]) return LE_LAYERS[LE_SEL_LAYER].p;
  return LOCAL_ADJ;
}
// leSet 里：
const t = leSetTarget();   // ← 有选中图层就改图层，没有就改基础
t[key] = Number(v);
```

配套改动：

| 改动 | 效果 |
|---|---|
| **采纳时自动选中新图层** | 点「采纳」→ 右边立刻显示它的参数 |
| **图层行可点选中/取消** | 点哪层就调哪层 |
| **图层行显示「改过」徽章** | 知道这层被你动过 |
| **「← 回到基础参数」** | 退回调全局 |
| `leNormP(p)` | 采纳时把参数补全默认值，滑块不会有空值 |

### 实测

| 项 | 结果 |
|---|---|
| 采纳前滑块 | 曝光 0 · 对比 1 · 高光 0 · 阴影 0 |
| **采纳后滑块** | **曝光 0.2 · 对比 1.06 · 高光 -0.12 · 阴影 0.18** ✓ |
| 右栏标题 | 「正在改：整体提亮，背景压暗，拉开层次」✓ |
| 拖滑块 | 写进 `LE_LAYERS[0].p`，**基础参数不动** ✓ |

## 48.3 ⚠️ 过程中还踩了一个正则的坑

`leSyncPanel()` 里要读出滑块的参数名，我写的是：

```js
.match(/'\\\\(\\\\w+\\\\)'/)   // ← 错
```

**Python 里多转义了一层，到 JS 变成 `\\(` 和 `\w` 的字面匹配**，
永远匹配不上 → 滑块值一直不更新，而且**不报错**。

改成：

```js
.match(/'([a-zA-Z]+)'/)
```

**教训**：Python 写 JS 正则时，`\\` 的数量要数清楚；
配套的办法是**改完立刻在浏览器里 `console` 验证一次**，别只看代码。

## 51.7 客人视角判断

|---|---|

| 第一张就够吸引人吗 | 封面定生死 |

下面给总结：「N 项悬着 · 拍之前补拍几张保险的」/「N 项都稳 · 基本不会被退」。
