# 2026-10-11 动图（motion GIF）能力：可行性验证与后端落地

## 为什么做这件事

用户提出能否把外部项目 `liangdabiao/product-motion-gif` 的"GIF 动图生成"能力
接进 YLCraft 的 AI 生图。经查证该项目的原理是：

> 让图像模型**一次性生成多格图（frame sheet）**，再切帧合成 GIF。

不是逐帧生成视频。这个区别决定了整套设计。

## 可行性验证（用真实模型跑通）

连接器：`不明中转站-gpt-image-2`（`/v1/images/generations`）与
`不明中转站- Image-2 Edit`（`/v1/images/edits`，multipart）。

⚠️ **本机 DNS 故障（与代码无关）**：Wi-Fi 只配了路由器 `192.168.18.1` 做 DNS，
该 DNS 一直超时，`socket.getaddrinfo` 直接 `[Errno 11001]`。而连接器刻意写了
`trust_env=False`（`backends/image/openai_sdk.py:64`，注释说明是为绕开失效的系统代理），
于是只能走坏掉的系统 DNS → 必然 `APIConnectionError`。验证时用 DoH 兜底补丁临时绕过。
**根治要把 Wi-Fi DNS 改成 `223.5.5.5` / `119.29.29.29`（需管理员权限，未执行）。**
判定这类问题时要记住：**"接口能返回数据" ≠ "我们能调它"**。

### 三轮实验：格数是关键变量

同一提示词（青瓷茶壶相机环绕），只改格数：

| | 4×4（16 格） | 4×4（改 prompt） | **2×4（8 格）** |
|---|---|---|---|
| 换行跳变 / 行内 | 1.33x | 1.17x | **1.05x** |
| 相邻格差异**最大值** | 9.30 | 4.53 | **4.66** |
| 首尾差异（转动幅度） | 12.51 | 7.43 | **17.05** |
| GIF 体积 | 2707 KB | 2629 KB | **1403 KB** |

**结论：8 格（2×4）最好**——换行跳变基本消失（1.05x ≈ 无）、转动幅度反而最大、体积小一半。
原项目能用 16 格是因为它用 `gpt-image-2.5`；`gpt-image-2` 不行。

### 一次诊断失误（记录下来）

我最初量到"换行处差异最大（6.19/9.30/4.93）"，据此断言"模型把 16 格当成 4 行独立环绕"。
**这个推断证据不足**：v1 的**行内**差异本来就有 9.30 那么大（第 7→8 格），
换行跳变 5.60 只比行内平均 4.22 高 33%，根本不算异常。真实情况更像是整张图存在不规则抖动。

第二轮"加禁止每行重开"的 prompt 确实把跳变压下去了（1.17x），但**转动幅度也几乎归零**
（跨度 0.014，等于没动）——用平稳换掉了转动，是笔亏本买卖。**减帧（第三轮）才是对的方向。**

### D 类（表情包）实测：表现远好于 A 类

输入蓝狗角色图（带 alpha），走图生图，16 格只变表情、机位锁死。
**换行跳变比 0.73x**（比行内还小）、五段节拍全部命中、身体背景未变形。

**这说明模型擅长"局部变化"、不擅长"整体视角变化"**：表情包只需面部局部变 + 全身锁死；
相机环绕要求维持 16 格的三维几何一致性。对实际用途是好消息——
**表情包、角色动作这类"机位不动"的需求，这个模型完全够用。**

### 补做的两处（初版遗漏）

- **上传补位传像素**：`POST /motion-gif/upload-frame`（multipart，按 owner 分目录，
  只接受 png/jpg/jpeg/webp，20MB 上限），返回上传序号；合成时 `_load_uploads`
  只读 **order 里真正被引用**的那些（用户传了又删的不参与）。
- **动图落库**：`AssetHubFacade.create_motion_gif` —— **一个动图 = 一个 AssetNode**
  （列表只占一行），`slice_config` 存进 `AssetVersion.params_json`
  （帧顺序/删了哪些格/循环/尺寸），多格图作为同一版本下的一个 representation
  （`format="framesheet"`）—— 这样「关掉页面再回来改切帧重出」才有依据。
  `POST /motion-gif/save` 是**合成 + 入库**一步（用户不用先合成再手动存）。

**公共组件的原则**：基础功能做通用，高级功能复用。切图逻辑原先焊在
`api/v1/characters.py:1279`（立绘九宫格）里，直接做动图就会产生第二份。
`slice_grid` 只负责几何切分，"删格/补图/调顺序"的语义由 `resolve_frames` 收口——
**各写一份必然漂移**。立绘尚未迁移（先做动图、验证后再迁，避免为"通用"先把能跑的功能改坏）。

## 开发中踩的坑

1. **背景掩膜阈值太低**。影棚背景是**渐变**的，阈值 40 会把整片背景判成主体，
   `getbbox()` 退化成整格、裁切失效（2×4 的 256×512 格被整块保留）。改 70 才稳。
2. **裁切框必须夹回图内**。不夹会得到负坐标，把**相邻格**卷进来（实测裁到 -132 就把左边那格吃了一半）。
3. **体积阶梯不能拿上一档的结果继续降**。必须每档都从同一批原始帧重新缩放，
   否则是二次有损、越降越糊。
4. **`autoSlice` 重复定义**覆盖了真实现——JS 里同名函数后者胜出，"保留上传图"直接失效。
5. PowerShell 的 `Set-Content`/`-Raw` 会把 UTF-8 中文测试文件写坏（`SyntaxError: invalid
   non-printable character`）。**改含中文的文件要用 Python 或编辑工具，不要用 PowerShell 重定向。**
6. **`useTheme()` 返回 `{ theme }` 不是 theme 本身**。直接 `const theme = useTheme()` 会
   拿到 context 对象，`theme.primary` 全部类型报错。正确写法 `const { theme: THEME } = useTheme()`。
7. **`Text` 在 image-gen 里没导入**。这个页面原本只用 `TextArea`，加文案时直接写
   `<Text>` 会报 "cannot be used as a JSX component"。

## 端到端实测发现的 bug

1. **切帧面板在还没生成多格图时就显示「已删 8 格」**。
   `dropped = cells - order.filter(origin).length` 在 `order` 为空时算出 `8 - 0 = 8`，
   用户会以为自己删过。空序列一律不报删除数。

2. **上传补位只记引用、没传像素**（初版）。`MotionGifSlicePanel` 只往 order 里加
   `{kind:'upload',index:n}`，**文件没给后端**，切帧预览与合成都取不到图。
   补 `POST /motion-gif/upload-frame`（multipart，返序号），前端改成**先传文件再写 order**。

3. **合成成功但一个表示都没入库**。`MotionGifService.representations()` 返回的是
   **相对项目根**的路径（`backend/app/storage/...`），而进程 CWD 通常是 `backend/`。
   入库侧若直接 `Path(x).exists()`，每个表示都被判成"文件不存在"→ 全部跳过 →
   **HTTP 200 + success=false +「动图没有任何可入库的产物表示」**。
   修法：入库侧一律经 `resolve_asset_file()` 还原（与全项目同一约定）。
   已加回归测试 `TestRepresentationPathsAreResolvable` 钉住。

4. **无名标签**。`tags=["ai-generated","motion-gif",provider,model]` 里 provider/model
   可能为空，会写进标签表产生一个**空名标签**，素材库筛选里既没意义又占位。已过滤空串。

### 关于「标签在 `tags_json` 里是空的」

实测 `AssetNode.tags_json == []`，但 `AssetNodeService.get_tags()` 能查到
`['ai-generated','motion-gif']`。**这不是本次改动引入的**：`node_service.create()`
本来就只写关联表（`AssetTagLink`），`tags_json` 一直是空数组，
`get_tags_map` 的 docstring 明确记了这个不一致（"素材库按 rigged/animated 筛选
一条都查不到"）。本次沿用既有写法，未改动该行为。

## 用户实测发现的三个问题（2026-10-11 晚）

用户跑通后在「AI 优化」弹窗上发现三点，**全部确认成立**：

### 1. 模型下拉显示厂商名 → 出现多个一模一样的「OpenAI」

前端 `llmBackends.map(...)` 用 `label: item.provider_label || item.name`，而
`provider_label` 是**厂商**标签。同一厂商可以有多份配置（用户数据里 `本地反代` 与
`OpenAi` 都属 openai），于是下拉里出现多个「OpenAI」，用户分不出选的是哪个。

模型管理页写明「**模型是用户实际选择的 AI 配置项**」，所以要区分的是**配置名**。
改为 `配置名（厂商）`，并按配置名去重。

### 2. 优化请求根本没带图（用户的怀疑成立）

`runOptimize` 只传 `prompt / instruction / provider / model`，**没有 reference_images**。
而 `services/ai/types.py` 的 `LLMMessage.content` 本就支持多模态数组
（`content_package_planner.build_outline_messages` 有现成写法），连接器也早有
`support_vision_input` 字段（用户截图确认 `space-bunny` = 是）—— 只是没接上。

已接：图生图/动图下按**勾选顺序全传**，上限 6 张；**不支持视觉时静默降级**为纯文本
而不是报错（用户只是选了别的模型，不该因此整单失败）。

### 3. 优化结果和动图无关 —— 这是**逻辑冲突**，最严重

日志证实请求打到 `/api/v1/images/optimize-prompt`，该接口不知道动图存在，
`runOptimize` 也没传 `motion_gif`，于是 AI 按**静态图**思路产出：

> 一只蓝色狗狗神情疲惫…呈现"今天只想摸鱼"…高清细节，8K、高质量。

**完全没提要画 8 格、要连贯。** 更糟的是：应用该结果后前端标记 `optimized=true`，
于是**不再追加那 5 段系统技术规则**（含"画成 2×4 共 8 格""相邻两格变化量相同"等硬约束）
—— 结果是**既丢了多格图要求，又丢了技术约束**。

已修：传 `motion_gif={motion_kind, rows, cols, cells}`，后端拼
`MOTION_GIF_OPTIMIZE_SYSTEM` 进 system prompt；动效写法提示直接取
`services/image/motion_prompt` 的同一份规则，保证"优化时说的"与"实际追加的"不漂移。

### 补开发中踩到的坑

8. **我构造的 `messages` 变量压根没被用上**。`optimize_image_prompt` 里先构造了
   含多模态 content 的 `messages`，但 `ai.chat()` 仍传原来硬编码的两条消息 ——
   新逻辑一行都没生效。是测试（读 `captured["messages"][0].content`）暴露的。

9. **`_motion_rule_zh` 引用私有函数且签名不对**。`motion_prompt._motion_rule_zh`
   需要 `GridSpec` 参数且是下划线私有。改为从 `grid_spec()` 取，并按实际行列构造
   （环绕类角度步长依赖格数，8 格与 16 格不同）。

10. **`restoreAutoSlice` 让上传图反复累加**（用户发现：点一次格子右边就一直多）。
    它会被"生成完成""切换排布"多次调用，而"生成完成"传的 `order` 可能**本身就是
    该函数的结果**（里面已含上传图）—— 原实现无脑 append，于是同一张被反复追加。
    改为**按上传序号去重**。

11. ⚠️ **PowerShell 的 `Set-Content -Encoding UTF8` / `Get-Content -Raw` 往返会写坏
    含中文的文件**。本轮把 `frontend/src/pages/image-gen/index.tsx`（2000+ 行中文注释）
    搞成 GBK mojibake，**注释与后面的 `import {` 粘成一行**，tsc 报 20+ 语法错误。
    `git stash` 也会把坏文件一起带走。**正解：只用编辑工具改文件**；
    必须用脚本时用 Python 显式 `encoding='utf-8'`，**不要用 PowerShell 重定向**。
    恢复办法：`git checkout -- <file>` 后用编辑工具重做（编辑工具不会产生 mojibake）。

12. **生成完多格图，切帧面板一直显示「没有可用帧」、合成按钮根本不出现**
    （用户实测发现）。根因不在渲染，而在 `appendGeneratedImages` 的 `useCallback`
    依赖数组是 `[mode, navigate]` —— **漏了 `motionGifOn` / `motionGifLayout`**。
    该回调在首次渲染时就把 `motionGifOn=false` 记下了，之后打开开关它**不会重建**，
    于是 `if (motionGifOn && newImages.length)` 永远为假 → 候选池一直是空的。

    这是 `useCallback` 依赖漏项的典型危害：**代码读起来完全正确、tsc 也过，
    运行时静默失效**。同步与异步两条生图路径都汇聚到这个回调，所以两条都中招。
    修法：把 `motionGifOn / motionGifLayout / motionCandidates / motionPickedIndex`
    补进依赖数组。

    **教训**：凡是新增会影响 `appendGeneratedImages` 内部分支的 state，
    都必须进它的依赖数组；这类漏项不会报错，只会"什么都没发生"。

13. **空态文案是死胡同**：「没有可用帧」像"你切坏了"。改成明确的下一步指引。

14. **把"生成"当成了切图的唯一入口**（用户纠正）。
    原设计里切帧面板只有"刚生成完"才有格子，于是：
    - 已经生成过、想**重新切一次** → 做不到；
    - 想从**素材库挑一张现成分格图**来切 → 做不到；
    - 面板长期停在"没有可用帧"的死状态，用户没有下手处。

    改为 `MotionSheetSourcePanel`：**生成 / 从素材库选 / 上传** 三条**平级**入口，
    产出同一种东西（待切分图路径），后面的切帧与合成完全一致。
    **切图是独立能力，不以"刚生成"为前提。**

    配套：排布选择弹窗支持预设（2×4 / 4×4 / 1×4 / 3×3）与**自定义行列**；
    素材库选图复用既有 `AssetReferencePicker`；上传复用 `upload-frame` 端点
    （**不能直接传 data URL** —— `resolve_asset_file` 对 `data:` 直接返回 None，
    切帧/合成都在后端跑，前端预览用的 data URL 后端取不到）。

15. **切完没有预览**（用户反馈）。切帧面板只回「尺寸 + 来源标签」，前端只能渲染
    8 个**黑框** —— 用户无法判断切得对不对、主体有没有对齐，只能盲合成一次再看成品。
    改为：`slice-preview` 与 `compose` 都把每帧存成小图（长边 ≤240）并回
    `frame_urls` / `frame_paths`，前端直接显示真实像素。存 PNG 是本地文件操作，不花钱。

16. **「gif 主体上下位置不同」**（用户反馈）。根因：`apply_global_crop` 用的是所有帧的
    **并集**包围盒 —— 裁切框统一、尺寸一致了，但**主体在每格里的位置仍然不同**
    （图像模型不保证主体在每格中居中），于是主体在画面里上下跳动。

    新增 `slicing.align_frames_by_content`：按每帧自己的内容 bbox 把主体**平移**到画布
    中心。**只平移不缩放** —— 缩放会引入插值糊化，而位置抖动靠平移就能解决。
    实测（合成一张每格依次下移 12px 的图）：纵向跳动 **84px → 17.5px**。
    做成 `align_subject` 开关（默认开），代价是背景横向补边，对复杂背景可见。

    容差踩坑：`content_bbox` 的右/下边界是**开区间**，一个正好居中的偶数尺寸主体

18. **删了格、重新合成，下载到的还是旧文件**（用户反馈）。

20. **黑边（用户反馈"有黑边"）—— 两个不同的原因，只有一个是 bug**。

21. ⚠️ **对齐的平移方向是反的**（修黑边时顺带发现）。

22. **公共组件的边界没划干净：立绘切图还在自己写 `image.crop()`**（用户提问）。

    与 `slice_grid` 的整除**算法不同** —— 同一张 1024px 图两种切法结果可能不一致。
    已改为调用 `slicing.slice_grid`。
    原则照旧：**基础功能做通用一点当公共组件，然后给高级功能用。**

23. **手动切格：为什么做"规整网格 + 可拖分割线"而不是自由框**（用户问，我给的理由）。
    自由框更灵活，但要处理任意重叠、任意大小的框，交互立刻变得难懂
    （"这两格为什么叠一起了""这里为什么有个洞"）。规整 rows×cols 只让**分割线
    可拖**，拖一条线相邻两格同时变形，符合直觉，且**不可能出现空洞/重叠**。

24. **`_normalize_edges` 的夹紧不能用 `min/max` 硬压**（实现踩坑）。
    两条线拖到重合时 `min(1, max(0, v))` 夹不出严格递增 —— 格子宽度会变成 0，
    而"严格递增"是画框的前提。必须**在撞上时向前推**一点。
    但推的量要小（`1e-6`）：一开始推 `1e-4`，实测把用户拖到 `0.5` 的线变成
    `0.5001`，肉眼无意义却会让"拖出来的比例 ≠ 显示的比例"。
    → **只在真的撞上时推开，正常值原样保留。**

25. **回传 `grid_edges` 会造成无限刷新循环**（前端踩坑，逻辑读起来完全正确）。
    `refreshMotionFramePreview` 的 `useCallback` 依赖里有 `motionGridEdges`，
    而函数体里 `setMotionGridEdges(data.grid_edges)` —— 后端每次回传一个新对象，
    引用一变就重新拉 → 重新拉又写新对象 → **死循环**（肉眼是面板一直转圈）。
    解法：**比较后再写**，值没变时返回原引用（`setState` 传同一引用不触发更新）。
    这是"把服务器修正值写回自己依赖的状态"的**固定陷阱**，凡是 XHR 结果写回
    自身依赖的状态都要这么写。

26. **每帧微调只做像素级，明确不做重画**（设计取舍）。
    亮度/对比度/饱和度/色相/旋转 —— 零模型调用、零费用，能解决"某格偏亮导致闪烁"。
    重画/扩图/换背景会**花钱且可能与其它格对不上**（光照角度笔触都会变），
    所以做成面板里一个**单独的跳转按钮**，不塞进滑块区，免得工具栏变成大杂烩。
    用户选择"内嵌右栏"而非跳转，也是同一个判断：微调是高频轻操作，
    跳转是低频重操作，两者不该混在一起。

27. ⚠️ **可拖分割线的第一版直接把用户卡死了**（用户实测：`切帧预览失败：
    单格尺寸过小：0x0 像素 (2x4 切 1024x1024)`，8 格全停在"预览生成中…"）。

    复现后根因不在切法，在**边界数组的两种写法没对齐**：
    - 前端 `uniformEdges` 与 `slice-preview` 回传的都是**含两端点**的
      `[0, 0.25, 0.5, 0.75, 1]`（`cols+1` 个）；
    - 后端 `_normalize_edges` 按**只含内部线**读，于是把开头的 `0`
      当成第一条内部线 → **第一格宽度直接塌成 0**。

    链子是"回传 → 存 → 再发回"形成的：首次生成走的是均匀路径所以没事，
    一旦前端把回传的值存下来再发，就必挂。**这类 bug 只在第二次操作后出现** ——
    单元测试若只用 `SheetGrid.uniform()` 构造输入，就永远测不到。

    修法：`_normalize_edges` 同时接受两种写法（长度 ≥ `count+1` 视为含两端点、
    去掉首尾）。已加参数化测试覆盖 6 种排布 + **幂等性**（回传→再发回必须不变）。

    连带修掉一个**我一开始搞错的方向**：原先每次都做 `max(v, prev + 1e-6)`，
    会把 `[0, 0.5, 1]` 推成 `[0, 1e-6, 1]`，**均匀的那份也照样塌**。
    正确做法是**只在真的撞上时推开**（`if value <= out[-1]`），正常值原样保留。

    **教训**：凡是自己存下来、之后再原样发回后端的结构（边界、坐标、参数），
    必须能吃下**自己输出的那种格式**，并测一次"来回传不变"。

34. ⚠️ **从图片编辑器跳回来，页面回到"刚打开"的样子，辛苦调的切法全丢**
    （用户实测，本批最严重的一个）。截图里"已替换 1 帧"的提示挂着，但页面上
    什么都没有 —— 因为它是**往一个空序列里替换**。

    根因：`/image-gen` 是**路由页**。跳到 `/image-editor` 再跳回来是
    整个组件**重新挂载**，所有 `useState` 归零 —— 待切分图、帧顺序、
    拖过的分割线、调过的颜色、素材库节点 id 全没了。

    这不是"顺手修个 bug"，是**设计时漏掉的一层**：凡是有"跳出去再回来"
    流程的页面，编辑态就必须能跨挂载存活。新增 `motionDraft.ts`：
    - 用 **sessionStorage** 存（不是 localStorage）：这份状态属于"我正在编辑
      这一张图"，是一次会话的事。localStorage 会让明天打开生图页时看到昨天
      那半张图还挂着，反而像 bug。
    - **不存** `motionFrameUrls` 与 `motionOutput`：小图和成品都是后端产物，
      回来重切/重合成即可（不花钱），而存下来的 URL 会指向**已被原地覆写**的旧文件。
    - 只在**主动关掉动图开关**时才清草稿：否则空状态也会被写进去覆盖好草稿。
    - 各 `useState` 用 `useMemo(() => loadMotionDraft(), [])` 的结果当初始值 ——
      必须只读一次，否则每次渲染都从存储里读，用户改什么都改不动。

    连带修掉一个**误导性提示**：帧下标越界时原来**静默跳过**，
    但"已替换 N 帧"的提示照发 —— 用户看到"替换成功"而画面没变。
    现在分开报：真换上了才说成功，越界/上传失败如实说没换上。

44. 🔴 **框架级 bug：`get_async_session` 会把已写入的数据回滚掉**（本轮最严重）。
    用户反馈"素材库还是没有新入的动图"。用浏览器 skill 实测时发现更精确的现象：
    **接口返回 `success: true` 并给出 `node_id`，但数据库里没有这条记录**。

    根因在会话上下文管理器的"是否需要 COMMIT"判据：

    ```python
    # ❌ 旧代码（app/db/database.py）
    if not (session.new or session.dirty or session.deleted):
        await session.rollback()
        return
    ```

    `session.new/dirty/deleted` 是 **ORM 的变更跟踪集合**，而 **`flush()` 会把
    对象从这些集合里挪走**（写进事务、变成 persistent）。服务层普遍是
    `session.add(obj)` 紧跟 `session.flush()` —— 退出时三个集合**全空**，
    被判成"没有写入" → **`rollback()` 把数据丢掉**，接口照常返回成功。

    实测证据：`new=0 dirty=0 deleted=0` + `AFTER context exit: rows in DB = 0`；
    改成 `in_transaction()` 判据后同一次探针变成 `rows in DB = 1`。

    **危害面**：这是**所有走 `get_async_session()` 的写路径**的公共依赖 ——
    全仓 **129 处调用**。判据错一次，每一处写入都可能静默丢失，
    而且不报错、不抛异常、日志干净。**它不是我引入的，但正好被这个功能撞上。**

    **修法**：判据改为 `session.in_transaction()`。`flush()` 会开启事务、
    只读查询不会 —— 既保住"只读不发 COMMIT"这个优化，又不会丢写入。

    **验证**：新增 `tests/test_db_session_commit.py`（6 条），用内存 SQLite 自建引擎
    （不依赖远程 PostgreSQL）。含一条**静态守卫**，直接读生产实现源码断言
    判据是 `in_transaction()` 且没有退回 `new/dirty/deleted` —— 反向验证过会红。

    容器宽度不变、边界数组格式统一、setState 更新函数可以放副作用、所有帧同尺寸。
    **下次改这类"多步骤 + 多层数据流"的交互，先把每层的前提写下来核对一遍。**

49. 🔴 **真正的根因：预览小图 URL 不变 → 浏览器一直用旧位图**（用户："还是没反应"）。

    第 48 条修完尺寸逻辑后，**用户仍然看不到变化**。用浏览器实测逐层排查：

    | 层 | 事实 |
    | --- | --- |
    | 后端返回的格尺寸 | `378 / 134`（正确，已非均匀）✅ |
    | 磁盘上的缩略图 | `177×240 / 63×240`（正确）✅ |
    | **页面上 `<img>` 的 naturalWidth** | **120×240（旧的！）** ❌ |
    | 手动刷新页面后 | `177 / 63`（正确）✅ |

    **关键线索是"刷新一次就对了"** —— 典型缓存问题。

    根因：切帧预览目录是按**多格图路径**派生的（`sheet-<hash>`），
    所以每次改切法都**原地覆写同一个 `frame_02.png`** —— **URL 一个字都不变**。
    浏览器（以及 React 复用的 DOM 节点）完全有理由继续用旧位图。

    修法：给预览小图 URL 加**内容指纹**（`?v=<指纹>`）。
    指纹取"每帧尺寸 + 来源标识"的组合：
    - 切法/删格/换顺序 任一变化 → 指纹变 → URL 变 → 必然重新加载
    - **同一切法得到同一 URL**（不用时间戳），避免来回切时堆无意义缓存

    前端另外把图片地址并进 React `key`，让地址一变就重建节点。

    **实测确认**（浏览器，全程不刷新）：
    - 点「重置网格」：帧从 `231/9/40/200` 变成 `120/120/120/120` ✅
    - 拖动 + 确认：帧变成 `183/57/120/120` ✅

    ⚠️ **排查教训**：这次走了两个弯路 ——
    ① 先入为主怀疑"前端没重新渲染"，其实**接口返回的数据一直是对的**；
    ② 一度用 `fetch(..., {cache:'reload'})` 验证，拿到的是**正确的新图**，
    于是误判"缓存没问题"——但 `fetch` 和 `<img>` 走的是**不同的缓存路径**，
    **不能用 fetch 的结果证明 img 没被缓存**。
    **正确做法：直接读 DOM 上那个 `<img>` 的 `naturalWidth`**，与磁盘/接口对照。

51. ⚠️ **"改了循环重新合成，预览没变"**（用户实测）—— **我上次只修了一半**。

53. **提示词块改为可编辑**（用户选的 B 方案）+ 修两处规则内容问题。

    ## 用户的两个原始诉求

    > "我发现表情包写死了动作不能动，但实际我们用表情包时候是有动作的，只是主体不变"

    > "提示词这个不能修改了吗"

    ## 修的三件事

    **① 提示词块可编辑**：`block_overrides: {id: 新文本}`，空串=关掉。
    后端 `apply_block_overrides()`（用 `dataclasses.replace`，**不改原对象** ——
    否则「恢复默认」拿不回原文）。前端每段一个 `Input.TextArea`，
    带「已改 / 默认」标记、「恢复默认」链接、以及默认文案提示。
    改动跟着草稿跨页保存（`rememberMotionBlockSettings`）。

    **② 表情包允许小动作**：原文"除了表情，画面里任何东西都不变"
    → 改为"表情为主线，**允许小幅肢体/尾巴/耳朵动作**，
    但不得改变主体身份特征与整体轮廓"，同时保留机位锁死。

    **③ 修「8.571 度」串味**（本轮的额外发现）：
    `motion_prompt` 的**连续性段落四类共用一句**"每格约 8.571 度" ——
    那是 `60° ÷ 7` 算出来的**相机环绕专用**数值。表情包要求"机位完全锁死、
    任何东西都不变"，却又被告知"每格要转 8.571 度"，**自相矛盾**。

    修法：给 `MotionKindSpec` 加 `change_zh` / `change_en`，每类有自己的度量 ——
    环绕用角度、角色动作用姿态幅度、速度型用位移量、表情包用表情强度。
    **表情包那条还特意补了"脸的位置、大小、朝向全程不动"**，与机位锁死一致。

    - 改第 2 段 → 出现「已改」标记 + 「恢复默认」+ 默认文案提示 ✅
    - 改后的文字**出现在底部最终提示词里** ✅
    - 接口层：自定义段进了 prompt、被关的段没出现、`edited` 标记正确、
      `default_texts` 正常返回 ✅

    回归 15 条（含"四类度量必须各不相同"与"非环绕类不得出现角度数值"）。
    反向验证过：把度量改回共用一句，测试立刻红。

    ⚠️ **测试断言写太粗会误报**：第一版用"含『度』字"判断有没有角度，
    结果 `幅度`（amplitude）天然带一个"度"字 → 误报。
    改成用正则匹配 **数字+度**（`\d+\.?\d*\s*度`）才是对的判据。

54. 🔴 **从素材库选图后切帧报"多格图不存在"**（用户实测：`c475e739-da29-…`）。

    **把 assetId 当文件路径传了。** `AssetReferencePicker` 有两种模式：
    - **base64 模式**：`url` 是空串，**只给 assetId** —— 那是给**生图**用的，
      生图接口自己会解析 assetId；
    - 来源 URL 模式：给真实 url。

    而动图的 `slice-preview` 走 `resolve_asset_file`，**只认文件路径与
    `/api/v1/assets/download?path=` 这类地址**，不认 assetId。

    我当时的注释还写着"用它的 id 让后端解析成本地文件" ——
    **那个假设是错的**：能解析 assetId 的是生图端点，不是切帧端点。

    修法：前端先 `getAsset(id)` 拿 `file_path`（实测返回
    `backend/app/storage/images/20261013_183855_….png`），再传给切帧。
    回退顺序 `真实 url → 详情 file_path`，两者都没有就明确报错。

    **实测确认**：解析出的路径能正常切开（`slice-preview` 返回 200、
    4×4 每格 256×256）✅

    回归 1 条，把"**后端确实不接受 assetId**"这个前提钉住 ——
    万一以后有人把前端改回去，这条能说明原因。

    **教训**：*"同一个后端会解析 X" 不能想当然推广到另一个端点。*
    这次是"生图能解析 assetId" → 误以为"切帧也能"。**跨端点复用参数前，
    要看那个端点的解析器实际接受什么。**

55. 🔴 **"调帧以后预览怎么生效"**（用户实测提问）—— 又是缓存，这次漏的是 `adjust`。

    第 49 条给切帧预览加了 `?v=<指纹>`，但**指纹漏了 `adjust`**：

    ```python
    # ❌ 旧：只取尺寸 + 来源
    f"{f.width}x{f.height}:{r.kind}:{origin}"
    ```

    而**调色不改变尺寸**（亮度/对比度/色相都是原地变换）—— 所以调完亮度，
    指纹一个字没变、**URL 完全相同**，浏览器继续用旧缩略图：
    **用户滑完滑块看不到任何变化**（后端其实已经重切好了，实测像素均值
    203.5 → 80.9）。

    **实测复现**：同一个 `output_dir` 下，调色前后 URL **完全相同**。

    修法：把 `adjust` 编进指纹（**排序后拼接** —— 参数字典的书写顺序不该影响指纹，
    否则同样的调色会得到不同 URL，白白失效缓存）。

    实测（浏览器）：`v=cdb3dc9b7138` → `v=80b1e68d51b5` ✅

    回归 4 条：调色要换 URL、改数值要换 URL、同参数要稳定、键顺序不影响指纹。
    反向验证过会红。

    ⚠️ **这是同一个指纹我漏了两次**：
    第一次漏了 `adjust`（本条），上一次漏了整个成品（第 51 条）。
    **教训：给缓存指纹列输入时，要按"哪些输入会改变输出像素"逐个过一遍，
    而不是只列自己当下想到的那几个。**
