## 一、OhMyGame vision.md —— 为什么推翻旧模型

### 1.1 旧模型的毛病（原文）

> 「**We decided what a screen can be.** 一旦作者想要分类没预料到的东西，
> **工具就停止帮忙了**。」

旧模型有 10 种固定节点类型：Start / Open UI / Scene / Interaction / Choice /
Ending / Story Map / Settings / Condition / Update State，
「每种有自己的表单、规则和播放器界面」。

### 1.2 🔴 两个真实案例（重构的直接触发因素）

**案例 1：主菜单**
> 「这不是"菜单类型"，**它是一个被设计过的页面**：像素字体的时代标题、副标题、
> 四个各有规则的入口、一段说明、深色建筑背景。
> ……固定的 Open UI 节点**能近似一排按钮，但不能让作者发明这个界面**。」

**案例 2：档案页**
> 「档案是桌上摊开的书。右页是案件索引，选中会改变左页。左页显示**取决于玩家做过什么**
> 的记录……这个屏幕**混了旧模型拆成多种类型的东西**：
> 屏内换页、依赖进度的内容、出口、每屏都有的导航。
> 用固定分类做，**要么把一个自然屏幕拆成几个节点，要么放弃交互**。」

### 1.3 案例共性（整份文档的关键洞察）

> 「作者要的不是新的节点类型。他们要的是 **网页的自由**，加上项目素材，
> 以及一个清楚的方式说明 **玩家下一步能去哪**。」

### 1.4 🔴 为什么是"托管节点"而不是一个大网页游戏

| # | 理由 | 原文 |
| --- | --- | --- |
| 1 | **流程可见** | 「图能回答"玩家怎么到这儿的"，**不用读代码**」 |
| 2 | **Agent 在小上下文里工作** | 「改档案只碰档案，不碰主菜单。**更小的上下文产生更好的结果和更少的意外回归**」 |
| 3 | **工作可增量** | 「先连粗流程，再逐屏打磨」 |
| 4 | **基础设施共享** | 「状态、存档、返回、试玩、发布由 Runtime **提供一次**」 |

> 💡 **第 1 条反过来验证了我们画布底子是对的** ——
> 我们有 `relation` 类型、端口校验、循环检测，
> **缺的只是"选中时高亮上下游"这个让价值可见的交互**。

## 二、OhMyGame authoring.md —— ⭐ 最能直接抄的一节

### 2.1 编辑器总原则

> 「**作者描述。Agent 构建。作者实时看到结果。**
> 手工改代码是可能的，但它是**大多数作者从不打开的逃生舱**，
> **任何常规任务都不应该需要它**。」

### 2.2 工作区布局

```
┌──────────────────────────────────────────────┐
│ Header: Project ▾ · Back  Playtest · chat · Publish │
├───────────────┬──────────────────────────────┤
│ Chat with     │ Story（流程画布）              │
│ the Agent     │ 或                              │
│（左/右，可折叠）│ Scene Workbench（从场景打开）    │
└───────────────┴──────────────────────────────┘
```

### 2.3 🔴 画布卡片上放什么（本轮最值得抄）

> 「画布只回答一个问题：**玩家能在项目里怎么移动**」

| 元素 | 说明 |
| --- | --- |
| 🔴 **实时缩略图** | 「由 Runtime 渲染的，**所以画布看起来像游戏，而不是像图表**」 |
| 场景标题 | |
| **每 Exit 一个出口端口** | 标 Exit 名；**依赖进度时用小字标出条件** |
| **Start 徽章** | `Set as Start` 可改 |
| **Ending 徽章** / `Off map` | |
| 🔴 **问题标记** | 构建失败 / 发出未声明 Signal / **Exit 指向了不存在的地方** |

**三条减噪规则**：
- 「出现在多个场景上的顶栏，把它的 Exits **加到每张卡片上**，**没有单独的卡片**」
- `Allow Back`（`push` 边）**画法不同**，带 `↩ Back` 标签
- **Navigation Exit 没有连线**，只写名字（`→ Platform`），**只影响画法，不影响跳转**

### 2.4 🔴 Scene Workbench：没有属性面板

```
┌──────────────────────────────────────────────┐
│ Scenes / [Title]        Replay · Play from here │
├──────────────────────────────────────────────┤
│                                              │
│         ( Would open Club lobby   [Open] )  │  ← 预览上覆盖的提示
│                Live preview                   │
│         (real Runtime, real assets)           │
│                                              │
│  ┌────────────────────┐  ┌──────────┐         │
│  │ ▶Play ⌖Select TText ✥Move ✎Draw │ 2 issues │ │
│  └────────────────────┘  └──────────┘         │
└──────────────────────────────────────────────┘
```

**三条设计（都是范本级）**：

**① 没有 inspector**
> 「**There is no inspector**：Agent 改变场景，**作者在预览上指、编辑、或画**，
> 来说明要改什么。」

**② 实时预览里点 Exit，会显示"将会去哪"而不跳走**
> 「在预览里点『进入俱乐部』会触发 `enter-club` Exit。
> **它不会离开场景**，而是在预览上覆盖一条短消息说它会去哪，
> 如『**Would open Club lobby**』，并给一个 `Open` 按钮；几秒后淡出。」

**③ 预览工具栏决定指针行为**
| 工具 | 作用 |
| --- | --- |
| `▶ Play` | 播放场景 |
| `⌖ Select` | 选元素喂给 chat，**选中的显示成 chip**；Shift/⌘ 选多个或取消 |
| `T Text` | 就地改文字（Enter 确认，Esc 撤销） |
| `✥ Move` | |
| `✎ Draw` | |

**选中的图片旁边有一条小工具栏**：**从素材库替换 / 上传 / 让 Agent 生成**。

### 2.5 建场景流程（细节很好）

1. 作者在画布上点 **Add Scene**
2. 窗口里每个 Template（Blank / Main menu / Choice / QTE / Hotspot / Ending /
   Story map）**一张图 + 一行说明**
3. 场景**带着可用的起始内容**出现在画布上，Workbench 打开
4. 🔴 **聊天框自动聚焦到这个新场景**，准备好接受
   「把这个改成俱乐部主屏，深色石头背景，四个入口」

> 「A Template is **starter content plus instructions for the Agent**.
> **It is not stored as a type**, and a Scene created from "Main menu"
> **can later become anything**.」

### 2.6 「Allow Back」「Navigation」由 Agent 标，作者用自己的话提

> 「作者用自己的话提出（"let Archive open the case archive with Back allowed"），
> Agent 负责标记。」

## 三、handraw 的门禁纪律写法 ⭐ 我们的 skill 该抄

### 3.1 阶段门槛写死成一条链

> 「**调研与方案 → 用户确认 → 画面素材准备 → 全部画面素材审查通过
> → 配音与动画 → 合成 → 验收**」
>
> 「"帮我做视频"**仅授权方案阶段**。确认前可盘点已有素材；
> **不得生成画面、配音、动画代码或预演**。」

### 3.2 素材没审过，不许往下走

> 「全部必需图片、录屏、视频、图表数据、动作素材**经技术检查与实际画面审查通过前，
> 不生成配音、不编写本期动画、不预渲染或合成**。」

### 3.3 🔴 明确写"什么不能做"（而非只写"应该做什么"）

| 条目 | 原文 |
| --- | --- |
| 不用生成内容冒充真实素材 | 「真实录屏、事实数据、用户原件及实际字幕时间缺失时，提供采集或补充要求，**不能用生成内容冒充**」 |
| 不许凑时长 | 「未回传、过短、损坏、身份/动作/衔接不合格**均阻止制作**。**不循环、冻结或变速凑时长**」 |
| 不许静默换服务商 | 「`build` 可按明确配音设置执行，但**指定服务不可静默替换**」 |
| 新增分类要验证 | 「**先完成技术验证与实际审片，由用户决定是否收录共享库；新增名称不等于新增能力**」 |
| 不猜 ID | 「资源查找用 `hvp jianying-resources`，**不猜资源 ID**」 |
| 不覆盖用户配置 | 「配置存放在**仓库外的本机用户目录**，更新仓库和同步 Skill **不会覆盖**」 |
| 不自动换路径 | 「未设置、目录失效或配置损坏时**明确报错，不自动换路径**」 |
| 禁止自修复用户工程 | 「禁止 **overwrite** 自修复用户工程」 |

### 3.4 每帧由帧号复算（不用墙钟）

> 「**每帧由帧号复算**。网页实现保留 `renderFrame(t)`；
> CSS 动画暂停并定位，**JS 不依赖墙钟**。」

> 💡 **这条对我们做视频合成有直接技术价值** —— 时间驱动必然导致不一致。

### 3.5 🔴 预渲染的授权纪律（写得很死）

> 「确需 ST-005～007 或 JS 环境效果时，先说明
> **具体镜头、耗时来源、画面将合并为视频和可编辑性损失**，取得**用户真实同意**；
> `render_backend=web` 或 `auto` **都不等于用户授权**；
> **方案改版旧授权失效**。」

> 「未经同意时，调整为可原生效果或提交浏览器路线方案，
> **不静默改变视觉**。」

> 「明确 `render_backend=jianying` 的镜头不支持时**仍阻止**，
> **不用授权覆盖其原生要求**。」

### 3.6 🔴🔴 诚实性的极致：反复区分"结构通过"和"真的能用"

| 原文 | 含义 |
| --- | --- |
| 「**软件或网页未能实际审看时标记未验证，不能只凭结构断言画面正确**」 | 没看过 = 未验证 |
| 「**草稿结构通过不能称为剪映实际导出通过**」 | 结构 ≠ 导出 |
| 「写入结构通过**不等于**软件最终渲染通过」 | 写入 ≠ 渲染 |
| 「生成时检查实际结构及哈希，**失败不得标注通过**」 | 失败不许标过 |
| 「应用打开、实际导出、音频与字体检查、用户审美接受**分别登记**」 | 四件事分开报 |

> 💡 **这是我们 skill 第 4、5 条元规则（"文档承诺≠能做"、"装上≠能用"）的完整版** ——
> 他们已经细到"结构通过 / 写入通过 / 导出通过 / 审美接受"四层分离。
> **我们的 skill 目前只有两层，粒度不够。**

## 四、对我们的意义

### 4.1 抄进 skill 的三条（粒度升级）

| # | 抄什么 | 层级 |
| --- | --- | --- |
| 1 | 🔴 **把"验证状态"分级**：`已实现` / `已安装` / `结构通过` / `实际跑通` / `未验证` | 我们现在只有 2 层，他们 4-5 层 |
| 2 | **门禁写"不能做什么"**，不只写"该做什么" | 我们 skill 目前偏正面表述 |
| 3 | **降级/替代方案必须用户同意**，方案改版旧授权失效 | 直接可抄 |

### 4.2 抄进 UI 的两条（OhMyGame）

| # | 抄什么 | 成本 |
| --- | --- | --- |
| 1 | 🔴 **画布卡片用实时缩略图**，让画布"像作品"不像"图表" | 中 |
| 2 | 🔴 **节点选中时高亮上下游 + 标出断链**（Exit 指向不存在的地方要打标记） | 低（数据已有） |

### 4.3 一个技术点值得单独记

**「每帧由帧号复算，JS 不依赖墙钟」** —— 做确定性视频渲染的基本原则。
我们若有类似拼接逻辑，应检查是否踩了这个坑。`待核实`
