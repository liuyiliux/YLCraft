## 〇、先说核实结论：我们的画布**比想象中强**

> **这是本轮最重要的发现之一** —— 我们之前以为"无限画布只有占位"，
> 但读了 `frontend/src/pages/canvas/index.tsx` 之后发现**连线系统已经很完整**。

### ✅ 我们已有（读代码核实）

| 能力 | 证据 |
| --- | --- |
| **连接实体 + 关系类型** | `CanvasConnection`，`relation` 分 `reference` / `context` / `generation` / `sequence` |
| **端口系统 + 类型校验** | `CanvasEdgePort`（input/output 独立），「端口类型不兼容，无法建立连线」 |
| **循环依赖检测** | 「链路里存在循环连接，请先拆开循环再运行」 |
| **批量对应模式** | `逐项 Prompt[]` + `逐图生图`：「第 1 条对应第 1 张图，第 2 条对应第 2 张图」 |
| **撤销 / 重做** | `historyPast` / `historyFuture` + `undo()` / `redo()` |
| **JSON 导入导出** | 「画布 JSON 已导入」 |
| **素材库关联入节点** | 「已导入素材库并创建关联节点」，带 `canvas_source_node_id` |
| **状态栏显示规模** | 「N 个节点，M 条连线」 |

### ❌ 我们没有（对方有的）

| 能力 | 谁有 |
| --- | --- |
| **版本历史**（每次保存记一笔） | BeefTV |
| **图片拆宫格**（4/9/16/25） | BeefTV |
| **批量创作表** | BeefTV |
| **小地图（minimap）** | Infinite Canvas |
| **选中节点时高亮上下游** | Infinite Canvas |
| **3D 导演台节点** | Infinite Canvas（我们有自己的独立 Previs 页） |

> **结论**：**"连线=依赖"这个核心我们已经有了，且做得更细**
> （relation 类型 + 端口校验 + 循环检测，都比对方多）。
> **缺的不是连线，是"版本历史/批量表/高亮上下游"这些周边。**

## 一、handraw-style —— 「把画风编号化」（5.5k star / 647 fork）

> **一手**。`github.com/yang0/handraw-style`，137 commits，最新提交 15 小时前。
> 定位：「**手绘风格与排版图型提示词库**」。

### 1.1 它解决的核心问题（原文对照表）

| 创作痛点 | 它的解法 |
| --- | --- |
| 「画风描述模糊，**每次生成都漂移**」 | **编号化精准激活**：331 种手绘风格（FA~FH 分类 + 001–327 传统编号） |
| 「告别『可爱一点、文艺一点』的**玄学生图**」 | 同上 |
| 版式构图单调 | **165 种排版图型**：21 社媒卡 / 35 数据信息图 / 68 漫画分镜 / 13 IP设计 / 24 电商图型 |
| 色彩杂乱 | **36 种经典单色**：克莱因蓝、鼠尾草绿、爱马仕橙、佩恩灰 |
| 图文不搭 | **双模式**：纯图模式 / 图文模式（文字与画面一体化构图） |
| 模型画风锁死 | **模型能力分层与兜底**：显式模型精准标定，通用模型走**参考图兜底** |

### 1.2 🔴 三种使用模式（梯度设计）

**① 智能推荐（零门槛）**
> 输入：「帮我生成猫咪在窗台晒太阳的治愈插画提示词，你帮我选风格和主题色」
> 输出：`风格 #FA-018 (#018) · Minimal Deadpan Dialogue Cartoon + 主题色 C-26 · 柿子橙`
> **并给推荐理由**：「（理由：画面充满温暖治愈与松弛感）」

**② 精准指定（自选编号）**
```
单独：FB-006号风格，主题：秋天的第一杯奶茶
组合：图型 SC-001，风格 FB-006，主题：秋天的第一杯奶茶
全指定：图型 SC-001，风格 FB-006，主题色 C-01，主题：秋天的第一杯奶茶
```

**还有「补齐模式」**：只给风格 → 自动推荐主题色；只给颜色 → 自动推荐画风。

**③ 海报模式**：按「**8 大核心纯净设计字段**」输出
（主题、场景、受众、密度、情感、主题色、editorial 风格、画风）

### 1.3 对我们的意义

**这是"一致性"问题最落地的解法**：用户不会写画风术语 →
**编号 + 双语提示词 = 稳定输出**。

我们已有 `scene` 概念（`THEME.ecommerce` / `photography` / `drama` / `coser`），
但**粒度粗得多，也没有"选编号出提示词"这条路**。

### 1.4 它的工程做法（值得学）

- **中英双语成对文件**：`STYLES.md` / `STYLES_en.md`、`COLORS.md` / `COLORS_en.md`…
- **职责分离的清单文件**：`STYLES` / `LAYOUTS` / `COLORS` / `MANIFEST` / `DEPENDENCIES` / `RELEASE_AUDIT`
- **发版自检脚本**：`scripts/audit_release.py`（检查本机路径、凭据、视频文件是否混入）
- 许可宽松：「欢迎自由使用、修改和**商业化**」，只要求保留作者署名

## 二、OhMyGame —— 「Agent 真的在操作画布」（Apache 2.0）

> **一手**。`WhiteTowerAI/ohmygame`，中文 README 全文实抓。
> 定位：「**你的一人游戏工作室**」「用 AI 做游戏的一切，都在一个应用里」。

### 2.1 两条设计理念（原文）

> 1. **一切都在画布上。**「设计文档、概念图、3D 模型和视频并排放在同一块画板上。
>    一张角色草图可以延伸出更多美术图、一段视频，或者一个绑好骨骼的 3D 模型」
> 2. **活由 Agent 来干。**「它像你一样操作画布」

### 2.2 🔴 Agent 的自审闭环（我们最缺的）

> 「它在**一个你可以旁观的窗口**里打开游戏并**亲自试玩**，
> 包括实时渲染的 Canvas 和 WebGL 游戏。
> **发现问题时，它会尝试修复，然后再玩一遍。**」

**"生成 → 试玩 → 发现问题 → 修复 → 再试"** 这个闭环，
和 OpenMontage 的 post-render self-review 是同一思路。

### 2.3 三条实现原则（很干净）

| # | 原则 | 原文 |
| --- | --- | --- |
| 1 | **界面为"查看结果"设计** | 「界面**专为查看结果而设计，而不是让你读 diff**」 |
| 2 | **每个工作区都是文件** | 「设计文档是 Markdown，画板和素材画布共用同一套 **JSON 节点模型**……每种工作区都附带 `AGENTS.md` 和 JSON Schema，**所以 Agent 编辑它们的方式和编辑代码一样，可视化编辑器读写的也是同一批文件**」 |
| 3 | **游戏操作就是工具调用** | 试玩（`game_use`）、生成媒体、检查节点，都是普通工具，**Agent 能把它们串起来** |

> 💡 **第 2 条对我们的价值最大**：如果我们的画布数据是**文件 + schema**，
> Agent 与前端读写同一份，就不会出现"Agent 改了、前端看不到"。

### 2.4 按需连接模型（一张表说清依赖）

| 想做的东西 | 需要连接 |
| --- | --- |
| 设计文档、代码、试玩 | 任意**语言**模型服务商 |
| 图片和精灵图 | OpenAI / OpenRouter / 火山方舟 BytePlus |
| 视频 | OpenRouter / 火山方舟 |
| **3D 模型、骨骼绑定、动画** | Meshy / Tripo / Hyper3D |

> **这张"想做什么需要连什么"的表，就是我们 `AI 图片和视频创作` 那段介绍缺的。**

### 2.5 诚实的注释（和 BeefTV 同一个好习惯）

```
<!-- 目前试玩还是开环的：Agent 先规划一批输入，执行完再看结果，还没有实时反应能力。 -->
<!-- TODO(asset): 截图或 GIF…有真实素材之前先不放。 -->
<!-- TODO(legal): 列出更多订阅前，先确认各服务商的条款。 -->
```

**明确标注"现在做不到什么"**，而不是含糊过去。

### 2.6 隐私与成本

- 40+ 模型服务商（Anthropic / OpenAI / Google / DeepSeek / 通义 / Kimi / GLM / MiniMax / xAI / Mistral / Groq / OpenRouter / Bedrock / Vercel…）
- **可直接登录已有订阅**（ChatGPT Plus、GitHub Copilot）
- 「**密钥只保存在本地守护进程里，永远不会进入 Agent 的工作区、你的游戏或渲染进程**」
- **无按次计费点数**，做出来的东西归你所有

## 三、Infinite Canvas —— 节点模型最清晰的一个

> **一手**。公众号文章（挖挖，2026-09-14）全文实抓。
> 仓库 `tigerowo/infinite-canvas`。
> 🚨 **证据等级：只有公众号文章描述，我没见过它的真实界面。**
> 下面所有功能描述应理解为「作者这么写的」，不是「我看到的」。

### 3.1 六种节点类型

| 节点 | 作用 |
| --- | --- |
| **文本节点** | 保存故事、分镜、提示词、修改要求和 AI 文字回答 |
| **图片节点** | 放置参考图、生成结果，继续编辑或作为视频参考 |
| **生成配置节点** | **汇总上游提示词和参考图**，使用选定模型/比例提交任务 |
| **视频、音频节点** | 导入素材、播放结果，**并向后续生成提供参考** |
| **全景图节点** | 准备供导演台使用的场景环境 |
| **导演台节点** | 保存独立的 3D 场景、角色和机位 |

**关键设计**：「生成配置节点会**汇总上游**提示词和参考图」——
**这就是"资产自动注入"的机制化实现。**

### 3.2 🔴 选中节点高亮上下游

> 「**选中一个节点时，还能高亮相关的上下游内容，方便追溯某张图使用了哪些参考素材。**」

**比单纯画线更进一步** —— 是**可交互的依赖追溯**。

### 3.3 3D 导演台 → 回流画布

> 「可以先在场景里摆好人物、调整姿势和摄像机角度，
> 再**把机位截图直接送回画布**，作为生图或视频生成的参考。」

### 3.4 文本节点的"改写留痕"

> 「文本节点里的创意可以交给 AI 扩写，改写结果**生成到新的文本节点，保留原文用于对照**。」

**不覆盖原文，另开节点** —— 版本对比靠这个。

### 3.5 其他

- 多项目、缩放、**小地图**、复制粘贴、撤销重做、JSON 导入导出
- **存储分层**：账号同步 + **S3 兼容存储 / R2 / WebDAV**
- 管理页：算力记录、AI 接口日志、提示词管理、**Skill 库**、全局模型配置
- ⚠️ 默认管理员 `admin` / `infinite-canvas`（**部署时必须改**）

### 3.6 🚨 那段安装提示词，第 5 条值得抄进我们的 skill

> 「**不要把「安装成功」当成「生图和视频生成测试通过」。
> 没有配置模型 API 时，明确说明尚未验证生成能力。**」

**同一条纪律的另一个版本，和 BeefTV 作者的诚实是同一件事。**

### 3.7 它演示提示词的写法（对我们写提示词模板有参考）

> 「**不分轮确认，不先交付分镜或静态图片**」
> 「保持原视频的横版 16:9、**镜头顺序、景别、运镜、切镜节奏**、房间、桌椅和暗色光影」
> 「**不把背景人物一起替换，不混合两人的面部特征**」

**结构：先声明交付形态 → 再列必须保持的维度 → 最后写负面约束。**

## 四、三方对照：画布路线已经收敛

| 项目 | 许可 | 连线=依赖 | 关键差异 |
| --- | --- | --- | --- |
| **BeefTV** | MIT | 简单连线 | 4 个顺手小功能（版本历史/拆宫格/批量表/Tab 插素材名） |
| **OhMyGame** | Apache 2.0 | JSON 节点模型 | **Agent 自审闭环**；工作区即文件 |
| **Infinite Canvas** | — | 6 类节点 + **选中高亮上下游** | 生成配置节点汇总上游；3D 导演台回流 |
| **我们** | — | ✅ **更细**（relation 类型 + 端口校验 + 循环检测） | 缺版本历史 / 批量表 / 高亮上下游 |

**四方共识**：**「一切都在画布上 + 节点可引用 + 数据是文件」是这条路线的正解。**

## 五、对我们的意义

### 5.1 纠正了一个认知偏差

**我们画布的连线系统比 BeefTV / Infinite Canvas 都完整**
（有关系类型、端口类型校验、循环依赖检测、批量对应）。
**问题从来不是"没有连线"，而是"连线的价值没有被用户看见"。**

### 5.2 三条最值得补的（按性价比）

| # | 补什么 | 谁做的 | 成本 |
| --- | --- | --- | --- |
| 1 | 🔴 **选中节点高亮上下游** | Infinite Canvas | 低 —— 数据已有，只差交互 |
| 2 | **版本历史** | BeefTV | 中 |
| 3 | **Agent 自审闭环**（生成→检查→修复→再看） | OhMyGame / OpenMontage | 高（要定"什么叫合格"） |

**第 1 条性价比最高** —— 我们已经有 `CanvasConnection` 和 relation 类型，
**只差一个"选中时高亮"的交互**。

### 5.3 一条要写进 skill 的纪律

> 「**不要把「安装成功」当成「生成测试通过」。**」
> 「**README 里写的那是以后的目标，现在还做不到。**」

**同一个纪律的两种说法，应该固化成我们 skill 的元规则。**
