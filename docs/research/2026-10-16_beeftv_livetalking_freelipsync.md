## 一、BeefTV —— LibTV 的开源平替（最有参考价值）

> **一手**。公众号文章《小知》2026-10-15 全文实抓。
> 2026-09-24 开源，作者 `Beefnoodle`（独立开发者），**MIT**，超 1000 Star。

### 1.1 作者为什么做它 —— 正是我们的痛点

> 「他之前用 **LibTV 这类在线画布产品用得不顺**，**流畅度不行，限制也多，
> 价格还不便宜**，干脆花了一个星期，把核心功能复刻出来做了个本地版」

**这是第三方对在线画布产品的真实评价。**

### 1.2 🔴 最值得抄的一条：连线 = 依赖关系

> 「连线表示引用关系。比如我先生成一张**人物设定图**，后面三个分镜都拿它当参考，
> 就连三根线过去。**以后想改人物形象，源头那张图换掉，顺着线就知道哪些东西受影响**。」

**这正是我们一直想要但没做出来的两件事：**

| 我们想要的 | BeefTV 怎么做 |
| --- | --- |
| 资产自动注入生成请求 | **连线**表达「谁引用谁」 |
| 改一处，知道哪些受影响 | **顺着线就能看到依赖图** |

> 💡 我们的角色库/世界地图已经有依赖数据（`world_entity_relations`、
> `visual_profile` 等），**但没有把依赖关系画出来给用户看**。

### 1.3 形态与技术

- **桌面软件**（非网站）：Mac / Windows 安装包，Linux 有 DEB，约 **200MB**
- Go 后端 + React 前端，**Wails** 打包
- **本地优先**：项目、画布、素材、模型配置默认存在本机
- **只有点生成时才请求模型服务**
- 换电脑：退出软件，**把数据目录整个拷走**

### 1.4 模型不绑定（与我们设计原则一致）

> 「它不绑定哪一家模型。文本、图片、视频、音频的模型都能自己配，
> 填 **Base URL 和 API Key** 就行，**密钥只存在本地**。」

内置作者自建的 `BeefAPI` 渠道（浏览器授权即用）。

### 1.5 四个"顺手的小地方"

| 功能 | 说明 |
| --- | --- |
| **画布版本历史** | 每次保存记一笔；**恢复旧版本前自动备份当前** |
| **打素材名按 Tab 插入** | 写提示词时输入素材名，**Tab 直接插进去**，不用复制链接 |
| **图片拆宫格** | 4 / 9 / 16 / 25 宫格，**拆出来自动排好** |
| **批量创作表** | 一次跑一批提示词 |

**这四条我们的画布/创作台都没有**（`待核实`，我还没逐个确认）。

### 1.6 ⚠️ 作者的诚实（这点最值得学）

> 「**README 里写的让 Agent 主导创作流程，那是以后的目标，现在还做不到。**」
>
> 「核心维护的就两个人，更新快归快，**接口和数据结构说不定哪天就变了**，
> 升级之前建议先把数据目录备份一下。」
>
> 「Agent 那块目前也就是个辅助，**不算成品**。」

**一条文档纪律**：README 承诺的 ≠ 现在能做的，**必须明说**。
这条应该进我们的 skill（我们也有过"文档说有、实际没实现"的情况）。

## 二、LiveTalking —— 对话型数字人

> **一手**。公众号文章 2026-09-10 全文实抓。
> GitHub 近 **1 万星**，本体 **Apache 2.0**。

### 2.1 定位差异（很清楚的一句话）

> 「与『念稿播放』这类方案的**根本区别**，在于将自身定位为
> **『实时对话引擎』**，而非『**录像播放器**』。」

工作链路：**声音 → ASR → 大模型 → TTS → 驱动口型/表情**，
关键在**基于 WebRTC 的实时音视频通道**（非录制回放）。

### 2.2 🔴 支持打断

> 「数字人话说到一半，**你插一句，它能停下并重新接话**，不会自顾自继续念下去。」

**「可打断」是交互质量的硬指标** —— 不可打断 = 用户只能等。

### 2.3 硬件门槛已很低

| 组合 | 性能（官方参考数据） |
| --- | --- |
| Wav2Lip | RTX 3060 约 **60 fps** |
| MuseTalk | RTX 4090 约 **72 fps** |

> 「**无需数据中心级的服务器，一张主流游戏显卡**就能驱动"会说话的数字人"」

**这条对我们直接有用** —— `unirig-local-rigging-service` 曾因
「本机 6GB 显存 < 上游要求 8GB」被搁置。**这类口型/数字人任务门槛低得多**，
跟 3D 绑骨不是一回事，值得分开评估。

### 2.4 音色与输出

- 音色：GPT-SoVITS、CosyVoice 等开源 TTS
- 输出：WebRTC / RTMP 推流 / **虚拟摄像头**（可作会议分身）

### 2.5 ⚠️ 授权不统一（重要）

> 「LiveTalking 本身是 Apache 2.0，但**所集成的底层组件授权并不统一**。
> 例如用于驱动口型的 **Wav2Lip，其授权明确限定为个人与非商业用途**；
> 换用的模型、TTS 引擎也需逐一核查各自协议。」

**外加一条运行时约束**：
> 「基于 LiveTalking 生成的视频**需附带项目水印**，商用前请仔细阅读其水印规则。」

## 三、FreeLipSync —— 口型同步在线版

> **一手**。2026-10-16 实抓官网 + 教程页，截图目视。
> 也是 `dsh-tool-lipsync` 插件背后的服务。

### 3.1 落地页就是一个创作框（交互优点）

- 标题即功能：「免费 AI 口型同步生成器在线版」
- 副标题说场景：「让照片和视频用更自然的 AI 口型同步开口说话或唱歌，**适合创作者的高性价比工具**」
- **上传框直接写清格式**：
  > 「上传要进行口型同步的视频或图片」
  > 「拖拽文件到此处，或点击上传 **支持 MP4, MOV, JPG, PNG, WebP**」
- **上传框下方就是一排示例人脸**，每个带播放按钮 —— **点示例就能直接试**
- 底部标注哪些功能免费

> **没有任何参数面板。三个动作：上传 → 选示例/示例音 → 生成。**

### 3.2 功能按**输入方式**划分

视频对口型 / 图片说话 / 唱歌与 MV / **多人对口型** / 音频工具 / API

### 3.3 🔴 教程的组织方式值得抄

**两个维度并行：**

**① 按输入方式**：图片加文本 / 图片加音频 / 照片唱歌 / 处理现有视频

**② 按目标**（每条含真实输入素材 + 成品演示）：

| 教程 | 说明（原文） |
| --- | --- |
| 让照片开口说话 | 把人物照、头像或老照片生成**文本驱动**的说话视频 |
| 用上传音频驱动照片 | 「**保留成品录音中的节奏、停顿和表达方式**」 |
| 让照片或角色唱歌 | 用歌曲驱动清晰人脸图片 |
| 修改现有视频台词 | 「**保留原始人脸画面**，同时替换或重新同步语音」 |
| 🔴 **修复口型同步质量** | 「**重新生成前先排查时间和源图片问题**」 |

**最后一条最值得学**：它**把"修复质量"当成一个正式的教程分类** ——
**承认会失败，并给出排查顺序**。

> 这与我们 skill 里的「错误旁给可操作的下一步」「先复现再修」是同一条原则。
> 我们实测抓到的「点确认不生效、错误甩 SQL」，正是缺这一层。

### 3.4 应用场景用「角色 + 动词」写（SEO 结构）

| 场景 | 原文 |
| --- | --- |
| 教育 | 把老师照片或讲师视频做成**短讲解**、发音示例、多语言课程片头 |
| 营销 | 快速做**产品 demo**、创始人**口播**、广告草稿和落地页 presenter，「**文案一改就能重生**」 |
| 社交媒体 | creator clip、reaction、meme、talking photo、TikTok 素材、Reels 开场、Shorts 点子 |
| 企业培训 | 更新内训视频、入职说明、制度讲解、多语言团队通知 |
| 电商 | 商品页、店铺活动、UGC 广告补充 talking product intro |

**「文案一改就能重生」** = 提示词可复用迭代，
与 Flow TV 的 `Reuse Prompt` 是同一思路。

### 4.2 一条需要重新评估的

**`unirig-local-rigging-service` 的"显存不够"结论可能过宽。**
它是 **3D 绑骨**（要 8GB+）；而口型/数字人这类
（LiveTalking / FreeLipSync）**3060 就能跑**。
**两类任务的硬件门槛差一个量级，不该一起被"暂缓"。**
