# 第一部分：别家的 Agent 怎么搜网络知识

## 一、开源：Toonflow 的三个网络工具

Toonflow 的 10 个 Agent 工具里有 3 个和网络有关（源码实读）：

| 工具 | 干什么 | 什么时候用 |
| --- | --- | --- |
| **`webSearch`** | 搜索，返回标题 + 链接 + 摘要 | 不知道去哪找 |
| **`webFetch`** | 抓一个 URL 的正文 | 知道具体链接 |
| **`browser`** | 驱动浏览器（登录态、点击、滚动） | 需要登录 / 动态渲染 |

**它的设计特点：三个工具分开，让 Agent 自己选。**
不是"一个万能搜索"，而是"搜索 / 抓取 / 操作"分层。

**这条我们要抄** —— 我们现在只有 `kb_search`，缺 `web_search` / `web_fetch` / `browser`。

## 二、LibTV：产品级的"两扇门"

来源：[极客公园：一款产品，同时为人类和 Agent 设计](https://m.163.com/dy/article/L7UKMRH205119FMA.html)

**它没有强调"搜索"，而是强调"给 Agent 的门"** —— 但里面的三条结论直接决定搜索怎么做：

### 2.1 能力包装要在"中间层"

> API 太细，Agent 得来回调几十次。一键出片太粗，不同任务没法差异化。
> Sequoia 的说法是「Goldilocks」——**把大量控制流交给 LLM，但保留一组轨道和状态感知**。

**映射到搜索**：
`web_search(query)` 太细（Agent 得自己改查询、去重、判断权威性）
`research(topic)` 太粗
🔴 **中间层 = `research(topic, depth)`**，里面封好改写/去重/排序/读取，只留少量参数。

### 2.2 Agent 靠"量"补审美，所以必须支持批量

> Agent 没有创作者的直觉。它的办法是靠量：每个镜头生成好几个版本，
> 按一致性、构图、风格匹配度自动筛。**用算力换审美。**

**映射到搜索**：Agent 应该**一次看 10 条、并行搜索多个查询方向**，而不是一条一条试。
这也是为什么"便宜"很重要 —— Agent 天然要多调几倍。

### 2.3 🔴 Agent 交付的不是文件，是「可接管的项目」

> LibTV 返回的不是一个任务 ID，而是三样东西：
> - **`sessionId`** —— Agent 持续查询进展
> - **`projectUuid`** —— 挂在一个可持续的项目对象上
> - **`projectUrl`** —— 人类随时打开画布接管

**这句话对我们最重要**：
Agent 做完调研，交付的应该是**知识库里的一个条目（可编辑、可追溯）**，
不是一个聊天消息里的几段话。

## 三、OiiOii：7 个专职 Agent

来源：[OiiOii Changelog](https://www.oiioii.ai/changelog)

| 版本 | 内容 |
| --- | --- |
| v5.0 (2026-06) | **7-agent pipeline GA**：Art Director / Scriptwriter / Character Designer / Scene Creator / Animator / Editor / Sound Engineer |
| v4.5 | 角色一致性引擎（跨几百镜不变脸） |
| v4.0 | 画布式分镜编辑器 + Editor agent 自动重排时间线 |

**它的分工方式值得看**：不是一个通用 Agent，是**7 个角色化的**。

**映射到搜索**：
- Scenario Writer 不需要搜索
- **Art Director 需要搜参考风格**
- **Scene Creator 需要搜实景/材质参考**

🔴 **搜索需求是分角色的** —— 不是"给所有 agent 一个搜索工具"，
而是"某个角色在某个环节才需要搜"。

## 四、Lovart：搜索是"设计调研"的一部分

Lovart 2.0 的能力里有一条 **「设计调研」**（和画布巡检、设计委托并列）。

它的做法不是在节点里塞个搜索框，而是：
**把"调研"作为一个 Agent 主动发起的行为** —— 你说"做个美妆海报"，它先去调研同类设计的做法，再动手。

**这和我们基调 I1「设计解说」是配套的**：
先调研 → 再设计 → 汇报时说"参考了哪几类做法"。

## 五、🔴 最有价值的：一条完整的联网检索链路

来源：[阿里云：给 AI Agent 接入联网搜索](https://developer.aliyun.com/article/1771291)

**核心观点**：
> 搜索 API 只是其中一环。最终效果取决于**整条链路**，而不是接口一次返回多少条。

### 9 步链路

```
用户问题
  ↓ ① 判断是否需要联网
  ↓ ② 查询改写与拆分（2-4 个，不同侧重点）
  ↓ ③ 并发搜索
  ↓ ④ 结果标准化、去重
  ↓ ⑤ 相关性与来源排序
  ↓ ⑥ 只读 3-5 个候选网页
  ↓ ⑦ 正文切分与压缩（top 8 段）
  ↓ ⑧ 生成带引用答案
  ↓ ⑨ 🔴 引用一致性检查
```

### 每一步的坑和做法

| 步 | 坑 | 做法 |
| --- | --- | --- |
| ① 要不要搜 | 模型以为自己知道（其实是过期的内部知识） | 强制规则：含「今天/最新/价格/版本/政策」→ 必搜；其余 model_decide |
| ② 查询改写 | 直接搜用户原话 → 结果分散 | 让模型生成 2-4 个查询，覆盖**现象 / 术语 / 可能原因** |
| ③ 并发 | 串行慢 | 多查询并行 |
| ④ 去重 | **5 条结果都来自同一篇稿**，模型以为交叉验证了 | 删 `utm_*`、统一 http/https、标题相似度、正文指纹 |
| ⑤ 排序 | 权威 ≠ 相关 | `SOURCE_WEIGHT`: official 1.0 / academic 0.9 / pro_media 0.75 / community 0.55 / unknown 0.3<br>**权重不能代替相关性** |
| ⑥ 只读几个 | 读所有页面太慢 | 10 条 → 排序 → 只读前 5 |
| ⑨ 🔴 引用校验 | 「答案后面有链接」就结束了 | **把答案拆成事实陈述，逐条找证据** |

### 引用校验的例子（这条最值得抄）

```
陈述：某功能从 3.2 版本开始支持。
证据：官方更新日志明确写明 3.2 新增该功能。
结论：支持。

陈述：该接口平均延迟低于 500ms。
证据：引用页面只写了"低延迟"，没有测试数据。
结论：不支持 → 应删除具体数值，或降级为"据称低延迟"
```

**处理方式**：删除 / 降低语气 / **明确标注为推断**。

🔴 **这正是我们画布里那条「是我的经验推断，材料里没写死」的完整版。**
我们做对了一句，这里给出了系统化做法。

### 失败分类（很容易漏）

```python
class RateLimited(SearchError): ...   # 指数退避重试
class SearchTimeout(SearchError): ... # 缩短查询或换备用源
class EmptyResult(SearchError): ...   # 改写查询再搜
```

> **Agent 不能把"搜索失败"理解成"网上没有信息"。**

### 评价指标

| 指标 | 说明 |
| --- | --- |
| Top5 相关率 | 前 5 条真正相关的比例 |
| 新鲜信息命中率 | 时间敏感问题是否找到最新 |
| 权威来源占比 | 候选里可信来源比例 |
| **重复结果率** | 是否实际来自同一内容 |
| 正文读取成功率 | 能否提取有效正文 |
| 🔴 **引用支持率** | 引用内容是否支持结论 |
| P50/P95 耗时 / 单任务成本 / 任务完成率 | |

## 六、六家对照总结

| 谁 | 搜索怎么做的 | 我们该抄什么 |
| --- | --- | --- |
| **Toonflow**（开源） | 3 个工具分开：`webSearch` / `webFetch` / `browser` | ✅ **工具分层，不是万能搜索** |
| **LibTV** | 不强调搜索，强调"给 Agent 的门"：中间层 Skill + 返回 sessionId/projectUuid/projectUrl | ✅ **搜索结果要落成可接管的项目** |
| **OiiOii** | 7 个角色化 agent，搜索需求分角色 | ✅ **不是所有 agent 都要搜** |
| **Lovart** | 「设计调研」作为 Agent 主动行为 | ✅ **先调研再动手，汇报时说参考了什么** |
| **阿里云流水线** | 9 步链路 + 引用一致性检查 | 🔴 **完整链路 + 引用支持率** |
| **我们现在的** | `kb_search` 一个工具，只查内部知识库 | 缺 web 搜索、缺引用校验、缺失败分类 |

# 第二部分：P4 / P5 / P6 落地

## P4：Context chips 可移除

![chips 可移除](v14/42_chips_off.png)

```
使用了  ●我做 Cos 图的 7 条经验 ✕   ●AI 生图的提示词工程实践 ✕   ●短剧分镜的 12 个镜头语言 ✕
```

点 ✕ → 这条被**划掉**，并且 Agent 回一句：

> 好，以后**不再引用**《AI 生图的提示词工程实践》。
> ⚠️ 需要的话可以在知识库里重新启用它。**本次回答里已经用到的那段保留，不回滚。**

**最后那句很重要** —— 停用是"以后不用"，不是"这次重答"，说清楚不然用户会误解。

**实测**：3 个 chips 各有 ✕；点了之后 `.off` 类生效（划线 + 变淡）。

## P5：间隔重复

![错题本带复习时间](v14/41_sr_wrongbook.png)

```
错题本 2 题   [1 题该复习了]                [再测一次]

磨皮要避免"塑料感"，下面哪个做法对？
错 3 次    该复习了                        ← 琥珀色高亮
来自《我做 Cos 图的 7 条经验》第 3 段  看原文 →

ⓘ 为什么排时间：答错后 1 天复习 → 对了排 3 天 → 7 天 → 16 天 → 35 天；
  再错退回前一档。（间隔重复）
```

### 曲线

```
答错 → 1 天后复习
答对 → 3 天 → 7 天 → 16 天 → 35 天 →（出队）
再错 → 退回前一档
```

**不是固定间隔，是"对了拉长、错了缩短"。**

**实测**：答错 → `wrongBox=1`，下次 `明天`；模拟到期 → `到期=1`；答对 → `stage 0→1`。

## P6：划词标注

```
全文 · 划一下可以标注

第 1 段：先看整体再抠细节，别一上来就调参数。
第 2 段：参数是给别人看的，效果是给自己看的 —— 先看效果。
第 3 段：……
第 4 段：不确定的多跑两版，用数量换质量，别在一个参数上死磕。

选中一行 → 浮出 [＋ 标注这句] → 输入 → 存进标注 tab
```

**实测**：选区检测可用；标注数 2 → 3；新标注进「标注」tab。
