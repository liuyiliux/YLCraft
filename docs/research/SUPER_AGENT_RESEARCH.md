## 1. 核心论点

> 「单任务的上限取决于模型能力，**多任务的上限取决于人的注意力**。」

一个人同时只能跟 3-5 个活跃会话。现有的单 Session Agent 有三个死结：
- 单会话同步阻塞
- 多任务上下文混乱
- 本地设备离线即停止

**Super-agent 的四个特征**：连续 / 高效 / 主动 / 持久。

> 「**单个 ReAct Loop 无法同时支持上述四个特征**，底层需要一套相应的架构。」

---

## 2. 五个模块（骨架）

| # | 模块 | 一句话 |
|---|---|---|
| ① | **双层架构** | Router（常驻、只分派、对外说话）+ Worker（隔离、并行干活）|
| ② | **事件驱动** | 输入从「人打字」变成「环境事件 Trigger」|
| ③ | **面向人的交互** | 异步 ReAct Loop（全双工）+ 按信道定制输出 |
| ④ | **计算/状态/环境分离** | 云端跑 Loop，端侧只放轻量 daemon |
| ⑤ | **Watchdog** | 主系统之外的独立 Agent，监控任务有没有跑偏 |

细节见 [`SUPER_AGENT_MODULES.md`](./SUPER_AGENT_MODULES.md)（reference 子文件，按需查）。

## 3. ⭐ 对我们最有价值的四条

### 3.1 「聊天框为中心是路径依赖」——验证了我们的方向

原文 8.2：

> 「以**聊天窗口为中心**的交互在一定程度上是**路径依赖**的结果。
> 交互可能可以更多地发生在**领域特化的交互界面**中……
> **Session 应当是系统的实现细节，而不应是用户的认知负担。**」

**我们正在做的 Agent 页面改造，方向是对的。** 并且：
- 界面上不该出现「会话」这种底层概念
- 应该按「领域」组织（素材/项目/任务），不是按「会话」

### 3.2 「用户看到的一个会话 ≠ 底层一个 Session」——解决 AI创作/画布的纠结

> 「用户看到的一个会话在**底层未必只对应一个 Session**。」

**AI 创作视图 和 画布视图 = 同一会话的两种呈现。**
不用纠结合并还是分开。

### 3.3 多租户按「上下文共享边界」划分（8.3）

> 「组织在决定如何配备 Super-agent 时，实际上是在**划分上下文共享与隔离的边界**。
> **需要共享上下文的范围共用同一个实例，需要隔离的范围则各自独立配备。**」

**比「一人一进程」精确。** 对我们：**一个工作室/团队 = 一个实例**，
因为同项目的人本来就该共享上下文。

### 3.4 我们 agent 的核心缺陷被点破

> 「相比于在单 Session 中依赖提示词工程和模型临场判断分不分工，
> 双层架构通过让 Router 不直接执行具体工作……**在系统层面**上缓解了这一问题。」

我们现在的 Agent 就是「**单会话 + 靠提示词让它自己分工**」——正是文章说不可靠的那种。

## 4. 实验数据（判断用）

| 方案 | 完成时间 p50 | p95 |
|---|---|---|
| **Super-agent（双层）** | **12.4 min** | **15.7 min** |
| 单会话 + Subagent（中性提示）| — | **29.5 min** |
| 单会话 + Subagent（提示优先委派）| 较快 | 仍有长尾 |

**关键**：中性提示下，5 次运行里**0 次**调用 Subagent，全在主会话里被新消息打断。

**Router 批处理**：事件密度从 1 条/分 → 40 条/分时，
平均 batch 1.0→2.8，单请求耗时 2.5s→3.9s，
**单个决定分摊时间 6.4s→1.6s**（越密越划算）。

**代价**：多会话导致读缓存 token 更高（用 token 换更短更稳的完成时间）。
去掉直通后 Router 决定数 +30%，token +37%。

## 6. ⚠️ 一条安全警告（我们正踩）

8.4 原文：

> 「只要**端侧环境中的凭据能够进入模型的上下文**，正常执行过程中同样存在凭据泄露的风险；
> 因此还需要设计相应的机制，让 Agent 能够在**完全不接触凭据本身**的情况下使用凭据。」

**我们有 5 个平台的 cookie 存在浏览器 profile 里**（1.2 GB）。
**绝不能直接让 Agent 读到 cookie 内容。**
