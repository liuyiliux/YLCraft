## ① 双层架构

### Router 层

**职责**：常驻、承接所有人类交互、汇总跨任务决策、全局记忆。
**关键约束**：**不直接执行具体任务**，只做交互与分派，**甚至可以不配 Bash 工具**。

为什么不会成为瓶颈：
> 「上一轮推理期间到达的环境事件会积压下来、在下一轮一并处理，形成**批处理（Batching）**」

Router 每步通常是「长输入、短输出」，积压事件在 Prefill 阶段并行计算，
**单次请求耗时增长远慢于批处理大小**。

规模不够时可水平切分（Sharding），但「切得越细吞吐越高，分片间连续性越差」。

### Worker 层

**职责**：上下文隔离、挂完整执行工具、专注单一任务。
**配置**：通常要**能力最强的模型**（因为直接决定产出质量）。
**关键约束**：**不直接与人类交互**，向 Router 汇报，由 Router 统一回复。

Worker 内部可以再开 Subagent 或整个 Agent Team，**对上层透明**。

### 与 Agent Team 的区别

| | Agent Team | Super-agent 双层 |
|---|---|---|
| Team Lead | 深入任务细节，承担很重推理 | Router 只处理**任务之间**的关联 |
| 子步骤 | 耦合紧，需高频协调 | Worker 独立推进，同层不通信 |
| 分工方式 | 靠提示词 + 模型临场判断 | **系统层面强制**（Router 不干活）|

## ② 事件驱动

### 3.1 事件过滤：Fast Path / Slow Path

| 层 | 做什么 | 例子 |
|---|---|---|
| **程序层（Fast Path）** | 确定性条件直接准入/拒绝 | 来源、群组范围、用户白名单 |
| **语义层（Slow Path）** | LLM 判断是否需要行动 | 提示词写的策略 |

**目的**：在调模型前先筛掉大部分噪音，省延迟和算力。

### 3.2 事件路由：订阅与直通

**Thread** = 一条事件流（同一个 PR、同一个 IM 话题、同一封邮件串）。

| 路径 | 说明 |
|---|---|
| **已订阅（Fast Path）** | 同一 Thread 后续事件**程序直通**已订阅的 Worker，不经 Router |
| **未订阅（Slow Path）** | Router 仍可观测全局，但只分派未订阅的新事件 |

**多对多**：一个 Worker 可订阅多个 Thread；一个 Thread 可被多个 Worker 订阅。
好处：多个 Worker 在共享环境里**无需点对点通信**，靠同一个 Thread 的事件自然发现冲突。

**实测**：去掉直通后任务完成时间基本不变，但 **Router 决定数 +30%、token +37%**。

### 3.3 上下文组织：Inline & Spill + 链式召回

**核心比喻**：把上下文窗口当 **Cache** 管理。

| 操作 | 含义 |
|---|---|
| **Inline** | 近期很可能用到的信息直接内联进窗口，省掉工具调用往返 |
| **Spill** | 超出预算或低频的完整信息留在窗口外，只留引用/摘要 |

**渐进策略**：
1. 从最少信息开始（ID + 摘要）
2. 利用局部性逐步 Inline（关联对象 ID → 时空相邻内容 → 前后几条消息）
3. 超上限则 Spill（截断 + 保留续读入口）

**链式召回（Chain of Recall）**：
给 Trigger / Thread / Worker Session 各自唯一 ID，注入时内联下一跳的 ID，
底层构成**引用图**，模型可沿引用逐跳按需展开。

> 「浪费上下文窗口，就是浪费模型的智能。」

### 3.4 投机执行（Speculative Execution）

在不确定结果会不会被采用时，**后台提前做**，有价值就交付，没价值就丢弃。

例子：收到会议邀约邮件 → 后台先核日程冲突、备好回复草稿 → 用户过目就能发。
内部实例：群里有人反馈问题 → 后台先复现并找修复 → **确认找到简单修复才交付，否则全程安静**。

## ③ 面向人的交互

### 4.1 全双工：异步 ReAct Loop

| | 经典 ReAct | 异步 ReAct |
|---|---|---|
| 工具调用 | 同步 `run()`，**阻塞**直到完成 | 异步 `start()` / `stop()` |
| 调用后 | 等待结果 | **立即返回 Started** |
| 结果 | 阻塞时返回 | 作为**新事件消息**投递回会话 |
| 期间能接新输入吗 | ❌ | ✅ |

> 「这一异步任务机制已经在 DeepSeek Harness 中实现，但**尚未默认开启**。」

### 4.2 多信道定制输出

| 信道 | 风格 |
|---|---|
| **IM（即时）** | 低打扰、只问直接问题、**单次回复不超过 100 词** |
| **GitHub / 邮件（异步）** | 结构化、高信息密度、完整背景+改动+验证 |

## ④ 计算、状态、环境分离

### 5.1 计算与状态分离

- Agent Loop 计算放**云端无状态弹性容器**
- Session 等持久状态存**数据库**
- 容器可水平扩展/重启/替换，连续性由存储保障

### 5.2 计算与执行环境分离

**问题**：真实环境有未提交改动、私有凭据、内网依赖、特定工具链 —— 复制到云端成本极高。

**解法**：**执行环境留在原地**，端侧只放**不保存会话状态的轻量 daemon**，只负责执行命令+返回结果。

> 「既然难以复制和同步的是环境本身，就**不必让执行环境跟着 Agent Loop 上云**。」

与 Anthropic「脑手分离」思路一致，区别在场景：
那边是托管服务 + 沙箱；这边首先接入**用户日常使用、可能间歇在线的个人机器**（BYOM）。

好处：**支持间歇在线的设备** —— 某台机器重新上线后，云端 Agent 再自动触发任务。

## ⑤ Watchdog

**为什么要外部**：
> 「持久在线的分布式系统很难仅靠主系统内部逻辑保证长期可靠运行，
> 需要在主系统之外引入独立的外部控制回路（Control Loop）。」

**为什么不能只看进程存活**：
> 「许多异常并非进程崩溃，而是模型在执行中**陷入无效循环或偏离目标**。」

**实现**：独立的 Watchdog Session，定时消息驱动。职责：
- 处理接口报错、状态恢复失败等基础设施故障
- **由模型判断各 Worker 是否有实质进展、方向是否偏离整体目标**
- 发现异常及时介入，偶发故障持续复查

**它本身也是完整 Agent**：可以用自然语言问它故障原因，也让它在线上修正主系统行为（增删提示词、调整触发规则）。
