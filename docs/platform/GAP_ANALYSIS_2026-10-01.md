## 一之二：B站子回复已补（2026-10-04）

原文记着「B站子回复 ⚠️ 随顶层返回」，而且 `meta.py` / `comments.py`
两处都写「随顶层评论一起返回，直接看顶层返回即可」——
**这是错的，而且给了一个指向虚空的出路**。

### 实测（BV1UAaS6KEgs，20 条顶层评论）

    6~7 条带 reply_count（16 / 8 / 13 / 1 / 4 / 7 / 12…）
    但每条的 replies 数组 **全空**

原因：项目取顶层走 **WBI 新接口** `x/v2/reply/wbi/main?mode=3`，
它**不内嵌** replies —— 那是**老接口 `mode=1`** 的行为。
于是 `/comments?parent_id=` 报 501「不支持单独取子回复」。

### 但 B站其实能取到

实测两条路（oid=117371205322627, root=319481921680）：

| 端点 | 结果 |
|---|---|
| `x/v2/reply/wbi/main?root=` | `code=-403` 访问权限不足 ❌ |
| **`x/v2/reply/main?root=`**（老接口） | `code=0`，**20 条真实数据** ✅ |

已补 `BilibiliClient.get_replies`（走老接口），meta 声明 `replies`，
实测 `/comments?parent_id=319481921680` 返回 20 条真实楼中楼。

### 顺带修掉的坑：total 语义不同

老接口带 `root=` 时 `cursor.all_count` 返回的是**整个视频的评论总数**
（实测 **1944**），不是这条主楼的子回复数（**16**）—— 差 110 倍。
第一版直接拿它当 `total`，前端会显示"1944 条回复"。已改为不编造总数。

## 一之四：子回复复验（2026-10-04）—— 又推翻了两条结论

B站那个 bug 让我意识到：**「平台限制」类结论可能早就过时了**。
于是对剩下三个平台各做复验（这次**直接打接口**，不靠抽样推断）。

### 结果

| 平台 | 结论 | 依据 |

| X | ⚠️ **半可用** | `reply_count=1` 有，但原始树里被引用 **0 次** |

### 微博：第三次栽在同一个坑上（2026-10-04 下午）

用户直接给了确定有楼中楼的链接（此前两次我都是**抽样**）：

    https://m.weibo.cn/detail/5336295257679240

实测 `GET /api/v1/comments?platform=weibo&item_id=5336295257679240`：

    顶层 20 条 → **20/20 都有 replies**，共 32 条，rootid 零串号
    样本：text="你居然看过[允悲]"  is_mblog_author=True
          （与用户提供的微博 App 截图完全对应：博主回复粉丝）

而我此前写的是「仍未验到」—— 因为翻了 30+ 个内容都没碰到样本。

⚠️ 原来的论证方式本身就该被怀疑，它用了两条**无效证据**：

1. 「实测 20 条里 0 条带 `comments`」—— 那是**抽样**抽到的另一批内容
2. 「MediaCrawler（★66k）也只读 `comments` 且默认开关关着」——
   **别人没实现 ≠ 平台没有这个数据**（他可能是没做，不是做不了）

### ⚠️ 顺带发现一个更隐蔽的 bug：`reply_count` 写死 0

微博**自己给**的 `reply_count` 字段**恒为 0**（实测 20/20 全是 0），
而 `client.py` 里也**写死了** `"reply_count": 0` —— 尽管同一个对象里
`replies` 有真实数据。

前端判断"要不要显示楼中楼入口"用的是：

    (c.reply_count ?? c.rcount) > 0

所以**即便数据抓到了，用户也永远看不到回复入口**。
这比"取不到"更隐蔽：日志里有数据、接口返回 200、就是没人点得开。
已改为 `len(replies)`。

另外 `is_author_reply`（博主本人回复）采集端产出了，但
`comments.py` 的归一化是**白名单式**的 —— 没列出的字段会被丢掉，
所以它到不了前端。已加进白名单。

**教训：加字段要同时看"采集端产出"和"归一化白名单"两处。**


### ⚠️ 本轮最大的教训：`reply_count` 字段**不能用来判断有没有楼中楼**

快手那 15 条评论的 `reply_count` **全是 0**，
我据此写下「快手取不到子回复」——
**但直接打 `sublist` 接口，第一条就返回了 1 条真实数据**（`'男的是腹肌'`）。

也就是说：我第一轮的结论**完全错了**，
错的原因是「抽样恰好没抽到」被当成了「平台没有」。

正确做法：**直接打接口**看返回什么。字段是提示，接口才是事实。

这个坑 B站那次也踩过：先信了「子回复随顶层评论返回」这句话，没实测，
结果那个 `replies` 数组**全是空的**。

### X 的情况（加了诊断日志才定论）

    顶层 9 条评论，其中 3 条带 reply_count=1
    顶层返回的 replies 数组：全空
    打 /comments?parent_id=2105686349768790102 → 200，0 条

加诊断日志后：

    [twitter] 子回复诊断: 树内 9 条，其中 1 条 in_reply_to；
    parent=2105686349768790102 在树内被引用 **0 次** → 命中 0 条

即 **原始响应里根本没有**那些子回复。X 的 `reply_count` 来自服务端统计，
但回复本身**没下发给客户端**（已删／折叠／需额外展开）。

返回值都是 0 条时，「X 侧没给」与「我们过滤掉了」**看起来一模一样** ——
不看原始数据无法区分。代码保留（X 改了就能用），
但**当前不能宣称支持**。

只能说「**仍未验到**」，不能说「确认取不到」——
鉴于快手那次的前车之鉴，没有直接打接口验证之前，

## 一之六：YouTube 评论 500 的真实原因（2026-10-04 复测，结论已被推翻）

原记录（见上一版表格）写的是「匿名 yt-dlp 被拦 / 平台侧限制」。
**这个结论是错的**，本节是推翻过程 + 现状。

### 症状

`GET /api/v1/comments?platform=youtube&item_id=njK0eebUsQw` → **500**
`Sign in to confirm you're not a bot`

### 第一直觉（错的）

这句话直译是「登录以确认你不是机器人」→ 容易得出两个错误结论：

1. 「YouTube 评论区必须登录」→ 去加 cookie / 加登录态
2. 「平台限制，我们做不到」→ 文档记一笔就完事

### 复测数据

**同一 IP、同一分钟、同一份代码**（yt-dlp 默认 client，无 cookie）：

| | njK0eebUsQw | dQw4w9WgXcQ | 9bZkp7q19f0 | BaW_jenozKc |
|---|---|---|---|---|
| 搜索 | ✅ 16 条 | ✅ 299 条 | ✅ 257 条 | ✅ 7 条 |
| watch 页 | ❌ not a bot | ✅ **2,400,000 条评论** | ❌ not a bot | ❌ 已下架 |
| 取评论 | ❌ | ✅ 3 条 | ❌ | ❌ |

扩大到 8 个视频（含 Despacito / Adele Hello / Happy 等顶流）：
成功 **1/8**，唯一成功的是 240 万播放的那条。

### 试过且**全部无效**的手段

| 手段 | 结果 |
|---|---|
| `player_client` = web / web_safari / android / ios / tv / mweb | 6 个，失败视频一律失败 |
| `player_client` = web_embedded | ❌ 失败视频仍失败，**且把能用的 dQw4w9WgXcQ 也弄坏** |

⚠️ `web_embedded` / `mweb` 的**副作用**是本次实测最有价值的发现之一：
它们不是"更宽松的后备 client"，而是**会把本来能用的视频也弄坏**
（`Requested format is not available`）。所以**不能**拿来做 fallback。

### PO Token 也无效（最值得记的一条）

PO Token 是 2025 年后 YouTube 反爬的**真正开关**，本来最有希望。
不是查文档下结论 —— **真的装了测**：

    pip install bgutil-ytdlp-pot-provider      # 2.0.1（只装插件）
    git clone --branch 2.0.1 …/bgutil-ytdlp-pot-provider
    cd server && npm ci && npx tsc            # 装 317 个包
    node build/main.js -p 4416 -H 127.0.0.1    # /ping → {"version":"2.0.1"}

两种模式都试了：

| 模式 | 失败视频 | 原本能用的 dQw4w9WgXcQ |
|---|---|---|
| `bgutil:script-node` | ❌ 仍 not a bot | ❌ **变成 no formats**（32.6s）|
| `bgutil:http` | ❌ 仍 not a bot | ❌ **变成 no formats** |
| `bgutil:http` + 默认 client | ❌ 仍 not a bot | ✅ 正常（31 formats）|

官方文档其实提前说过：*"Providing a PO token does **not** guarantee
bypassing 403 errors or bot checks"* —— 实测确认，而且**有副作用**。

### 精确定位：不是"连不上"，是页面里被标成 LOGIN_REQUIRED

直连 watch 页看 HTML，同 IP、同一分钟、同一个 urllib 请求：

| 视频 | HTTP | 大小 | `playabilityStatus` | 含 `not a bot` |
|---|---|---|---|---|
| dQw4w9WgXcQ | 200 | 1,298,628 | **OK** | False |
| njK0eebUsQw | 200 | 1,228,029 | **LOGIN_REQUIRED** | **True** |

**两个都是 HTTP 200、都带 `videoDetails` 和 `ytInitialData`** ——
页面是完整拿到的，是 YouTube **在页面里把这条视频标成 LOGIN_REQUIRED**。
所以不是连不上、不是被重定向、不是 cookie 没带对，
而是**服务端按视频的判定**，客户端侧没有可绕的开关。

### 顺带修掉的一个通用 bug：错误消息被截断在结论前面

改完上面这些之后，**实测接口返回**才发现消息在出口被切了：

    HTTP 429
    …已试过且无效：7 种 player_client、…、**PO Token**（…）。
    可                                        ← 断在这里

原因：`comments.py` 用 `str(exc)[:300]` 硬截。而平台错误消息是
"解释 + 处置办法"的多行结构，**处置办法总在最后一行**，
按字数硬截正好把它切没 —— 用户看到的是「可」，等于什么都没说。

⚠️ 这个 bug **不只影响 YouTube**，是所有平台长错误消息的通病。
已改成 `_brief(exc, N)`：**保尾**（结论在尾部）、截断处补 `…` 让用户知道
内容被省了、尽量按整行取舍。日志仍打**未截断**的原文，排查不受影响。

教训：写完错误消息**要真的看接口返回的字节**，不能只看异常对象 ——
异常对象是完整的，截断发生在出口。本轮就差点误判成"控制台乱码"。

测试：`backend/tests/test_error_message_not_truncated.py`（7 个）。
其中那个"扫源码禁止裸切片"的测试**第一版有洞**（变异测试发现）：
正则只匹配字面量 `str(exc)[:300]`，把 `_brief(exc)` 换回去竟然全绿。
改成 AST 结构化判定后同一个变异能抓住。

### 真实结论

这是 YouTube 对**当前出口 IP** 的人机校验，**只能靠等 / 换 IP 缓解**。
既不是代码缺陷，也不是"必须登录"，更不是"平台不支持评论"。

### 已做的改动

- `get_comments` / `get_detail` / 搜索 三处都识别该错误 →
  抛 `RiskControlError` → 接口层 **429**（原来 500）。
  500 语义是"我们坏了"，会把排查方向误导到服务端。
