## 抖音「作品列表」已被封（2026-10-11 实测）

用户报错：`获取作品列表失败 … Blocked by ArgusSecurityPlugin Uifid Not Found`。

原报错文案说这是"概率性拦截（社区约 5/8）… 请稍后重试"。
**实测推翻了这两个说法**（同一 cookie、同一 UA，连打 8 次）：

| 端点 | 结果 |
|------|------|
| `aweme/post`（**作品列表**） | ❌ **403 × 8/8** |
| `aweme/detail`（视频详情） | ❌ 403 |
| `user/profile/self`（我的资料） | ✅ **200** ← **登录态是好的** |
| `user/profile/other`（别人资料） | ✅ 200 |
| `comment/list` | ⚠️ 200 但空 body（缺 a_bogus，另一个已知问题） |

### 试过但**全部无效**的手段（别再试了）

- 换 UA：`Chrome/120`、`Chrome/154`、**空 UA** → 全 403
- 补 `msToken`（cookie 里确实没有）→ 仍 403
- 加 `referer` / `Sec-Fetch-*` 头 → 仍 403
- **加 `a_bogus` 签名**（164 字符，签名器工作正常）→ 仍 403
- 换一个**不存在**的 `sec_user_id` → 仍 403
- 移动端 UA → 仍 403

⇒ 结论：**网关按路径拉黑**（`aweme/post` + `aweme/detail`）。

  · **不是**"概率波动"（是 100% 稳定拦截）
  · **不是**登录态失效（资料接口同一 cookie 就是 200）
  · **不是**缺签名（加了也没用）
  · ⇒ **"稍后重试"是无效建议**

⚠️ 与 `apis.py` 里"a_bogus 对**搜索**无用"的记录**不矛盾** ——
那是另一个端点、另一次实验，结论相同（签名救不了）。

### 已经做的改动

1. **报错文案改如实**：说明是稳定封禁、重试无用、且**不是**登录态问题；
   并顺带告诉用户**哪些还能用**（资料 / 搜索）。
2. **`/users/videos` 风控改回 503**（原来 500）——
   500 会让用户以为是我们程序坏了，503 才表达"平台侧不可用"。
   用**异常类型**（`RiskControlError`）判断，不做字符串匹配
   （字符串匹配改文案时会静默失效）。
3. **回归测试**：`tests/test_douyin_env_limited.py` 新增 5 条，
   锁住"不再建议重试 / 不再甩锅登录态 / 503 / 用类型判断"。

#### 抖音 offset 翻页已失效（2026-09-28 复测）

代码注释里"offset=0/20/40 有效"是 2026-09-27 的结论，**现在不成立**：

    offset=0   count=20  -> 18 条  cursor=20  has_more=True   ✅
    offset=20  count=20  ->  0 条  cursor=40  has_more=False  ❌
    offset=5   count=5   ->  0 条  cursor=10  has_more=False  ❌

**在真实浏览器里跑同样的请求，offset=20 也是 0 条** ——
所以这是抖音的**服务端行为变化**，不是我们的代码问题，
也不是"自动化被限制"（真实浏览器也一样）。

**结论：抖音目前只能拿首页（约 18 条）。**
代码保留 offset 递增逻辑，若抖音恢复该能力则无需改动即可生效。

#### ⚠️ 「内容搜索」页**不放**「用户」tab（2026-10-10 定，2026-10-11 补 X）

而「内容搜索」页的用户 tab 只是把**同一个接口换个地方摆**，

> ⚠️ **X 那个 tab 本来就是坏的**：实测搜索返回 **0 条**
> （同一关键词下 综合/最新/媒体 都正常）。
>
> 根因：`TwitterClient.search()` **不判断 `search_type`** ——
> 只会搜内容（只把 product 改成 `People`），拿回的用户对象被当推文解析
> → 一条都解析不出。
>
> 对比：**B站 `search()` 有正确的路由分支**
> （`if search_type == 'user': return self.search_users(...)`）。
>
> ⇒ 所以**不能一刀切全删** —— 要按"该平台这个 tab 是否真能用"逐个判断。

### ⚠️ 「互动数据看不见」的真相：**是转推**（2026-10-11 用户反馈）

用户："能看到了，但是那些互动数据还没有。"

**查下来不是没取到，是转推本来就只有一个数字**。实测该账户的「正在关注」：

```text
33 条里 25 条是**转推**（正文以 `RT @` 开头）
转推：likes=0 comments=0 shares=113   ← 只有转推数有值
原推：likes=85 comments=3 shares=0    ← 数据齐全
```

X 对**转推**只返回 `shares`（转推数）—— `likes`/`comments`
属于**被转的原推**，不在这个条目上。

⇒ 原来的界面把「赞」**写死显示**，于是转推条目全是光秃秃的 `0`，
看着像"数据没取到"。

**修法两条**：

1. **为 0 的一律不渲染**（赞也不再写死显示）
2. **转推显式打标签**：`转推 171` —— 直接把"为什么没有赞"讲清楚

> **教训**：平台给了 0，不代表"没有数据"，也可能是
> **这个字段对这种内容本来就不适用**。
> 界面要么解释，要么别显示那个 0 —— **不要留一个会误导的 0**。

#### ⚠️ 那条 `views=0  # 实测拿不到` 的注释是**错的**

代码里长期写着"浏览量实测拿不到 → 0（不编造）"。
实际它**就在顶层**：

```python
tw["views"] = {"count": "14478", "state": "EnabledWithCount"}
```

**只是不在 `legacy` 里** —— 当初只翻了 `legacy` 就下了"平台不给"的结论。

> **教训**：不要因为"某个子对象里没有"就断定"平台不给"。
> 换个层级找找，或者直接 dump 整个对象的键再下结论。
> 这与之前"`u.core.name` vs `u.name`"是**同一类错误**（只看了一层）。

**修法**：两个解析函数（`parse_tweet_http` / `_parse_tweet_result`）
**都要改** —— 同一份数据两处解析，只改一处会出现
"搜索页有、我的数据没有"。已加测试锁住两者一致。

**映射**：书签 → `collects`（语义一致），浏览量 → `views`，
引用数 → `raw_data.quote_count`（通用结构没有对应字段）。

⚠️ 前端收藏数要**同时认两个键**：小红书一直用 `collect_count`，
X 用 `collects` —— 只读一个另一边就显示不出来。

#### ⚠️ 我犯的错（记录以免重犯）

一开始我**只在小样本上测**（`count=20`，看了几条），
误判成"三个列表都没有 views"，于是写了个 `enrich_views()`
**逐条补 TweetDetail**。

**两个问题**：

1. **白打请求** —— 「正在关注」本来就有，不需要补
2. **平白增加限流风险** —— 一页 20 条 = 多 20 次请求，
   每次都要生成 `transaction-id`，是**显眼的自动化特征**

**已全部删除**（`enrich_views` 函数 + 三处调用）。实测耗时：

```text
正在关注  11.3 秒 → 4.2 秒     （白打的请求去掉了）
我的点赞  ~11 秒  → 3.6 秒
```

> **教训一**：**小样本别下结论**。"我没看到" ≠ "平台不给"。
> 要测就把**整批**都数一遍（这次是 54/54 全有键）。
>
> **教训二**：**别用"多打请求"来补数据缺口** ——
> 这是拿**账号安全**换一个锦上添花的数字。
> 用户比我先想到这一层。

### ⚠️ 列收敛为**公共列库**（2026-10-11 抽出，2026-10-14 覆盖查询页）

### 预览 / 下载（2026-10-11 加）

用户要求："x点赞的列表支持下载和预览 看看查询那里怎么做的"。
照「查询」页（`crawler/index.tsx`）的成熟做法实现，**三个关键点**：

**① 媒体字段只认 `images` / `video_url`**（与搜索页**同一约定**）

后端 `_media_of()` 从 `raw_data._images` / `raw_data._video_url` 取，
组装成前端认的两个键。**作品列表（`/users/videos`）与点赞列表共用
这一个函数** —— 各写一份迟早漂移。

⚠️ **不兜底**：没有直链就空数组/空串，**绝不**拿 `url`（原文链接）兜底。
兜底会让所有图集都有 `video_url`，前端据此把**图集误判成视频**、
渲染出 0:00 空播放器（搜索页踩过一次）。

**② 视频必须走后端代理**（`/api/v1/proxy/video`）

浏览器 `<video>` **一定会带 `Referer`**，而 X 的 CDN **带 Referer 就 403**：

    裸请求（无 Referer）    → 200 ✅
    带 Referer（localhost） → 403 ❌

后端 `proxy.py` 的 `_NO_REFERER_HOSTS` 已含 `twimg.com`，按域名剥掉
Referer 并透传 `Range`（可拖进度条）。**前端不用关心平台差异。**

**③ 图片也走代理 + 用缩略尺寸**

列表用 240px、预览用 800px、缩略图条用 120px ——
原图 1~2MB，几十张会加载很久（看起来像"加载失败"）。

### 实测（2026-10-11）

| 项 | 结果 |
|---|---|
| `/users/likes` | 200，20 条，19 条带视频+封面 |
| 预览视频（代理） | 200 `video/mp4` 579KB |
| 预览图片（代理） | 200 `image/jpeg` 43KB |
| **真实下载一张图** | `success: true`，`saved: 1`，`failed: 0` |
| **真实下载一个视频** | 200 `video/mp4` 578KB，**MP4 签名校验通过** |

⚠️ **下载接口的返回契约是 `saved`（列表）**，不是 `success_count`。
第一版按猜的字段写，会**永远显示"0 张"**（静默错，页面不报错）——
已按 `download.py::download_images` 的真实契约修正并加回归测试。

### ⚠️ 「预览」和「下载」是两条**不同**的路（用户反馈踩坑）

用户反馈："你这个下载不是跳下载页面吗？"

**根因**：第一版把**流地址直接当下载链接**：

```js
a.href = '/api/v1/proxy/video?url=...'   // ← 这是"播放流"
a.download = 'x.mp4'                     // ← 被浏览器**忽略**
```

`proxy/video` 返回 `video/mp4` 流且**不带 `Content-Disposition`**，
浏览器把它当"导航到媒体" → **跳播放页**，`download` 属性形同虚设。

| 用途 | 走哪条路 | 为什么 |
|------|---------|--------|
| **预览播放** | `/api/v1/proxy/video` | 支持 `Range`（拖进度条），剥 Referer |
| **下载文件** | **跳 `/download?url=<原文链接>`** | 与「查询」页同一入口：清晰度/进度/续传/入库都有 |

⚠️ **传给下载的必须是「原文页 URL」**，不是 CDN 直链 ——
下载后端是 **yt-dlp**，它认"网页"不认裸 CDN：

```text
video.twimg.com/...mp4                     → 下载失败 ❌
https://x.com/<user>/status/<id>           → DONE，真存了 mp4 ✅
```

⇒ `TweetDetail` **只下发这一批**。X 的计数（41）包含二级回复
和它未下发的部分，所以**天然对不上**。

⇒ 前端做法：**主动说明**「原帖显示 41 条，实际取到 19 条 ——
X 只下发这一批」，并给「去原站看」的出口。
**不解释 = 用户以为我们漏抓**，这是最该避免的误解。

**② 子回复 X 只给一部分**

点「N 条回复」会按 `parent_id` 去取，但实测：

```text
reply_count=2  → 拿到 1 条
reply_count=1  → 拿到 0 条     ← 点开是空
reply_count=1  → 拿到 0 条     ← 点开是空
```

⇒ 取到 0 时**必须说明是平台没下发**：

> 「X 没有提供这些回复（平台限制）—— 可点「打开原文」去原站查看」

**留空白会让用户以为功能坏了**（实测 3 条里有 2 条是空的，
这个概率很高，绝不能靠"一般都有"糊过去）。

> **通用教训**：平台"计数"和"能取到的"经常不是一回事。
> 两者不一致时，**界面要解释差异**，而不是默默显示小的那个 ——
> 否则用户会认定是我们的缺陷。这与本仓库
> 「宁可报错也不要静默返回空」是同一条原则的延伸。

### 各平台对比

| 平台 | 搜用户 | 用户详情 | 我的数据 |

### 微博（实测免登录可用）

    用户搜索  containerid=100103type=3&q={关键词}&page_type=searchall&page=N
              → cards[].card_type=11 → card_group[] → user{}
    用户详情  containerid=100505{uid} → data.userInfo{}

⚠️ **用户卡片与内容卡片的解析路径完全不同**：
    内容：card_type=9  → .mblog
    用户：card_type=11 → .card_group[].user

⚠️ **`followers_count` 是带单位的字符串**（`"58.8万"`），
不是数字 —— 直接 `int()` 会炸。已有 `parse_count` 处理 万/亿/K/M。

### X（纯 HTTP）

    搜用户   复用 SearchTimeline，只把 product 改成 "People"
             （调研确认 X **不存在**独立的 SearchUser operation）
    用户详情 UserByScreenName（queryId Gb-d6r0vxPOADdG62OEBpQ）
             必须带 9 个 fieldToggles

⚠️ **新旧 schema 并存**，解析要兼容两套：
    旧版扁平：legacy.screen_name / followers_count / ...
    新版嵌套：core.screen_name / relationship_counts.followers /
              tweet_counts.tweets / profile_bio.description / ...

### ⚠️ 「我的数据」的通用陷阱：不能抓页面上的链接当"自己"

微博**没有**"我是谁"的接口。第一版实现从页面抓第一个
`/profile/{uid}` 链接 → 拿到一个 **275 万粉的真实博主**，
还当成"我自己"返回了。

**未登录时页面里全是别人的链接。** 所以：
  · 微博：先查 `/api/config` 的 `login`，未登录返回 None
  · X：handle **只从账号菜单**（`SideNav_AccountSwitcher_Button`）取

**给错人的资料比"没有数据"危险得多。**

### X 的「我的数据」是已知缺口

twscrape 与 Scweet **都没有 `me()`**，全部 `OP_*` 常量里
**没有 Viewer**（已穷尽核对）—— 所以**不臆造 queryId**。
实现为「浏览器读 handle → UserByScreenName」两步，需登录。
