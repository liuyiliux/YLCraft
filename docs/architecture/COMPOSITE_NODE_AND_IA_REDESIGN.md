# 复杂节点设计 + 页面结构分层（修正版）

> **修正一处方向性错误：**
> 我上一版写「页面核心逻辑抽成 `run()`，让画布能调用」——
> **那是让页面配合画布（侵入式改造）。**
>
> **正确的是：画布侧按页面的功能封装接口。页面不动。**
>
> `页面 ← 兄弟 → 画布节点`，两者都调**同一个后端能力**，互不依赖。

---

# 第一部分：修正后的关系模型

## 1. 谁是父谁是子

```
        后端能力（一个 API / 一组 API）
                 ▲            ▲
                 │            │
        ┌────────┴───┐   ┌────┴──────────┐
        │  页面（UI）  │   │  画布节点      │
        │  参数面板    │   │  spec 描述     │
        │  预览/历史   │   │  端口/常用参数  │
        └────────────┘   └───────────────┘
             人点            连线触发
```

🔴 **页面和画布节点是兄弟，不是父子。**
- 页面：给"坐下来慢慢做"的人
- 画布节点：给"搭好流程自动跑"的人
- **两者都直接调后端能力，谁也管不着谁**

## 2. 两种错误的理解（我上一版踩了第 2 种）

| 错误理解 | 表现 | 问题 |
| --- | --- | --- |
| ① 画布 = 页面的壳 | 在页面里加"导出为节点"按钮 | 页面被画布绑住 |
| ② 页面 = 画布的实现细节 | 🔴 **"页面抽 run() 给画布调"** | **页面被画布侵入** |

## 3. 正确：画布侧维护一份 spec

```ts
// 画布侧的文件，不在页面里
// 类似 Toonflow 的 packages/nodes/*
export const imageGenNode: PageNodeSpec = {
  id: 'image-gen',
  label: '生图工作台',
  category: 'generate',

  // ① 怎么调 —— 直接指向后端能力
  invoke: {
    method: 'POST',
    path: '/api/v1/images/generate',
    // 画布字段 → 后端字段的映射
    map: (inputs, params) => ({
      prompt: inputs.prompt,
      reference_asset_ids: inputs.reference,
      model: params.model,
      aspect_ratio: params.ratio,
      n: params.count,
    }),
  },

  // ② 输入端口 = 页面能接受的"外部输入"
  inputs: [
    { id:'prompt',    label:'提示词', type:'text',  required:true },
    { id:'reference', label:'参考图', type:'image', multiple:true },
  ],

  // ③ 输出端口 = 产物
  outputs: [
    { id:'images', label:'图片', type:'image', multiple:true },
  ],

  // ④ 节点上直接露出的参数（≤3 个）
  inlineParams: ['model','ratio'],

  // ⑤ 精调入口（跳页面，带上当前参数）
  openPage: (params) => `/image-gen?model=${params.model}&ratio=${params.ratio}`,
};
```

**页面完全不知道这个文件的存在。**

## 4. 所以「加新用途」的成本

| 要加的 | 改哪 | 页面动不动 |
| --- | --- | --- |
| 新基础节点 | 画布侧加一个节点类型 + 调后端 | ❌ 不动 |
| 🔴 **新复杂节点（包装已有页面）** | **画布侧加一个 spec** | ❌ **不动** |
| 新模板 | 连好的图存成模板 | ❌ 不动 |
| 页面自己迭代 | 页面自己改 | — |

🔴 **这就是"加新用途不改代码"的真实含义：画布侧加配置，两边都不动。**

# 第二部分：唯一需要注意的例外

## 5. 什么情况下页面要"动"

**只有一种：某个能力现在纯粹在前端算，后端没有。**

比如 `/image-editor` 的 9 个工具（裁剪/滤镜/水印/字符画）—— 它们很可能是**浏览器 canvas 里算的**，后端没有对应 API。

这时画布要复用它，有两条路：

| 路 | 做法 | 页面动不动 |
| --- | --- | --- |
| **A（推荐）** | 把那个**纯函数**抽成共享模块（`shared/image-ops.ts`），页面和画布都 import | 页面改 import，**逻辑不动** |
| B | 后端补一个同名 API | 页面不动，后端加 |

**A 是"抽共享函数"，不是"改页面逻辑"。**
而且这只能针对**纯前端计算**的部分 —— 有模型的（生图/动图/3D）后端都有 API，不需要动页面。

## 6. 所以真正的"改造清单"是这份（不是页面清单）

| # | 要确认的事 | 为什么 |
| --- | --- | --- |
| 1 | **后端 API 是否独立可用**（不依赖前端拼好的东西） | 画布没有页面上下文 |
| 2 | **产物是否有稳定引用**（`asset_id` / `task_id`） | 画布节点要把产物接下去 |
| 3 | **参数是否能全量传**（页面上的每个参数，后端都认吗） | 否则"打开页面精调"和"节点运行"结果不一致 |
| 4 | 纯前端能力是否已抽成共享函数 | 见上 |

**这四条查完，画布侧就能写 spec 了。一条都不用改页面。**

# 第三部分：复杂节点的设计（不变）

## 7. 三条路选 A

| 路径 | 做法 | 出处 | 成本 |
| --- | --- | --- | --- |
| **A. 页面能力包装** | 画布侧的 spec 描述"这页能干什么、怎么调" | 🔴 **Lovart 的 Skill**（点开是表单）/ Toonflow 的 node 插件 | **低** |
| B. 子图折叠 | 一组节点折叠，双击展开 | Blender Node Group | 中 |
| C. 子流程引用 | 节点 = 引用另一张画布 | n8n Sub-workflow | 中高 |

**定两条：**
- 🔴 **系统复杂节点 = 不可展开**，只能「打开完整页面」
- 🔴 **用户自己打的组 = 可折叠成"我的流程"节点**

（系统节点展开会露馅：页面内部不是我们的节点组成的，展开是另一套 UI）

## 8. 🔴 参数分两档（这是"复杂节点不复杂"的唯一办法）

```
┌─ @生图工作台 ─────────────────────┐
│ 输入                               │
│   ● prompt       ← 从连线来        │
│   ● 参考图 ×3    ← 从连线来        │
│                                   │
│ 参数（就这两个）                    │
│   模型  GPT Image 2  ▾            │
│   比例  2:3          ▾            │
│   ⚙ 还有 4 项                     │
│                                   │
│ 输出  ● 图片                       │
│                                   │
│ [▶ 运行]      [打开完整页面 ↗]      │
└───────────────────────────────────┘
```

| 档 | 在哪 | 谁用 |
| --- | --- | --- |
| 常用参数（≤3） | 节点上直接改 | 90% |
| 其余 | 点「打开完整页面」 | 要精调 |

## 9. 三个动作要分清

| 动作 | 行为 |
| --- | --- |
| 单击 | 选中 + 右侧参数面板 |
| 双击 | （系统节点）无 /（用户组）展开 |
| 「打开完整页面」 | 跳页面，**带上当前参数** |

## 10. 视觉规范

| 元素 | 规范 |
| --- | --- |
| 前缀 | `@` |
| 边框/底 | 紫色（`#a78bfa`） |
| 图标 | 用页面自己的图标 |
| 节点库 | 分两栏：基础节点 / 复杂节点 |

# 第四部分：导航分层

## 11. 🔴 先分清两件事

| | 目的 | 关注谁 |
| --- | --- | --- |
| **架构分层**（基础/组合/画布） | 让同一份后端能力被两个入口复用 | 开发者 |
| **导航分层** | 让用户快速找到要做的事 | 用户 |

**导航如果也叫"基础功能/组合功能"，用户会先想"这算哪层" —— 那是我们的事。**

## 12. 现状：8 组 44 项摊平

```
世界观 / 创作工作台 / 采集与下载 / AI创作 / 编辑制作 / 阅读中心 / 发布运营
```

**问题：**
1. 按功能域分，不按任务分 —— 想"做一集短剧"得跨 4 个组
2. 44 项太长 —— Lovart 只有 8 项，LibTV 只有 4 项
3. **画布藏在"创作工作台"第 3 个** —— 它才是枢纽

## 13. 建议：6 项，按任务阶段

```
▸ 画布        ← 枢纽，放第一个
▸ 项目        ← 组合流程
▸ 工作台      ← 单步组合
   生成：生图 / 动图 / 视频 / 3D
   编辑：图片 / 剪辑 / 字幕 / BGM
   出片：合成 / 发布
▸ 工具        ← 基础功能
   裁剪 · 滤镜 · 抠图 · 提示词优化
▸ 资产        ← 素材 / 角色 / 世界观 / 采集
▸ 设置        ← 账号 / 任务 / 配置
```

**三层映射：**

| 层 | 导航哪 | 用户看到 |
| --- | --- | --- |
| 基础 L1 | ▸ 工具 | 「工具」 |
| 组合 L2 | ▸ 工作台 | 「工作台」 |
| 画布 L3 | ▸ 画布（第一项） | 「画布」 |

🔴 **用「工具 / 工作台 / 画布」三个词，不用「基础功能 / 组合功能」。**
