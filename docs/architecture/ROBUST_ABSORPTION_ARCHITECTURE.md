# YLCraft 稳健架构：如何吸收任何新项目（2026-10-17）

> 本文不是功能清单，是**吸收协议**。
> 目的：以后每遇到一个新项目（OhMyGame / ArtCraft / BeefTV / OpenMontage / 下一个没见过的），
> 都能**用同一套流程判断"要不要学、怎么学、学到哪一层"**，而不是推翻重来。
>
> 依据：`docs/research/2026-10-1*` 下 9 篇实测文档 +
> 本地实测的 4 个真实产品（OhMyGame 出图成功 / ArtCraft 3D舞台 / BeefTV 画布 + 源码 / 即梦·可灵·海螺等）。

---

## 一、先立一条硬规矩：证据分级

**在动任何代码之前，先给这个新项目定级。**

| 级别 | 含义 | 允许的结论 |
| --- | --- | --- |
| **L0 听说** | 只看到文章/README | ❌ 不许写进架构文档 |
| **L1 读到** | 读过源码/文档，没跑过 | ⚠️ 只能写"它声称…" |
| **L2 装上** | 装好能启动 | ✅ 可写"界面/流程存在" |
| **L3 打通** | 亲手跑通核心流程 | ✅ 可写"它的做法有效" |
| **L4 压测** | 知道它在什么情况下坏 | ✅ 可写"该抄/该避" |

### 这条规矩的代价，我们付过三次

| 事故 | 真相 |
| --- | --- |
| 我说「BeefTV 是 Docker Web 服务，文章说 Wails 是错的」 | **我错** —— QUICKSTART 写了桌面版是主形态，我只看漏了 |
| 我说「BeefTV 有画布工作台」 | 是的，但**Agent 在服务端形态下不可用**（设计如此），我一开始当 bug 查了 1 小时 |
| 我曾把"读文档"标成"第一手观察" | 没看过 UI 就写了结论 |

> **规矩：`L0/L1` 的结论必须标注等级；只有 `L3+` 才能写进"该抄"。**

## 二、三层架构：什么该稳，什么该换

这是本文的核心。**把系统切成三层，只有 L0 是"不许动"的。**

```
┌─────────────────────────────────────────────────────────┐
│ L2 实现层（随时可替换，吸收新项目的主战场）                 │
│   具体 provider / 具体 UI 组件 / 具体技能 / 具体平台采集器  │
├─────────────────────────────────────────────────────────┤
│ L1 契约层（稳定，但可扩展；吸收 = 在这里加东西）             │
│   操作注册表 / 模型用途槽位 / 资产引用格式 / 技能格式        │
├─────────────────────────────────────────────────────────┤
│ L0 内核层（不变量，任何项目都不许改）                       │
│   图结构 / 身份 / 溯源 / 预算 / 证据 / 幂等                 │
└─────────────────────────────────────────────────────────┘
```

### L0 内核：六个不变量

这六件事**在所有我们实测过的产品里都存在**，且形态高度一致。
**它们不是"我们选的技术"，是"这个行业的问题本身"。**

| # | 不变量 | 它解决的问题 | 业界一致的形态 |
| --- | --- | --- | --- |
| 1 | **图结构**（节点 + 类型化边） | 生成有依赖关系 | OhMyGame 画布 / BeefTV 画布 / Infinite Canvas / ComfyUI / 我们的 `CanvasConnection` |
| 2 | **身份**（主体 + 变体） | 同一个角色/物体多次出现要一致 | LTX Elements / Dashtoon 角色映射 / ArtCraft Characters / 我们的角色库 |
| 3 | **溯源**（产物从哪来） | 出问题要能回溯 | 我们的 Asset Hub / BeefTV `canvas.task.bind` / ArtCraft My Library |
| 4 | **预算**（花多少、谁批的） | 生成要花钱 | ArtCraft `COST BREAKDOWN` / BeefTV `Costs 14` / OpenMontage 预算治理 |
| 5 | **证据**（这个结论可靠吗） | 判断要能复核 | 本文的证据分级 / BeefTV「已保存，尚未测试」 |
| 6 | **幂等**（同一次操作重放安全） | 重试不能重复扣费 | BeefTV `ReplaySafe` + `revision CAS` + `operationId` 复用检测 |

> 🔴 **判据：如果新项目改的是这六件事之一 → 它可能在教我们新东西（进 L1 讨论）。
> 如果它只是换了个实现 → 它是 L2，看看就好，不动我们的代码。**

### L1 契约层：四个可扩展点

**这是"吸收"真正发生的地方。** 我们已有的四个可扩展点：

| 契约 | 我们现在的形态 | 吸收新项目时怎么用 |
| --- | --- | --- |
| **操作注册表** | Agent tool registry | 新工具 = 加一个 descriptor，不写死流程 |
| **模型用途槽位** | provider + capability | 新模型 = 填槽位（生图/视频/文本/助手） |
| **资产引用格式** | `reference_asset_ids` / `<subject>` | 新参考机制 = 映射到这套 ID |
| **技能格式** | `SKILL.md` | 新方法论 = 写一份 md，不改代码 |

### L2 实现层：吸收的主战场

**绝大多数新项目落在这一层。** 换实现不影响架构。

## 三、🔴 吸收协议：五步法

遇到任何新项目，按这个顺序走。**不许跳步。**

### 第 1 步：定级（5 分钟）

- 只看到文章 → **L0**，写一行备忘录，**结束**
- 能拿到源码 → 读 README + 部署文档，**L1**
- 能装上启动 → **L2**
- 能跑通核心流程 → **L3**
- 知道它在什么条件下坏 → **L4**

> **停止规则**：L1 以下不许写架构结论。
> **省时间规则**：先读部署文档再动手 —— BeefTV 我踩了一小时 Docker，
> 而 `docker-compose.yml` 里那句 "the server profile has no launch token" 早就写了答案。

### 第 2 步：抽契约（30 分钟）

**不问"它有什么功能"，问"它暴露了什么接口/数据结构"。**

具体要找四样东西：

1. **它的操作/工具清单** → 有没有注册表？（BeefTV 有 `/ops`，21 个 op）
2. **它的模型配置结构** → 怎么声明用途？（BeefTV 四个槽位：生图/视频/文本/助手）
3. **它的资产引用格式** → 怎么指代"同一个东西"？（LTX `<subject>`，Dashtoon 角色映射）
4. **它的技能/提示词格式** → 方法论是代码还是内容？（BeefTV 33 个 `SKILL.md` 形态的 md）

### 第 3 步：归类到 L0/L1/L2

| 如果它改的是… | 结论 | 动作 |
| --- | --- | --- |
| **L0 六不变量之一** | 🔴 **重要** | 进第 4 步，认真评估 |
| **L1 四个契约之一的形状** | ⚠️ **可扩展** | 记下，可能需要加字段 |
| **纯 L2 实现** | ✅ **参考** | 看有没有具体做法值得抄，**不动架构** |
| **我们完全没有的维度** | 🔴 **新领域** | 单独评估，可能需要新增 L0/L1 |

### 第 4 步：只在 L0/L1 才动代码

**判断标准（三条全部满足才改）**：

1. 它解决的问题我们**已经遇到**（不是"以后可能会"）
2. 业界**多家一致**（不是一家独有）—— 我们的实测里至少 2 家做同样的事
3. 不改会**持续产生错误**（不是"不够优雅"）

> 举例：`@` 引用素材这事，**即梦/可灵/海螺/RunningHub/BeefTV 五家都有**，
> 我们 `ChatRequest` 连字段都没有 → **满足三条，该改**。
>
> 反例：BeefTV 的「小地图」很酷，但我们画布目前规模不大，
> 不满足第 1 条（还没遇到）→ **记为 L2 参考，不动**。

### 第 5 步：写进研究文档，标注等级与结论

**格式固定**（照抄这个模板）：

```markdown
## <项目名>（<日期>）
- 证据等级：L0/L1/L2/L3/L4
- 它改的层：L0 / L1 / L2
- 它解决的问题：
- 我们的对应：
- 结论：该抄 / 该避 / 仅参考
- 待核实：
```

## 四、业界已收敛的 8 个模式（L3 级，可直接用）

这些是**至少两家实测产品都做了、且我们已跑通或读到源码**的。
**可以当作架构基线，不需要再论证。**

| # | 模式 | 证据 | 我们的状态 |
| --- | --- | --- | --- |
| 1 | **`@` 引用素材** | 即梦/可灵/海螺/RunningHub/BeefTV（5家） | ❌ **`ChatRequest` 无字段** |
| 2 | **工具 = 数据不是代码** | BeefTV `/ops` 注册表（源码） | ⚠️ 有 registry，但流程仍写死 |
| 3 | **模型按用途分槽位** | BeefTV 四槽 / OhMyGame usages / ArtCraft 62模型 | ⚠️ 有 capability，无"助手跟随文本" |
| 4 | **成本明细在生成前** | ArtCraft `COST BREAKDOWN` / BeefTV `Costs 14` | ❌ 没有 |
| 5 | **配置状态分"已保存/已测试"** | BeefTV `● 已保存，尚未测试` | ❌ 没有 |
| 6 | **技能是内容不是代码** | BeefTV 33 个 22K 字级 md | ⚠️ 有 13 个，**无使用数据** |
| 7 | **阶段门禁 + 必须确认** | 森海 9 Phase / ArtCraft `Build`→`Record` | ❌ 确认按钮实测点了不生效 |
| 8 | **画布减噪工具** | BeefTV 隐藏连线 / 网格吸附 / 自动整理 / 小地图 | ❌ 一个都没有 |

## 五、业界已暴露的 6 个反模式（L3 级，一定要避）

**这些是我们实测时踩到或看别人踩到的坑。**

| # | 反模式 | 谁犯的 | 我们的状态 |
| --- | --- | --- | --- |
| 1 | 🔴 **原始错误码甩给用户** | BeefTV `Request failed with status code 403` | ❌ 我们更糟——**实测甩过 SQL 给用户** |
| 2 | 🔴 **结构化数据不清洗就落地** | 【#2 技能要"洗掉 Markdown 符号"才喂模型】 | ❌ 我们 `JSON.stringify(step.output)` 直接甩 UI |
| 3 | 🔴 **确认按钮存在但不生效** | — | ❌ 我们两个"确认执行"按钮实测点了没反应 |
| 4 | **"正在开发"假装有** | ✅ BeefTV 做得对（明确标注） | ⚠️ 我们要学它 |
| 5 | **README 声称 ≠ 能用** | OhMyGame README 说支持图像，实际要手改配置 | ⚠️ 我们自己也有这类文档 |
| 6 | **装了 ≠ 验证了** | 我自己的教训 | ✅ 本文第一节就是对策 |

## 六、这个架构怎么"吸收未来项目"

### 6.1 为什么它能吸收

因为**它把"变"关在了 L2**。

- 新 provider 出现 → 填槽位（L1 契约不变）
- 新 UI 范式出现 → 换组件（L0 图结构不变）
- 新方法论出现 → 写 md（L1 技能格式不变）
- 新平台出现 → 加采集器（L0 溯源不变）

**只有一种情况需要改 L0：当我们发现"六不变量"少了一个。**
而这是**极低频事件** —— 至今只发生过一次（"幂等"是后来才意识到的）。

### 6.2 吸收的产出物固定是三种

任何新项目经过五步法，最终只会产出三类东西之一：

| 产出 | 落到哪 | 例子 |
| --- | --- | --- |
| **一条 L0 补丁** | 架构文档 + 代码 | 「幂等要显式建 `operationId`」 |
| **一个 L1 扩展** | 契约 + 字段 | 「`ChatRequest` 加 `attachments`」 |
| **一条 L2 参考** | 研究文档 | 「BeefTV 有小地图，规模上来再做」 |

**如果产不出这三类之一，说明这个项目对我们没价值 —— 记一行备忘录就够，别浪费时间。**

## 七、当前优先级（按吸收协议评估后的结论）

**只列满足"三条全中"的**（我们已遇到 + 多家一致 + 不改会持续出错）：

| 优先级 | 事项 | 为什么是现在 |
| --- | --- | --- |
| **P0** | `ChatRequest` 加 `attachments` + 输入框 `@` 引用 | 5 家一致，我们连字段都没有，用户已经在问 |
| **P0** | 确认/取消按钮真正生效（幂等 + operationId） | 实测点了没反应，是**当前最直接的"看起来有其实是坏的"** |
| **P1** | 工具结果分层渲染（`summarizeToolResult` 不再压成"返回字段：url…"） | `JSON.stringify` 甩 UI，用户看不懂 |
| **P1** | 配置状态区分"已保存/已测试" | 避免"配了以为能用" |
| **P2** | 成本明细进确认卡 | 花钱的事必须先知道 |
| **P3** | 画布减噪工具（隐藏连线/网格吸附/自动整理） | 画布规模还没到痛点 |

> **注意 P0 两条都是"已经坏了"而不是"缺新功能"** ——
> 这符合吸收协议第 4 步：**先修持续出错，再加新东西。**

## 八、这份文档怎么用

**下次遇到新项目时：**

1. 打开本文 → 看第一节，给项目定级
2. 看第二节，判断它改的是 L0/L1/L2
3. 按第三节五步法走
4. 看第四节，它做的我们是不是已经有了（8 个收敛模式）
5. 看第五节，它犯的我们是不是也在犯（6 个反模式）
6. 结论只能落在第六节那三类之一

**每吸收一个项目，回来更新第四、五节的表** —— 那两张表会越来越厚，
而**架构本身不用变**。这就是"稳健"。
