## 一、问题 1：画布属于项目，按什么维度？

### 1.1 先看别人怎么分

| 平台 | 画布的归属维度 | 证据 |
| --- | --- | --- |
| **OhMyGame** | **按项目**（`projects/<uuid>/workspace/canvas/boards/`） | 我实测看到这个路径 |
| **BeefTV** | **按工作区 + 多画布**（`未命名工作区 / 画布 1 ▾`） | 实测截图，顶部有画布切换器 |
| **ArtCraft** | **按场景**（`Untitled New Scene`），没有项目概念 | 实测截图 |
| **Infinite Canvas** | **按文件**（boards.json） | 读源码 |
| **ComfyUI** | **按工作流文件**（.json） | 公开文档 |

**两种维度都存在：**
- **按项目**（OhMyGame）—— 画布是项目的附属物
- **按产出物**（ArtCraft 的"场景"、BeefTV 的"画布1/2/3"）—— 画布是独立的工作单元

### 1.2 我们该按哪个维度

**答：按「工作单元」分，不按项目分。**

理由三条：

| # | 理由 |
| --- | --- |
| 1 | **一个项目可以有多种画布** —— 分镜画布、角色设定画布、成片组装画布，目标和粒度都不同 |
| 2 | **一张画布可以跨项目** —— 把 A 项目的角色和 B 项目的场景拼一起，是真实需求 |
| 3 | **`DESIGN.md` 已经把它定为"独立创作画布"** —— 不是"项目画布" |

**所以正确形态是：**

```
画布 = 独立实体，有自己的名字、自己的节点、自己的版本
       ↓ 松耦合
  节点上带 project_id（可选）
       ↓
  能按项目筛选"这个项目用了哪些画布"，但画布不被项目"拥有"
```

**类比**：像 Figma 的文件——可以放进 Project，但文件本身独立，不放在项目里就活不了。

### 1.3 界面怎么体现

```
现在（错的方向）：  创作项目 → 某项目 → 展开 → 画布列表
正确形态：         独立「创作画布」入口（保持现在的位置）
                   + 画布页顶部有「关联项目」下拉（可选，能改）
                   + 项目页里有「本项目相关画布」的只读列表（跳过去）
```

**结论：`/canvas` 保持独立，不挂到项目下。我上一版错了。**

## 二、问题 2：要不要做 n8n / 扣子那种工作流？

### 2.1 先把三种"看起来都像工作流"的东西分开

| 东西 | 本质 | 我们有没有 | 状态 |
| --- | --- | --- | --- |
| **A. Skill Bundle** | **文本化流程**：多个 SKILL.md 组合，`/skill_name` 触发 | ✅ 有 | `DESIGN.md`：完整 |
| **B. 创作画布** | **产物关系图**：节点是图/视频/文本，连线是语义关系 | ✅ 有 | 部分 |
| **C. Agent Run** | **执行记录**：每步工具调用、输入输出、trace | ✅ 有 | 有 trace |

**n8n / 扣子的"工作流"是第四种东西：**

| 东西 | 本质 |
| --- | --- |
| **D. 自动化编排** | **操作流水线**：节点是 HTTP/LLM/分支/循环，**有触发器、定时、重试、错误分支** |

### 2.2 关键区别：节点代表什么

| | 节点代表 | 数据流向 | 触发方式 |
| --- | --- | --- | --- |
| **n8n / Coze** | **一个操作** | 上一个节点的输出 = 下一个的输入 | 手动/定时/webhook |
| **ComfyUI** | **一个处理步骤** | 有类型化端口，串成管线 | 手动跑一次 |
| **我们的画布** | **一个产物** | 语义关系（参考/上下文/生成/顺序） | 手工编辑 |

**这三者不是同一件事。**

### 2.3 我们该不该做 D？

**答：不该做成画布，但该借它的三样能力。**

### 不该的理由

1. **会和 A（Skill Bundle）职责重叠** —— 我们已经有"可复用工作流"了，再加一个节点图会分不清该用哪个
2. **我们的用户不是工程师** —— `DESIGN.md` 第一条约束是「**降低门槛**：用户只需要表达目标和选择内容，不必先理解 Prompt 工程、Tool schema、Run、Memory」
   **节点图 = 让用户理解数据流，这违背第一条约束**
3. **我们的核心场景是一次性创作** —— 小说→短剧是"做一件作品"，不是"配一个每晚跑的自动化"

### 该借的三样

| # | 借什么 | 为什么 |
| --- | --- | --- |
| 1 | **执行记录可视化**（每节点输入/输出/耗时/状态） | 我们画布已有"运行 trace"，但**没做成节点级可看** |
| 2 | **可重跑子图**（选中几个节点 → 重跑这一段） | Agent 改坏了，能只重跑受影响的部分 |
| 3 | **触发器**（"这个画布每晚自动跑一次"） | 批量化生产时有用，但**优先级低** |

### 什么时候才值得做 D

**触发条件（三条同时满足）：**
1. 用户开始抱怨"每次都要手工点一遍"
2. 出现"同样的流程我要重复做 10 次以上"的真实案例
3. Skill Bundle 已经不够用（比如需要条件分支、循环、失败重试）

**现在一条都不满足。**

## 三、产品结构（修正版）

### 3.1 底座不变

```
┌──────────────────────────────────────────────────────────┐
│  素材资产中枢（Asset Hub）                                │
│  所有产物、血缘、版本、项目关联                            │
└──────────────────────────────────────────────────────────┘
                          ▲
┌─────────────────────────┴────────────────────────────────┐
│  Agent Skill 运行时                                       │
│  SKILL.md · slash 激活 · Bundle（= 我们已有的工作流）      │
└──────────────────────────────────────────────────────────┘
                          ▲
┌─────────────────────────┴────────────────────────────────┐
│  创作项目（主链路）                                        │
│  小说 → 世界 → 角色 → 大纲/章节/正文 → 剧本 → 分镜        │
└──────────────────────────────────────────────────────────┘
                          ▲
        ┌─────────────────┼─────────────────┐
        │                 │                 │
   AI 创作工具        创作画布（独立）      编辑制作
   （生图/视频/3D）   产物关系图            （剪辑/字幕/BGM）
```

**画布是并列的工具之一，不是中心。**

### 3.2 画布的准确定位

> **画布 = 把「已经存在的产物」摆在一起、连线、看清关系的白板。**

它**不生产**东西（生产是工具的事），**不驱动**流程（驱动是 Skill 的事）。
它做三件事：
1. **摆**（把产物放进来，看它们的关系）
2. **连**（表达依赖：这张图参考那张图）
3. **出**（组合成一条时间线，导出成片）

**现在缺的是第 3 件（出片）和第 1 件的入口（从工具加入画布）。**
